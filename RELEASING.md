# リリースとバージョン番号

この文書には、バージョンの付け方・互換性の約束・手順・検査の一覧（規則）を記載します。理由と退けた案は [docs/decisions.md](./docs/decisions.md) に書き、同じ内容を 2 か所に記載しません（「品質の仕組みの理由」の「規則を 1 か所に書く」）。

## バージョン番号の方針

[Semantic Versioning 2.0.0](https://semver.org/lang/ja/) に厳密に従います。npm の利用者は `^1.2.0` のような範囲を指定して依存関係を管理し、「メジャーが同じなら互換」という前提で自動的に更新されるためです。番号自体には日付やデータのバージョンの意味を持たせず、「どの時点の法令・官報まで反映したか」は番号とは別の `dataVersion` で示します。

### 用語

この文書と decisions.md のバージョンの区分・互換性の約束・品質の仕組みでは、次の言葉をこの意味だけで使い、言い換えません。

- **約束**: 利用者向けの文書（decisions.md の 38 番の構成）と型の説明（TSDoc）と decisions.md に書いた、利用者に見える挙動
- **結果**: 関数とメソッドが返す値、投げる例外の `code` とクラス、診断が返す項目。メッセージの文言は含まない
- **不具合**: 次のどちらか。入ったバージョンは問わない。(1) 約束から外れた結果。法令・公式データと食い違う計算も含む。(2) 同じ種類の入力や誤りに対して呼び出しごとに結果がそろっておらず、文書と決定がそれを決めていない（欠けている、互いに食い違う）もの。(2) は、直すバージョンで decisions.md に規則を書き、規則から外れた側を直す。そろえる向きは、決定の文書の既存の考え方に合う側にし、決め手がなければ変わる呼び出しの少ない側にする
- **退行**: 前のバージョンでは約束どおりだった不具合。不具合の一種で、区分では区別しない
- **不具合の修正**: 不具合の結果を直す変更。例外を投げる向き・投げなくなる向きを問わない
- **約束のない挙動の変更**: 約束のない結果を変える変更で、不具合の (2) に当たらないもの
- **バージョン**: npm に公開する、番号の付いたパッケージ（パッチバージョン・マイナーバージョン・メジャーバージョン、前のバージョン・今のバージョン）。刊行物と法令の呼び方（言語ごとの呼び方、年・日付の付いた法令の呼び方）だけは旧い用語のまま書く（`check-claims` が確かめる）
- **公開物**: npm に公開するファイル
- **時間の上限**: `pnpm check` は手元の 1 コアで 3 分、CI の全件は 1 ジョブ 10 分。決まりとして守る時間（「品質の仕組みを足すとき」の 5）
- **タイムアウト**: ワークフローの `timeout-minutes`。止まったジョブを終わらせる安全装置で、時間の上限とは別のもの
- **注意**: 失敗にしない知らせ（手元の開発環境のバージョンの違い、CI のジョブの時間が中央値の 1.5 倍を超えたこと）
- **警告**: Node.js の警告（失敗にする）と、診断の重さ `warning` だけを指す

### 区分

| 変更                                                                                                                                                                                                                                   | 1.0.0 以降 | 0.x      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | -------- |
| 公開している関数・オプション・エクスポートの削除や改名、戻り値の形の変更、既定値の変更、判定の優先順位の変更、対応年の縮小、Node.js の打ち切り、コンパイルが通らなくなる型の変更、利用者が実装するインターフェースへの必須の項目の追加 | メジャー   | マイナー |
| 約束のない呼び出しを新たに例外で止める変更（不具合の (2) に当たるものは除く。それは不具合の修正の行）                                                                                                                                  | メジャー   | マイナー |
| 機能の追加、規則で計算する提供元の対応年の拡大、約束のない挙動の変更、非推奨にすること、誤った祝日の `key` の修正（decisions.md の 25 番）                                                                                             | マイナー   | マイナー |
| 不具合の修正                                                                                                                                                                                                                           | パッチ     | パッチ   |
| 公式データの反映（年ごとの表で持つ提供元に告示済みの年を足すことを含む）                                                                                                                                                               | パッチ     | パッチ   |
| 文書・性能・サイズの改善、公開物からの届かない部分の整理（結果が変わらないもの）                                                                                                                                                       | パッチ     | パッチ   |

変更が 2 つ以上の行に当たるときは、バージョンの大きいほうの行で出す。どの行に当たるか迷うときは、利用者のコードや結果が壊れうるなら 1 行目として扱う。この表が区分の唯一の判定で、ほかの節と decisions.md は行を指す。

- **先送りした項目**は、次のマイナーバージョンの範囲に入れて作業指示にします。公開日は対象範囲が確定した日とし、公開日を先に決めるために対象範囲を縮めることはしません。先送りの間も、区分の表でパッチに当たる変更は、ほかの期間と同じにパッチで出します。先送りした項目のうちパッチに当たると分かったものは、次のマイナーバージョンを待たずにパッチで出してよい
- **公式データの反映はパッチ**とします。出力を固定したい利用者には、バージョンの完全一致での固定を README で案内しています（理由は decisions.md の 32 番）
- 公式データの反映と同時に API を足す場合は、マイナーにします（データの反映だけを急ぐ場合は、先にパッチで出します）
- **年ごとの表で持つ提供元（シンガポール）に新しい年を足すのはパッチ**です。マイナーに置く「対応年の拡大」は、規則で計算する提供元（日本・英国・フランス）が計算の範囲そのものを広げる場合です（理由は decisions.md の 32 番）
- 不具合の修正の CHANGELOG には、Fixed に、外れていた約束（どの文書・決定・型の説明か）か、そろっていなかった呼び出しと同じバージョンで書いた規則を書き、古い結果に頼った利用者がいそうなら影響も書きます。1.0.0 以降、公開から複数のマイナーバージョンを経た挙動が文書と違うときは、直す前に次の 3 つのどれにするかを決め、決めた結果と理由をそのバージョンの CHANGELOG に書きます: コードを文書に合わせる（パッチ。Fixed）、文書を挙動に合わせる（パッチ。Fixed に「文書を直した」と書く）、挙動の変更としてマイナーバージョンで扱う（Migration）。0.x ではこの 3 択を使わず、不具合の修正として扱います（理由は decisions.md の 32 番）
- **誤った祝日の `key` の修正はマイナー**とします。旧い `key` を `keys` で受け付ける期間を置き（診断の `deprecated-option` で知らせる）、移行ガイドに書きます（理由は decisions.md の 25 番）。その仕組みと前のバージョンとの祝日データの比較（`data-compare`）での扱いは、実際に必要になったバージョンで作ります
- **記録の書き分け**: 利用者向けの変更は英語で `CHANGELOG.md`（Added・Changed・Deprecated・Removed・Fixed・Security・Data・Migration）、公開物の変わらない品質の仕組みの変更（検査・CI・リリースの手順）は日本語で `docs/development-log.md`（npm の公開物に含めない）に書きます。どちらも 1 項目 1 行で、何を追加・廃止・変更したかを記録し、動かし方が変わる場合は環境変数・コマンドだけを書きます。経緯・退けた案・測定の詳細はコミットメッセージか PR に書きます（decisions.md の 38 番）。所定の語句（「サイズの上限」「性能の退行」と測定値）は、開発の記録の今のバージョンの 1 行に含めます（`check-size`・`bench-compare` が CHANGELOG と開発の記録の両方の節を探す）。0.30.9 以前の CHANGELOG は日本語のまま訳しません
- マイナーバージョンの CHANGELOG には **Migration** の小見出しを設け、利用者に必要な作業（改名・既定値の変更など）だけを英語で書きます。作業がなければ "No work is needed." と書きます。同じ内容を日本語で `docs/migration.md` にも足します（decisions.md の 38 番）

### 互換性の約束

パッチバージョンでは、次のうち「パッチバージョンでも」と書いたものだけが起こりえます。マイナーバージョンでは、次のすべてと、区分の表でマイナーに当たる変更（0.x では破壊的変更を含む。作業は CHANGELOG の Migration と移行ガイドに書く）が起こりえます。利用者はこれを前提にコードを書けます。（理由は decisions.md の 33 番）

- **出力の列挙に値が増える**: ライブラリが返す列挙の型（`Known…` の型がある開いた型。理由・祝日の種別・エラーコード・診断コードなど）は、値が増えることがあります。値を列挙して分岐するときは「その他」の分岐も書いてください（網羅を型で確かめたい場合は `Known…` の型を使えますが、値が増えたときに型エラーになることを受け入れることになります）
- **返すオブジェクトに項目が増える**: ライブラリが返すオブジェクト（`dayInfoOn` の結果や祝日など）に項目が足されることがあります
- **設定・引数に省略可能な項目が増える**: 既存の設定の意味は変わりません
- **パッチバージョンでも、例外・診断のメッセージの文言が変わる**: メッセージは API の一部ではありません。判定には `isBizdaysError()` と `code`（診断では各結果の `code`）を使ってください
- **診断の結果が増える**: 規則の診断（`bizdays-toolkit/diagnose`）は、新しい種類の問題を見つけるようになることがあります。テストで `[]` と比べている場合、新しいバージョンで警告が増えて失敗することがありますが、ライブラリの判定の結果は変わりません。前のバージョンが返した結果は新しいバージョンでも返します（CI の `result-compare` ジョブで確かめる）。ただし、誤った診断を直したときは消えることがあり、CHANGELOG の Fixed に書きます
- **パッチバージョンでも、不具合の修正と公式データの反映で結果が変わる**: パッチバージョンで結果が変わるのは、この 2 つだけです。マイナーバージョンでは、規則で計算する提供元の対応年の拡大・誤った祝日の `key` の修正・約束のない挙動の変更でも結果が変わり、CHANGELOG の Changed と Migration に書きます（上の「区分」。理由は decisions.md の 25 番・32 番）

次のことは、1.0.0 以降はメジャーバージョンでしか行いません。0.x ではマイナーバージョンで行います（区分の表の 0.x の列）。

- 公開している関数・型・設定の削除や改名、意味の変更
- 利用者が実装するインターフェース（`HolidayProvider`）への必須の項目の追加
- 既存の `code` の値の削除や意味の変更

削除する場合は、先に非推奨（`@deprecated`）にし、少なくとも 1 つのマイナーバージョンのあいだ残します。

### 安定度の表示

公開しているものには TSDoc の `@public`（安定）か `@beta`（マイナーバージョンで変わりうる）が付いています。新しい機能は `@beta` で出すことがあり、利用実績を重ねて API が安定したら `@public` にします。公開しているものの一覧と安定度は `etc/api.md` にあり、`pnpm check` が意図しない変化を検出します。

### 0.x の期間

1.0.0 までは SemVer の規定どおり、破壊的変更をマイナーバージョンで出します（`0.1.x` → `0.2.0`）。パッチバージョンでは出しません（0.x のバージョンの区分は、区分の表の 0.x の列による）。実際のアプリでの利用を通じて API が安定したら 1.0.0 にします。1.0.0 以降は、破壊的変更はメジャーのみです。

0.22.2 の次は 0.30.0 です。公開する名前を規則に合わせて改めたバージョンを区切るため番号を飛ばしました（0.23.0〜0.29.0 は欠番。decisions.md の 9 番）。SemVer は番号を飛ばすことを禁じておらず、npm でも普通のマイナーバージョンの更新です。

### 1.0.0 で行う作業

1.0.0 で行う作業の一覧はこの節だけに書き、ほかの場所はこの節を指します。理由は decisions.md の 7 番・10 番です。

1. 移行ガイドの「1.0.0 で削除する予定の API」の節にあるもの（表と、表の後の文）をすべて削除し、節を空にする（名前はここに写さない。`check-names` が表と `@deprecated` を突き合わせる）
2. 設定の旧名（`src/core/renamed.ts` の表）を `invalid-option` にし、診断コード `deprecated-option`（ガイドの診断の表の行を含む）と、1.0.0 での扱いを予告するメッセージを消す。`kinds` の `"national"` は、ID `"JP"` の提供元を含む設定では `invalid-option`、含まない設定では普通の種別の文字列にする。移行の関数と、`never-matches` に添える改名の説明は残す
3. 旧名を書いたテスト（`test/support/old-names.ts` を使うもの）を消し、`test/deprecated.test.ts` を、旧名が `invalid-option` になることを確かめるテストに置き換える
4. CI の改名の前のバージョン（0.22.2）との比較をやめる（`ci.yml` と `result-compare-wide.yml`）
5. 非推奨の返す項目のための例外を消す（ガイドの「1.0.0 までは結果に非推奨の項目も付く」の注記、「文書を実装と照合する」の例外、例の照合の除外 `deprecatedResultKeys`）
6. README（英日）の非推奨の定数の記述を消す

### dataVersion

国ごとの提供元が `dataVersion`（日本は反映済みの官報の年月、英国・フランス・シンガポールは反映済みの GOV.UK・data.gouv.fr・data.gov.sg のデータの年月。例: `"2026-02"`）と `confirmedThrough`（公式に確定している最後の年）を公開します。データを更新したら CHANGELOG の **Data** 区分にも記載します。

## 日本のデータの更新

翌年の春分・秋分の日は、毎年 2 月 1 日ごろに官報で公表され、内閣府の CSV も更新されます。同じワークフロー（`data-watch.yml`）が毎日内閣府の CSV（<https://www8.cao.go.jp/chosei/shukujitsu/syukujitsu.csv>）と照合し、差分があればラベル `cao-data` の issue を立てます（0.18.0 で追加。それまでは 2 月に手動で `pnpm verify:cao` を実行していました）。

| 差分の種類                                    | 対応                                                                                                                                                                           |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| New years published in the Cabinet Office CSV | 翌年の春分・秋分の日が公表された。下の毎年の作業の引き金                                                                                                                       |
| Library does not match the Cabinet Office CSV | 法改正による祝日の新設・移動（特別法による移動を含む）、春分・秋分の日が近似式と食い違った。`src/jp/rules.ts` を直し、**その日より前に利用者へ届くようパッチバージョンを出す** |
| Fixture differs from the Cabinet Office CSV   | フィクスチャの更新が必要。上と同じコミットで更新する                                                                                                                           |
| ERROR（The check itself failed）              | 取得・解析の失敗（CSV の形式・文字コードの変更など）。監視が機能していないので、`scripts/verify-cao.ts` を直す                                                                 |

毎年の作業（New years published が来たら）:

1. `pnpm verify:cao` で照合する（新しい年の行が増えている）
2. 差分がなければ `pnpm verify:cao --write` でテスト用フィクスチャを更新する
3. `src/jp/rules.ts` の `CONFIRMED_THROUGH`（例: 2028）と `DATA_VERSION`（例: `"2027-02"`）を更新する
4. 春分・秋分の日が近似式と食い違っていた場合は、`rules.ts` に例外を追加する
5. CHANGELOG の **Data** に記載して、パッチバージョンとして公開する

## 英国のデータの更新

1974〜2011 年（GOV.UK のデータがない年）は、The Gazette の布告と当時の政府の公表一覧から作ったフィクスチャ（`test/fixtures/uk-1974-1999-proclamations.json`・`test/fixtures/uk-2000-2011-government-lists.json`。出典は `docs/sources/uk-bank-holidays-1974-1999.md`・`docs/sources/uk-bank-holidays-2000-2011.md`）で検証していて、出典が過去の記録なので監視の対象ではありません。出典の読み違いが見つかったときだけ、フィクスチャと `src/uk/rules.ts` の表（`RENAMED`・`SPECIAL_DAYS`・`MOVED`）を直してパッチバージョンを出します（decisions.md の 28 番）。

英国の bank holidays は、布告による臨時の祝日が 10 日ほど前に発表されることがあり、日本のように時期が決まっていません。そのため、GitHub Actions（`.github/workflows/data-watch.yml`。0.17.0 で `govuk-watch.yml` から改名し、シンガポール（0.17.0）・日本（0.18.0）・フランス（0.20.0）の照合も同じワークフロー実行内で行う）が毎日 GOV.UK と照合し、差分があればラベル `govuk-data` の issue を立てます（Actions の実行も失敗になります）。issue の本文には、`pnpm verify:govuk` の結果と、GOV.UK の公式リポジトリ（alphagov/frontend）の該当ファイルの最新のコミット（変更の理由の手がかり）が入ります。

| 差分の種類                       | 対応                                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| New years published by GOV.UK    | 新しい年が載った。規則の計算と一致していれば、`CONFIRMED_THROUGH`・`DATA_VERSION` を上げる（急がない）                   |
| Library does not match GOV.UK    | 臨時の祝日の追加・移動など。**その日より前に利用者へ届くよう、すぐにパッチバージョンを出す**（利用者の熟成期間も考える） |
| Fixture differs from GOV.UK      | フィクスチャの更新が必要。上の 2 つと同じコミットで更新する                                                              |
| Welsh names differ               | ウェールズ語の名称が変わった。`src/uk/index.ts` の名称を直す                                                             |
| ERROR（The check itself failed） | 取得・解析の失敗（GOV.UK の形式の変更など）。監視が機能していないので、`scripts/verify-govuk.ts` を直す                  |

1. `pnpm verify:govuk` で手元でも差分を確かめる
2. `src/uk/rules.ts` を直す（移動は `MOVED`、臨時の祝日は `SPECIAL_DAYS`、振替の割り当てだけが異なる場合は `RENAMED`）。`CONFIRMED_THROUGH`・`DATA_VERSION`（反映した GOV.UK のデータの年月）も更新する
3. `pnpm verify:govuk` が合格したら、`pnpm verify:govuk --write` でフィクスチャを更新する（GOV.UK から消えた古い年は残し、内容が変わった年だけ出典を書き換える）
4. 1 つのコミットにまとめ、CHANGELOG の **Data** に記載して、パッチバージョンとして公開する
5. 公開したら issue を閉じる

差分があったときの経路（issue の作成・更新・コメント）を確かめるには、Actions の「Run workflow」で **simulate** に印を付けて実行します。GOV.UK・data.gov.sg・内閣府・data.gouv.fr のデータにそれぞれ架空の祝日を 1 件足して照合するので、ラベル `govuk-data-simulation`・`datagovsg-data-simulation`・`cao-data-simulation`・`datagouv-data-simulation`、題名に `[Simulation]` が付いた issue が 4 つ作られ、実行は失敗になります（想定どおり）。もう一度実行すると、内容が同じなので issue は更新されません。確かめたら issue を閉じてください。監視の仕組み（`scripts/verify-govuk.ts`・`scripts/verify-datagovsg.ts`・`scripts/verify-cao.ts`・`scripts/verify-datagouv.ts` やワークフロー）を変えたときにも行います。

## フランスのデータの更新

### 監視の起動とハートビート

GitHub の schedule は高負荷時に遅延したり、実行されなかったりすることがあり、このリポジトリでは追加後、一度も実行されませんでした。そこで、監視は次の 3 つで支えます（decisions.md の 29 番）。

| 仕組み             | 役割                                                                                                   | 設定の場所                                                       |
| ------------------ | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| cron-job.org       | 主な起動手段。毎日 06:00（日本時間）に `workflow_dispatch` を API で呼ぶ                               | cron-job.org のジョブ（下記）                                    |
| GitHub の schedule | 予備の起動手段。毎日 18:17（日本時間）                                                                 | `data-watch.yml` の `cron`                                       |
| healthchecks.io    | 監視が動いたことの確認。最終ステップでハートビート（ping）を送り、ハートビートが途絶えたらメールが届く | healthchecks.io のチェックと、Secrets の `HEALTHCHECKS_PING_URL` |

ハートビートは、すべての照合が完了したとき（一致・差分あり）は成功を、いずれかの照合処理自体が失敗したとき（取得の失敗など）やそれ以前の段階で処理が停止したときは `/fail` を送信します。差分と照合処理自体の失敗は、データごとのラベルを付けた issue で通知します（取得や解析の失敗も issue にする。decisions.md の 29 番）。

GitHub の失敗通知（文書「Notifications for workflow runs」）は補助的なものであり、受け取る人の通知の設定によります。`workflow_dispatch` の実行は起動した人（cron-job.org から起動した実行はトークンの持ち主）に、`schedule` の実行はワークフローを作った人（cron を別の人が直したらその人。止められたワークフローを再び有効にした場合は、その操作を行ったユーザー）に届きます。data-watch は最後にジョブのトークン（github-actions のボット）で自分を有効にし直すので、予備の `schedule` の実行で、止められていたワークフローを有効にし直したときは、その後の `schedule` の通知がボット宛てになるおそれがあります。すでに有効なワークフローに有効化を呼んだときの扱いは文書になく、確かめていません。

**cron-job.org のジョブ**

- URL: `https://api.github.com/repos/inohan77/bizdays-toolkit/actions/workflows/data-watch.yml/dispatches`（POST。0.17.0 で `govuk-watch.yml` から改名したので、cron-job.org の URL も直す）
- ヘッダー: `Accept: application/vnd.github+json`、`Authorization: Bearer <トークン>`、`Content-Type: application/json`、`X-GitHub-Api-Version: 2026-03-10`（REST API のバージョン。指定しないと 2022-11-28 のバージョンになり、そのバージョンは 2028 年 3 月 10 日に提供が終わる。出典: https://docs.github.com/en/rest/about-the-rest-api/api-versions の Supported API versions）
- 本文: `{"ref":"main"}`
- 時刻: 毎日 06:00（タイムゾーン Asia/Tokyo）。失敗したときのメール通知を有効にする
- トークン: Fine-grained のトークンを、このリポジトリだけ・**Actions の Read and write だけ**で作る（Contents は不要）。このトークンで起動できるのは `workflow_dispatch` のある data-watch と、手動の広い比較のワークフロー（`result-compare-wide.yml`）だけで、コードの変更や npm への公開はできない。cron-job.org から起動するジョブは data-watch だけ。期限を設け（1 年など）、切れる前に作り直して cron-job.org のヘッダーを差し替える（切れると呼び出しが 401 で失敗し、cron-job.org の失敗の通知と、healthchecks.io のハートビートの途絶の両方で分かる）

**healthchecks.io のチェック**

- 種類は Simple、Period は 1 day、Grace は 6 hours（最後のハートビートから 30 時間以内に次のハートビートが届かなければメールが届く）
- チェックの Ping URL を、リポジトリの Secrets に `HEALTHCHECKS_PING_URL` として登録する（URL を知っていれば誰でもハートビートを送れるため、公開しない）

監視の仕組みを変えたときや、トークンを作り直したときは、cron-job.org の Test Run で data-watch が起動し、healthchecks.io にハートビートが届くことを確かめてください。2026-03-10 のバージョンでは、成功すると `200` と起動した実行の ID（`workflow_run_id`）が返ります（2022-11-28 のバージョンでは本文のない `204`）。応答のヘッダーに `Deprecation`・`Sunset` があれば、指定している API バージョンの提供終了が予定されているため、トークンを作り直すときなどに、GitHub の API のバージョンのページで新しいバージョンを確かめて `X-GitHub-Api-Version` を更新します。

監視のワークフローは、リポジトリに 60 日間動きがないと GitHub が定期実行を止めるのを防ぐため、実行のたびにワークフロー自身を有効化し直します（予備の schedule のため。通知の向き先への影響は上のとおり）。

**監視のワークフローを改修したときの確かめ方**

知らせの経路（ハートビートの成功・`/fail`、issue を立てる・更新する・何もしない、ジョブの終わり方）は、実際に差分や失敗が発生するまで実行されないため、変更による不具合に気付けません。ワークフローの `run:` のシェルを抽出し、偽の `gh`・`curl` コマンドを用意して、経路ごとに手元で動かします（スクリプトにはしない。改修したときにだけ使う手順）。

1. 偽の `gh`・`curl` を作る。呼び出し時の引数を `$CALLS` のファイルに書き、決めた応答を返す
   Windows では、`/tmp` を `C:\wt` のような短いパスに読み替える。ワークフローの改行コードが CRLF のままでも、Git Bash で動く

   ```sh
   mkdir -p /tmp/dw-check/bin && cd /tmp/dw-check
   printf '%s\n' '#!/bin/sh' 'echo "gh $*" >> "$CALLS"' 'case "$1 $2" in' \
     '  "issue list") printf "%s\n" "${GH_OPEN_ISSUE:-}" ;;' '  "issue view") printf "%s\n" "${GH_ISSUE_BODY:-}" ;;' 'esac' > bin/gh
   printf '%s\n' '#!/bin/sh' 'for a; do last="$a"; done' 'echo "curl ${last}" >> "$CALLS"' > bin/curl
   chmod +x bin/gh bin/curl
   export PATH="/tmp/dw-check/bin:$PATH" CALLS=/tmp/dw-check/calls.txt GITHUB_REPOSITORY=inohan77/bizdays-toolkit
   ```

2. ステップの名前を指定して、`run: |` のシェルを抽出する（行頭のインデント 10 文字分を外す）

   ```sh
   step() { awk -v name="$1" '
     index($0, "- name: " name) && substr($0, index($0, "- name: ") + 8) == name {found=1; next}
     found && /^        run: \|/ {inrun=1; next}
     inrun && (/^          / || /^$/) {sub(/^          /, ""); print; next}
     inrun {exit}
     found && /^      - / {exit}' <リポジトリ>/.github/workflows/data-watch.yml; }
   step "Open or update the issue" > issue.sh   # GOV.UK。ほかは "Open or update the data.gov.sg issue" など
   step "Send the heartbeat" > heartbeat.sh
   step "Fail when GOV.UK, data.gov.sg, the Cabinet Office CSV or data.gouv.fr differs or could not be checked" > fail.sh
   ```

3. 経路ごとに、ステップが読む環境変数を設定して実行し、`$CALLS` と出力を見る（ステップの `if:` は、ワークフローを読んで手動で適用する。issue のステップは照合の `outcome` が `failure`（終了コード 0 以外）のとき、失敗のステップはどれかの照合が `failure` のときに動く）
   - issue のステップ: `LABEL`・`TITLE`・`REPORT`（照合の報告のファイル）と、偽の `gh` の応答（`GH_OPEN_ISSUE` に開いている issue の番号、`GH_ISSUE_BODY` にその本文）
   - ハートビートのステップ: `PING_URL` と、各照合の終了コード（`CODE`・`SG_CODE`・`JP_CODE`・`FR_CODE`）
   - 失敗のステップ: 各照合の終了コード（`CODE`・`SG_CODE`・`JP_CODE`・`FR_CODE`）と各ラベル（`LABEL`・`SG_LABEL`・`JP_LABEL`・`FR_LABEL`）

4. 確かめる経路と、期待（今の data-watch.yml）

   | 経路                                                        | issue                                                 | ハートビート       | ジョブ                                                                                                                            |
   | ----------------------------------------------------------- | ----------------------------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
   | すべて一致（0）                                             | 動かない                                              | 成功               | 成功                                                                                                                              |
   | 差分あり（1）・開いている issue なし                        | ラベルを作り、issue を立てる                          | 成功               | 失敗                                                                                                                              |
   | 差分あり・開いている issue があり、1 行目のほかは本文が同じ | ラベルを作るだけ（更新もコメントもしない）            | 成功               | 失敗                                                                                                                              |
   | 差分あり・開いている issue があり、本文が違う               | 本文を更新し、コメントする                            | 成功               | 失敗                                                                                                                              |
   | 取得・解析の失敗（2）                                       | 差分ありと同じ（報告の本文に失敗の内容）              | `/fail`            | 失敗（メッセージは「… could not be checked (see the … issue)」。差分（1）は「… differ from the bundled data (see the … issue)」） |
   | 模擬（`simulate`）                                          | データごとの `-simulation` のラベルで、差分ありと同じ | 成功               | 失敗                                                                                                                              |
   | ハートビートの URL の未設定                                 | —                                                     | 送らず、通知を出す | —                                                                                                                                 |

## README のサイズの値

README の minify + gzip のサイズは、手動で測定した値です（測ったバージョンを README に添えています）。マイナーバージョンを出すときと、`src` を大きく変えたときに測り直します。`pnpm check` は、README（英日）に書いた「測ったバージョン」が今のマイナー系列であることを確かめます（マイナーバージョンを出すときの測り直し忘れを止める。「品質の仕組みの理由」の「文書を実装と照合する」）。

測り方は `scripts/measure-bundle.ts` に固定しています。ルートのすべてと、国の提供元（サブパスごとに、その提供元の export だけ）を読み込む入口を esbuild で bundle・minify し、gzip（レベル 9）で測ります。1 KB は 1,000 バイトで、小数第 1 位に丸めます。esbuild はリポジトリの依存にしないため（「品質の仕組みの理由」の「依存を足さない」）、熟成ゲートを過ぎたバージョンを一時ディレクトリにインストールして使います（例: `npm install --prefix <一時ディレクトリ> esbuild@0.28.2` のあと、`pnpm build` して `node scripts/measure-bundle.ts --esbuild <一時ディレクトリ>/node_modules/esbuild`）。出力表の「README の値」を README（英日）に転記し、「測ったバージョン」も改めます。

## 品質の確認

納品（ZIP）の手順は「すべての編集 → `pnpm fmt` → `pnpm check` → check の出力から CHANGELOG の測定値を転記 → ZIP」の順に固定し、`pnpm check` の実行後に何かを変更した場合は、check からやり直す。`pnpm check` は、CHANGELOG の今のバージョンの「測定 N」が実測と一致すること、`docs/sources/*.md` が README（英日）からリンクされていること、フィクスチャの `record` が実在することも確かめる（「品質の仕組みの理由」の「規則を 1 か所に書く」）。ドキュメントの数値・一覧（対応年など）も `dist` と照合し（下の表の「ドキュメントの数値」。「品質の仕組みの理由」の「文書を実装と照合する」）、コメントと文書に書いたファイルのパスと決定の番号が実在すること、決定の文書の目次が見出しと一致することも確かめる（「品質の仕組みの理由」の「規則を 1 か所に書く」）。コメントには、その場所でしか分からないこと（その行の理由・使い方）と、詳しい説明の場所（決定の番号）を書き、設計の理由の説明・バージョンの経緯・利用元の一覧・国の数や件数のような機能を足すと変わる事実は書かない。国や機能を足すバージョンでは、既存のコメント・文書の国名や件数の記述を `git grep` で探して読み直す（「品質の仕組みの理由」の「規則を 1 か所に書く」）。手元の確認は、前のバージョンのタグを読める状態（`git fetch --tags`）で、CI の `check` の行列に含まれるいずれかの Node.js のバージョンで `pnpm check` を通す（タグがないと `check-size` の上限の比較が飛ばされる）。名前を置換したバージョンでは、置換した後の名前が英文・和文の中に現れる行を `git grep` で洗い、コード以外の文脈（英語の普通名詞など）まで置換していないかを読む。旧名の値（`"national"` など）と、和文の中の旧名の語（`recurring` など）は `check-names` が見ないので、同じく `git grep` で読む（「品質の仕組みの理由」の「規則を 1 か所に書く」）。名前を置換したバージョンでは、`docs/decisions.md` の本文も新しい名前に書き換える（決定の文書は今の決定を書くもので、追記を重ねない。`check-names` の対象外なので人が読む。「品質の仕組みの理由」の「規則を 1 か所に書く」）。返す値（祝日の種別など）を改めたバージョンでは、その値を設定に書いた利用者の結果が変わらないかを考え、変わるなら移行ガイドに記載する（decisions.md の 10 番）。

### 品質の仕組みを足すとき

理由は「品質の仕組みの理由」の「前のバージョンと比べる」です。

1. 見つけた漏れには、事例ではなく種類のテストを足し、どの仕組みが見逃したかを開発の記録（`docs/development-log.md`）に書く
2. 最適化した判定には、素朴な定義のオラクルを添える（診断のオラクルのように、定義どおりに実際に確かめて突き合わせる）
3. 通常のテストでは再現できない例外経路は、作れる部品を作って確かめる（失敗の注入の提供元のように）
4. 新しい品質の仕組みは、目的（何を防ぐか）と根拠、規模・頻度・範囲の決め方、退けた単純な案を PR か開発の記録（`docs/development-log.md`）の 1 行に書いてから入れ、続く理由は「品質の仕組みの理由」に足す。仕組み（使い方）をやめるときは、作った部品ごとにほかの使い道を見直し、役に立つものは目的を書き直して残し、その仕組みのためだけのものを外す

5. **時間の上限**: `pnpm check` は手元の 1 コアで 3 分以内、CI の全件は 1 ジョブ 10 分以内に収める。上限を超えたときだけ、`pnpm check` の仕組みを次の順で CI 専用に下げ、上限に収まったら止める: (1) 最後に見つけた不具合が「記録なし」の仕組みのうち時間の長いもの、(2) 最後に見つけたバージョンが古いもの。品質の確認の表の「下げない」の列に印のある仕組みは下げない。上限の内では、仕組みを見直さない
6. CI の全件を動かすジョブは、ジョブの時間を、同じジョブ（分けたジョブは同じ分）の直近 3 回の main の成功した実行の中央値と比べ、1.5 倍を超えたら Job Summary に注意を出す（失敗にはしない）。比べる値が取れないとき（実行が 3 回に満たない、取得に失敗した）は、比べられなかったことを Job Summary に出す。各ジョブの中央値は時間の上限の 6 割以下に保ち、超えたら分ける数を見直す（6 割以下なら、1.5 倍の注意が時間の上限より先に出る。分ける数やテストの重さを変えた直後は、変えた後の実行が 3 回そろってから判断する）。注意が出たら、注意の出た 1 つのジョブ（分けたジョブはその 1 つの分）だけを、手元で前のバージョンと交互に 3 回ずつ測り（A B A B A B）、中央値の差で原因の変更を確かめる。時間の上限を超えるときは 5 に進む
7. 検討項目: oracle の分割を、設定の数ではなく費用（前回の ms）で均す（0.31.0 の ZIP-D_1 で、設定の数で分けた 0/4 が 439 秒、2/4 が 239 秒と偏った）

## 品質の仕組みの理由

品質の仕組み（検査・テスト・比較・実行環境・文書の照合）の理由と退けた案です（decisions.md の 40 番）。0.31.0 で決定の文書の 34〜37・39 番から移しました。

### 依存を足さない

（0.31.0 より前は決定の文書の 34 番「品質の仕組みに新しい依存を足さない。lint は oxlint」）

開発用の npm の依存を増やしません。サイズは minify せずに gzip で測り、API のスナップショットは TypeScript のコンパイラー API で作り、性質のテストの乱数は自前で実装します。

- 依存が増えるほど、供給チェーンの管理（熟成ゲート）の対象が増えるためです
- CI でだけ使う道具（actionlint・workerd・Bun・Deno・利用者の型チェック用の TypeScript の各バージョン）は、npm の依存にせず、バージョンと SHA-256 を固定した公式のリリースを取得します。README のサイズの値を測る esbuild は CI でも使わず、手元で一時的に入れて測ります（「品質の仕組みの理由」の「文書を実装と照合する」）
- lint は oxlint です。インストール時のスクリプトがなく依存が各 OS のバイナリだけで、管理の手間がほとんど増えません。ESLint と typescript-eslint は依存が多く、強みの型情報を使う規則（Promise の扱いなど）も、非同期の処理がないこのライブラリでは出番が少ないので取りません。規則は「正しさ」の分類を基本に意味のある規則を個別に足し、好みの分類（style・pedantic）は有効にしません。出力の対象（ES2022）より新しい機能を求める規則は採りません
- ワークフローの誤りは `pnpm check` でもテストでも見つからず GitHub に読み込まれて初めて分かるので、CI の `workflows` ジョブで actionlint にかけます

### 確かめる実行環境

（0.31.0 より前は決定の文書の 35 番「確かめる実行環境の理由」）

確かめる環境とバージョンの一覧は「品質の確認」と「開発環境のバージョン」に書きます。

- `engines` は「動くはずの範囲」で、動作確認済みの範囲は README と CI で示します。確かめたバージョンに `engines` を狭めると、`engine-strict` の利用者が入れられなくなるので狭めません。下限は ESM を `require()` で読めるバージョンです
- 下限のバージョンや新しい系列では、ビルド済みの `dist` だけを確かめます（依存がゼロなので足りる）
- ブラウザー・Workers・Bun・Deno でも確かめるのは、README に「動く」と記載する以上、実際に動作を確認する必要があるためです。npm の依存が要る環境（Vercel の Edge Runtime）は確かめず、README に書きます
- Node.js の警告を失敗にするのは、警告は合格のまま通るので見落とされるためです
- 開発用のツールのバージョンの違いは、CI ではエラーにし、手元では注意の表示にとどめます。熟成ゲートの都合で手元を先に変えることがあるためです
- スクリプトからレジストリに接続する npm の操作をさせないのは、スクリプトから起動する npm が、PowerShell の関数として定義された Safe Chain を通らないためです
- Windows 環境の CI は設けません。`dist` はどの OS でも同じように動作し、開発用のスクリプトの問題は手元（Windows）の `pnpm check` で止まるためです
- タイムゾーンを変えたテストを 4 ゾーンから 2 ゾーン（UTC より遅い America/Los_Angeles と進んだ Pacific/Chatham）にしたのは、依存の経路が静的に名指しできるためです。`src` はローカル時刻の `Date` の API・`getTimezoneOffset`・`toLocale…String`・`new Date(年, 月, …)`・`timeZone` を渡さない `Intl.DateTimeFormat` を使わず、`check-package` がこれを禁止します。残る動的な確認は、漏れた依存が日付のずれとして現れる向きが UTC との差の向きで変わるので、両側 1 つずつで足ります（UTC は既定の実行と同じで、Asia/Tokyo は Chatham と同じ側）。再実行するのは、瞬間・時刻を渡すテストだけです。`src` で `Date`・`Intl` に触れるのは日数の変換・瞬間の変換・`today` に限られ、暦日の文字列だけを渡すテストはゾーンを変えても同じ経路を通るためです。対象から漏れないよう、瞬間・時刻を書いたテストのファイルは、再実行の一覧か理由付きの除外のどちらかに載っていなければ失敗にします

### 規則を 1 か所に書く

（0.31.0 より前は決定の文書の 36 番「規則を 1 か所に書くことと、納品の検査・人の確認の理由」）

手順と検査の一覧は「品質の確認」に書きます。

- **同じ規則を 2 か所に書きません。** バージョンの区分・互換性の約束・手順・検査の一覧・コメントの書き方は RELEASING.md、その理由と退けた案は決定の文書とこの節、利用者への説明は README とガイドに書き、ほかの文書とコメントからは節名または番号で参照します。2 か所に書くと、片方だけが直って食い違うためです
- 納品の手順を固定し、check の実行後に変更した場合は、再度実行するのは、測り直し忘れ・リンクの書き忘れのような、記憶に頼った手順の漏れが続いたためです。機械で確かめられるものは `pnpm check` に入れます
- 最適化した判定（診断）は、素朴な定義（項目を実際に取り除いて全日で比べる）と総当たりで突き合わせます（規則は「品質の確認」）。乱数の性質のテストは、生成器が作れる設定しか試せず、生成器に規則の形を足し忘れた見逃しが続いたためです。同じ理由で、乱数のテストの生成器は目録 1 つにまとめ、公開の型と突き合わせます
- 黙って外れる検査・黙って合格になる確認を作りません（規則は「品質の確認」）。外れた検査は、確かめたように見えて何も確かめないので、合格より悪いためです
- コメントには、その場所でしか分からないことと、詳しい説明の場所だけを書きます。設計の理由をコメントにも書くと、片方だけが古くなるためです
- バージョンの区分・互換性の約束・品質の仕組みは、「用語」の節の言葉だけで書き、言い換えません。範囲は区分の表の行で決め、ほかの節と decisions.md は行を指して理由だけを書きます（範囲を言い直すと、片方だけが直って食い違う。0.31.2 の先送りの規則と 32 番の矛盾がこの形だった）
- 規則には、当てはまるものの名前を並べず、性質で書きます。性質で書けず一覧が要るときは、一覧を 1 か所（表かコードの定数）に置き、実装と突き合わせる検査を同じ変更で足します（0.31.1 のテストの関数名の一覧が、そろっていない `code` を固めていた）
- 規則の文では「ことがある」「など」「今は」を使わず、断定と列挙で書きます。バージョンによって変わる値（時間・件数・分ける数）は規則の文に入れず、開発の記録のそのバージョンの行に、測ったバージョンと条件と一緒に書きます
- コメントは指す先（番号・節の名前）だけを書き、指す先の内容を写しません
- 公開する `.js` からはコメントを除き、`.d.ts` は TSDoc を残します。保守する人向けのコメントを利用者の `node_modules` に届けず、コメントの量がサイズに影響しないようにするためです
- 機械で確かめられない誤り（説明が実装と合っているか）は、納品物を取り込む際の Claude Code による重点確認で見つけ、直さずに報告させます。取り込む側が直すと、何を直したかが納品物と食い違うためです

### 前のバージョンと比べる

（0.31.0 より前は決定の文書の 37 番「前のバージョンと比べて、意図しない変化を見つける」）

比べ方と失敗の条件は「品質の確認」の表に書きます。

- 照合のフィクスチャが守るのは公式データのある年だけで、テストは一部の設定しか試さないので、公開済みの前のバージョンの結果そのものを安全網にします（祝日データ・設定の結果・性能・サイズ）
- 比較は意図しない変化を見つけるためのもので、動作を固定するものではありません。意図した変化は、決まった場所に書けば通ります（祝日データは CHANGELOG の Data、設定の結果は `etc/result-changes.json`、性能とサイズは開発の記録（`docs/development-log.md`））
- 設定の結果の差分は、CHANGELOG の記載を根拠に差分を許容する方式は採りません。差分がどの変更によるものかを CHANGELOG からは決められず、関係のない差分まで通るためです。許す範囲は設定の特徴とバージョンで絞ります。限界: 許した特徴を持つ設定では、同じ設定のほかの差分も許します。また、許す項目は前のバージョンがその変更より前のときに効くので、`latest` との比較ではそのバージョンの公開後に効かなくなりますが、改名の前の 0.22.2 との比較では効き続けます（診断の差分は消えた結果のコードで絞って、影響を小さくします）。乱数では当たりにくい退行は、最小の設定を固定の設定として残します
- 1.0.0 より前のバージョンでは、改名の前の 0.22.2 とも旧名の設定で比べます。改名は結果を変えないという約束（decisions.md の 10 番）を確かめるためです
- 性能は絶対値ではなく、同じ実行の中の比率で比べます（ランナーの性能は実行ごとに数十%ぶれる）。判定基準は粗めに設定し、アルゴリズムの悪化だけを捉えます。正しさのために遅くなることを受け入れる道を残すのは、性能の判定基準が修正を止めないようにするためです
- いずれも npm への接続が必要か、結果が実行環境に依存するため、`pnpm check` には含めません
- 設定の結果の差分は、定期実行にしません。定期実行の頻度を正当化する理由がないためです（リリースの直後は `latest` と main が同じで何も見つけず、リリースまでの間は取り込みのたびに CI の比較が動く）。また、0.30.1〜0.30.7 の不具合を見つけたのは、狙いを絞った仕組み（オラクル、失敗の注入、API どうしの整合、生成範囲の検査、固定の設定）で、乱数による試行数を増やして見つけた不具合はありません。結果が変わりうるのは前のバージョンから変わったコードを通る設定だけで、決まった種の見本がそこに届くかは、見本の数では決まりません（0.30.7 で `diagnose.ts` を直したとき、CI の決まった種（倍率 1）の 0.30.6 との比較では「増えた診断の結果」は 0 件で、倍率 10 の広い比較では 6 件出た）
- 退けた案: 週 1 回、種を変えて規模を大きくする定期実行（0.30.7 の作業の途中で作った形）。上記の理由から目的を達成できず、起動・知らせ・飛ばしの仕組みの費用が大きい。作った設計の要点は、別の定期実行を作るときの参考に残します: 止まったことはハートビート、差分は issue と、知らせを分けた。主（外部の cron からの `workflow_dispatch`）と予備（`schedule`）の 2 つの起動で、同じ週の 2 回目は、既定の入力で成功した実行があれば飛ばした（decisions.md の 29 番の退けた案と同じ判定）。飛ばしたときと、種や倍率を変えた実行・模擬は、ハートビートを送らなかった（ハートビートを「その週の既定の比較が動いた」の知らせにそろえるため）
- 退けた案: リリースの前に 1 回、規模を大きくして比べる。見本の数は、変わったコードを通るかと関係せず、規模の数を目的から導けません
- 退けた案: 前のバージョンから変更されたコードを比較テストが実行したかを測る（カバレッジ）。目的には合いますが、新しい仕組み（V8 のカバレッジと、dist の差分の行の対応）が要ります。今は、結果を変える修正に固定の設定を足す決まりと、公開物が変わったら CHANGELOG の区分を求める検査で足りています。この決まりが守られない事例が出たら検討します
- 種と倍率を指定した広い比較は、手動の実行だけのワークフロー（`result-compare-wide.yml`）として残します。退行が疑われるときの調べや、判定結果に影響する変更を多く含むバージョンの公開の前に、GitHub の上の CI と同じ環境で動かせるようにするためです（手元でも `--seed`・`--scale` で同じことができる）。0.30.7 では、意図した変化（Fixed の 1 件目の `never-matches` が増える向きの直し）が乱数の設定に届いたことを確かめるのに使えました（倍率 10 で 6 件。どれも直しの形であることを 1 件ずつ確かめた）。比較が終わらなかったこと（終了コード 2）と差分（1）を区別するので、結果を読み違えません
- 品質の仕組みを足す・やめるときの決まり（「品質の仕組みを足すとき」）: 新しい仕組みは、目的（どの約束を、どんな失敗から守るか）と根拠（その失敗が実際に起きた、または起きうる事例）、規模・頻度・範囲の決め方（目的から導けない数は置かない。測って決めるなら、何を測ってどう決めるか）、退けた単純な案（既にある仕組みや決まりで済まないか）を、PR か開発の記録（`docs/development-log.md`）の 1 行に書いてから入れます（0.31.0 で、決定の文書に書いてから入れる決まりを緩めた。decisions.md の 40 番）。仕組み（使い方）をやめるときは、作った部品ごとにほかの使い道を見直し、役に立つものは目的を書き直して残し、その仕組みのためだけのものを外します。0.30.7 の作業で、定期実行の比較を目的から導かずに作り、仕組みを正しく動かすための改訂を重ねたためです（定期実行をやめ、広い比較・終了コードの区別・通知の届き先の事実・監視の改修の確かめ方の手順を残した）
- 見つけた漏れには、事例ではなく種類のテストを足し、どの穴から出たかを開発の記録に書きます。最適化には素朴な定義のオラクルを添え、通常のテストでは再現できない例外経路には、作れる部品を作ります（「品質の仕組みを足すとき」）。事例のテストは、同じ種類の次の漏れを見つけないためです

### 文書を実装と照合する

（0.31.0 より前は決定の文書の 39 番「文書を実装と照合する」）

照合するものの一覧は「品質の確認」に書きます。

- コード例は利用者が最もよく読む部分で、日英 2 つあるので、仕様の変更で片方だけ古くなりやすいところです。そのためすべて実行して結果を比べます。例は実行結果をすべて示す形で書きます（絞り込んで一部だけを示すと、設定の誤りを見落とす）。例外として、非推奨の返す項目（`scripts/check-readme-examples.ts` の `deprecatedResultKeys`。「1.0.0 で行う作業」で消す）は例に書かず、照合でも除きます。ガイドはこのことを利用者に書きます
- 文章の中の数値は、英語版と日本語版に同じ誤りがあれば、コード例の実行でも英日の対の検査でも通ります。そのため `dist` とソースの型を正にして照合します
- README のサイズの値は esbuild が必要なため手動で測定し、測り方をスクリプトに固定します（文章だけで決めると再現しない）

## 開発環境のバージョン

Node.js・npm・pnpm は、手元の開発環境と CI で同じバージョンを使います。CI のバージョンは次の場所で管理しています。

- `.github/actions/setup-toolchain/action.yml`: npm と pnpm のバージョン
- `.github/workflows/ci.yml`・`release.yml`・`data-watch.yml`・`result-compare-wide.yml`: Node.js のバージョンとランナー（`ubuntu-24.04`）
- `.github/workflows/ci.yml` の `compat` ジョブ: 公開物を確かめる Node.js のバージョン（engines の下限と、LTS の系列・LTS への移行を控えた系列のうち `check` で使わないもの。「品質の仕組みの理由」の「確かめる実行環境」）
- `.github/workflows/ci.yml` の `workerd` ジョブ: workerd のバージョンと SHA-256（公式のリリースの `workerd-linux-64.gz` を取得して計算する。熟成ゲートを過ぎたバージョンを指定する）。`safari` ジョブの macOS のランナーのバージョン（`macos-15`）
- `.github/workflows/ci.yml` の `bun`・`deno` ジョブ: Bun のバージョンと SHA-256（公式のリリースの `SHASUMS256.txt` の `bun-linux-x64.zip` の行）、Deno のバージョンと SHA-256（公式のリリースの `deno-x86_64-unknown-linux-gnu.zip.sha256sum`）。どちらも熟成ゲートを過ぎたバージョンを指定する
- `.github/workflows/ci.yml` の `workflows` ジョブ: actionlint のバージョンと SHA-256（公式のリリースの `actionlint_<バージョン>_checksums.txt` の `linux_amd64` の行）

`pnpm check` は最初に `scripts/check-toolchain.ts` で、ワークフローどうしの Node.js のバージョンがそろっていること、compat の行列に engines の下限が入っていること、実行している Node.js・npm・pnpm が固定バージョンと同じことを確かめます（固定バージョンとの違いは、CI ではエラー、手元では注意を表示）。

スクリプトからレジストリに接続する npm の操作（`install` など）はしません（「品質の仕組みの理由」の「確かめる実行環境」）。

npm 12 の動作要件は Node.js `^22.22.2 || ^24.15.0 || >=26.0.0` です。バージョンを上げるときは、公開後 48 時間以上経過したバージョンを指定し、手元の環境もそろえてください。開発用の依存（devDependencies）はバージョンの完全一致で指定し、更新時は `pnpm install` で `pnpm-lock.yaml` も更新してコミットします。

## 公開の手順

公開は staged publishing で行います。GitHub Actions（`.github/workflows/release.yml`）はバージョンを npm に**ステージ**するだけで、メンテナーが 2FA 付きで**承認**するまで利用者には届きません。GitHub のアカウントやワークフローが乗っ取られても、承認なしに公開されることはありません。手元の端末から `npm publish` はしません（provenance を付けるため）。

1. `package.json` の `version` を更新する
2. `CHANGELOG.md` の `[Unreleased]` を新しいバージョンの節に移し、末尾のリンク定義（`[Unreleased]` の比較元と新しいバージョンの行）を更新する（`pnpm check` は、現在のバージョンの節やリンク定義が合わないと失敗します）。見出しの日付は、タグをプッシュする日（日本時間）にする。リリースのワークフローが、タグを付けたコミットの日から実行した日までの期間内にあるかを確かめ、範囲の外ならステージする前に止まる
3. `pnpm check` が通ることを確かめてコミットし、main をプッシュして CI の合格を確認する
4. タグを付ける前に、文章の主張と CI の報告を読む（人の確認）
   - `node scripts/check-claims.ts --decisions --since v<前のバージョン>` を動かし、印（★）の付いた参照（前のバージョンから足した・変えた参照と、CHANGELOG の今のバージョンの節の参照）が、参照先の見出しと主張に合っているかを確認する。合わない参照があれば直してから進む（参照の実在は `pnpm check` が確かめている）
   - CI の `result-compare` ジョブの Job Summary の「診断の結果が増えた設定」を確認し、CHANGELOG に書くべき変化が書かれているかを確かめる
   - 同じジョブの「公開物の変化」の一覧が、CHANGELOG の利用者向けの区分と合っているかを確かめる
5. `v<version>` のタグを付けてプッシュする（例: `git tag v0.1.2 && git push origin v0.1.2`）
6. ワークフローが、`package.json` のバージョンとタグが一致すること、および同じバージョンが npm にまだ存在しないことを確かめ、`pnpm check` のあと npm にステージし、CHANGELOG の節を本文にした GitHub Release を**下書き**で作ります。ワークフローの実行結果の Summary に、承認の手順が表示されます
7. npm のパッケージページの **Staged Packages** タブで、ステージされたバージョンの中身（ファイル一覧・provenance）を確認し、**Approve** する（2FA を求められます）。CLI では `npm stage list bizdays-toolkit` で stage ID を調べ、`npm stage approve <stage-id>` でも承認できます
8. `npm view bizdays-toolkit dist-tags` で新しいバージョンを指していることを確かめてから、GitHub Release の下書きを公開する（`gh release edit v<version> --draft=false`）

ステージした内容に問題があった場合は、承認せずに Staged Packages タブ（または `npm stage reject <stage-id>`）で却下し、修正した新しいバージョンで出し直します。ステージしたバージョンの番号は公開済みのバージョンと同じ扱いになり、同じ番号でステージし直すには先に却下が必要です。

### npm 側の設定

- **Trusted Publishing**: npm のパッケージ設定でこのリポジトリとワークフロー（`release.yml`）を登録しています。npm のアクセストークンは GitHub に保存しません。許可する操作は `npm stage publish` だけにし、「Allow npm publish」と「Allow npm dist-tag」は無効にします
- **Publishing access**: 「Require two-factor authentication and disallow tokens」にします
- staged publishing には npm CLI 11.15.0 以上が必要です。CI では `.github/actions/setup-toolchain` で固定した npm を使います

### 利用者に届く時刻

ステージしたバージョンは、承認するまでインストールできません。npm 上の公開時刻（`npm view bizdays-toolkit time`）は、ステージした時刻ではなく承認した時刻になります（0.1.2 で確認: ステージ 2026-10-12T08:02:23Z、承認による公開時刻 08:05:51Z）。熟成期間（公開から一定時間待ってから取り込む運用）を設けている利用者にとっては、承認した時刻から数え始めることになります。
