## 型と入出力

### 1. 日付と月は単なる文字列型

`DateString`（`"YYYY-MM-DD"`）と `MonthString`（`"YYYY-MM"`）は `string` の別名で、ブランド型にしません。

- ブランド型にすると型の安全性は上がりますが、利用者が日付を渡すたびに型変換や検証関数を挟む必要が出ます
- 入力はすべて実行時に検証し、誤りがあれば `code` 付きの例外（`invalid-date` など）を投げるため、使いやすさを優先します
- 利用者が渡した暦日の値の誤りは、入力の形（文字列、Temporal の形の年月日）によらず `invalid-date` です（時・分の誤りは `invalid-time`）。年が 1000〜9999 の外であることも、値の誤りに含めます。`out-of-range` は、提供元の対応年の外と、瞬間（`Date`・`Instant`）を暦日に変換した結果や日付の計算が 1000〜9999 年の外に出たときだけです。同じ誤りの `code` が入力の形によって変わると、`code` で受けるコードが形ごとに漏れるためです（8 番と同じ理由）

### 2. 出力の列挙は「開いた型」

ライブラリが返す列挙（理由・祝日の種別・エラーコード・診断コードなど）は、既知の値の型（`Known…`）と `string & {}` の組です。

- 新しい値をマイナーバージョンで追加しても、利用者のコードがコンパイルエラーにならないようにするためです（値を列挙して分岐するコードでは、「その他」の分岐で受けます）
- すべての値を網羅していることを型で確かめたい利用者は、`Known…` を使えます。値が増えたときに型エラーで気付くかどうかを、利用者自身が選べます
- ライブラリの内部では `Known…` で分岐し、対応漏れを型で検出します
- 例外として、診断の重さ（`severity`）は、`"error"`・`"warning"`・`"info"` の 3 段階から増やさないので閉じた型にしています（網羅的に分岐できるほうが役に立つため）
- 利用者の設定の値か、その要約（合成したカレンダー。17 番）を返す項目（カレンダー・スケジュールの `outOfRangePolicy`・`unconfirmedHolidayPolicy`）は、設定の型と同じ閉じた型にします。どちらも設定の型の値の中から選び、ライブラリが新しい値を返さないためです

### 3. 例外は従来のクラスに `code` を付け、メッセージは API に含めない

例外は `RangeError` か `TypeError` のインスタンスで、`code` を持ちます。`isBizdaysError()` で、このライブラリの例外かを判定できます。

- 独自の例外クラスにすると、`instanceof RangeError` で判定している既存のコードが壊れるためです
- 同じ `code` は同じクラスで投げます。経路によってクラスが違うと、`instanceof` で受けるコードが経路ごとに漏れるためです
- `code` ごとのクラスの対応は次のとおりです。`invalid-input`（受け付けない種類の入力。文字列・`Date`・Temporal のいずれでもない値）だけが `TypeError` で、ほかのすべての `code` は `RangeError` です。値の誤りも、引数の型の誤り（関数でない・配列でない・オブジェクトでない）も `RangeError` にします（これはクラスの規則で、どの `code` になるかは 8 番による）。引数の型の誤りと値の誤りは、同じ `code`（`invalid-argument`・`invalid-date` など）では区別しません。そのため、クラスで分けると、同じ `code` に複数のクラスが対応してしまいます。`src/core/errors.ts` の冒頭はこの番号を指すだけにし、`test/robustness.test.ts` ですべての `code` について実際のクラスを確かめます
- メッセージの文言（例外と診断の `message`）は API に含みません。判定には `code` を使います。メッセージは英語で、改善のためにバージョンをまたいで変えます

### 4. 返すものは凍結し、設定は作る時点で取り込む

設定の配列・オブジェクトは作成時に複製し、返すオブジェクト・配列はすべて `Object.freeze` します。

- 作成後に利用者が元の設定を書き換えても結果が変わらず、共有されたカレンダーを誤って書き換えることも防げます
- スケジュールの値そのものは複製しません。値をあとから書き換えないことは利用者に任せます
- 凍結するオブジェクトには、作成後に印（`WeakMap` のキー、`defineProperty` の項目）を付けず、印はリテラルに含めます（列挙されない Symbol の項目など）。凍結済みのオブジェクトに後から印を付けると V8 がオブジェクトを遅い形に落とし、作成が約 30% 遅くなったためです

### 5. 型引数 `Kind` は残し、`kinds` もその型で受ける

`Calendar<Kind>`・`Schedule<Value, Kind>` の `Kind`（祝日の種別）は、既定値（`string`）付きで残します。規則の `kinds` も `readonly Kind[]` で受け、設定の型まで型引数を流します。

- 日本の祝日では `kind`・`kinds` の補完が効く利点があり、既定値があるので使わない利用者の負担はありません
- 種別は開いた型（2 番）なので、提供元にない文字列も型では通ります（診断で `never-matches`）
- 祝日の識別子（`key`）には型引数を足しません。2 つ目の型引数が `Calendar` から規則の型まで波及するので、各提供元に既知の値の型（`KnownJpHolidayKey` など）を添えるにとどめます（25 番）

### 6. 型と実行時を一致させ、黙って通っていた誤りは例外にする

型で受け付けない入力は、実行時にも受け付けません。型で区別できない誤った組み合わせは、黙って通さず例外にします。

- 型と実行時の食い違いは不具合として直します。規則の形ごとに受ける項目は型でも分けています（祝日・祝日の前後の規則の `holidayOverlapPolicy`、`"after-holiday"` のない `skipWeekdays` などは型エラー）
- 型で区別できない誤り（暦日の文字列と日時の文字列はどちらも `string`）は実行時に止めます。`businessDayOnOrAfter` の `cutoff` を時刻のない入力と組み合わせると `invalid-argument` です。暦日を 0 時として黙って扱うと、締め時刻を無視したことに、出荷に間に合わなかった後で初めて気付くためです
- 空白で区切った日時の文字列（`"2026-11-23 10:00"`）は `invalid-time` です。日時の区切りは ISO 8601・RFC 3339 の区切り（`T`・`t`）だけを受けるためです（型 `DateTimeInput` が表すのは大文字の `T` だけで、小文字は実行時だけ受ける）
- 省略可能な項目に明示的に書いた `undefined` は、どの階層（設定・規則・個別の日付・毎年の月日・メソッドのオプション）でも省略と同じに扱います。`exactOptionalPropertyTypes` を使わない利用者の型は `undefined` を通すので、項目によって作成が失敗すると、型が通るのに実行時に落ちるためです。知らないキーは、値が `undefined` でも診断の `unknown-option` で知らせます（打ち間違いを見つけるため）
- 黙って通っていた呼び出しを止める変更をどのバージョンで出すかの理由は、32 番にあります

### 7. 瞬間と暦日の変換は国に依らない経路にまとめる

瞬間（`Date`・Temporal の `Instant` など）と、あるタイムゾーンの暦日・時刻の変換は、ルートの関数（`toDateString`・`toDateTimeParts`・`toInstant`）と、カレンダー・スケジュールのメソッド（`dateOf`・`civilOf`・`instantOf`）の 2 経路だけにします。

- 国ごとの変換関数（`toJapanDate`・`toJapanDateTime`）は日本だけの特別扱いだったので非推奨にし、1.0.0 で削除します。`bizdays-toolkit/jp` の祝日の関数（`isHoliday` など）と既定のカレンダーは、README の最初の例で使う入口なので残します
- メソッドは主な用途（次に開く瞬間）がカレンダーのタイムゾーンで完結するため置きます。結果が文脈で変わるので、ルートの関数の別名ではありません（9 番）
- 時刻を必ず持つ入力（`Date`・`Instant`・`ZonedDateTime`・`PlainDateTime`・`"YYYY-MM-DDTHH:mm…"`）では、オーバーロードで `time` を `string` にします。返す値は変えず、型だけを正確にします
- 暦日と時刻から瞬間への変換は `Date` を返します。`Date` は 1 行のコードでエポックミリ秒・ISO 文字列・Temporal の `Instant` に変換でき、型を増やさずに済みます。入力は暦日の文字列だけで（`Date` を受けて「その日の 10:00」とすると、どの日か曖昧になる）、時刻は `"HH:mm"` と `"HH:mm:ss"` です
- 時刻は文字列（`"14:00"`）で受け、数値（`cutoff: 14`）では受けません。`14.5` が 14:30 なのかなどの曖昧さが増えるためです。年月日と月日も 1 つの配列にはまとめず、個別の日付と毎年の月日の項目を分けます（明示的に分けたほうが、どちらの意味かが読み取りやすいため）
- 夏時間の飛び・重複は Temporal の既定 `disambiguation: "compatible"` と同じにします（Temporal・Luxon・date-fns-tz の既定と一致し、別の道具と突き合わせても食い違わない）。選択肢は需要が見えるまで足しません。実装は `Intl` だけで、前後 1 日のオフセットを候補にして往復で一致するものを選びます

## 設定の受け付けと改名

### 8. 設定の知らないキーは無視し、知っているキーの矛盾は例外にする

`createCalendar`・`createSchedule` は、設定の知らないキーで例外を投げません。知っているキーの無効な組み合わせは、作成時に `invalid-option` です。

- 将来のバージョンで足した設定を古いバージョンに渡しても壊れないようにするためです（前方互換）
- 打ち間違いは TypeScript では型エラーになり、JavaScript では内部的に警告として記録され、診断の `unknown-option` で見つかります（30 番）
- 知っているキーの矛盾（祝日の規則に `holidayOverlapPolicy` を付けた、など）は、黙って無視すると設定の意図を読み違えるので例外にします。前方互換のための無視と、矛盾の検出は別の目的です
- 改名した旧名は、知らないキーではなく知っているキーとして扱います（10 番）
- 設定の誤りは `invalid-option`、それ以外の引数の誤りは `invalid-argument` です。設定とは、営業日カレンダーかスケジュールを作る関数が検証して取り込む、作るものの振る舞いを決めるオブジェクトで、オブジェクトでないことも設定の誤りです。設定・オプションの引数で「オブジェクト」として受けるのは普通のオブジェクト（`Object.prototype.toString` の種類が `Object` のもの。別の実行環境のもの・プロトタイプのないもの・クラスで作ったものを含む）だけで、種類がほかのものはすべてオブジェクトでないものとして扱います（例: `Date`・`Map`・`Set`・`RegExp`・`Error`・`Promise`・型付き配列・配列・関数・包んだプリミティブ、`Symbol.toStringTag` で種類を替えたオブジェクト）（関数によって黙って空の設定として受けると、同じ誤りが関数ごとに通ったり止まったりするため）。診断は作成と同じ検証をするので、同じ `code` を結果で返します。メソッドのオプション（呼び出し 1 回の振る舞いを決める）と、保存した設定を検証せずに書き換える移行の関数が受け取れない値は、引数の誤りです。同じ種類の誤りの `code` が関数によって違うと、`code` で受けるコードが関数ごとに漏れるためです（3 番のクラスと同じ理由）

### 9. 公開する名前は 1 つの規則に合わせる

公開する名前（export・型の項目とメソッド・引数・型引数・文字列の値）は、`etc/naming.md` の規則 N1〜N9 に合わせ、`scripts/check-names.ts` がビルド済みの型定義に当てて確かめます。名前を許す一覧（例外）は持ちません。

- 名前の揺れ（数を返す `businessDaysBetween` と一覧を返す `listBusinessDays` など）が生じた原因は、名前の付け方の規則を先に決めていなかったことです。1.0.0 の前に一度だけ、規則を作ってからすべての名前を合わせました（0.30.0）
- 規則の要点: N1 一語一義・一義一語（用語集）、N2 関数・メソッドの名前の形が返すものと引数を約束する（`is…` は真偽値、`diff…` は数、`…Between` は両端を含む一覧、`…On` はその日のもの、`with…` は足した新しい一覧など）、N3 真偽値の項目は形容詞か過去分詞、N4 単数・複数は型の形に合わせる、N5 選択肢の項目は `Policy` で終える、N6 関数を受ける項目は動詞で始める、N7 国の型の頭・設定の型の名前、N8 外部の名前は出典を書いて写す（`@namingSource`）、N9 スケジュールの側の型は `Schedule` で始める
- 意味の重なりのうち型で表せるもの（`day` を項目名の末尾に使わない、`rule` は繰り返しの規則の型だけ、など）は、用語集の「型」の列で機械的に確かめます。同じ名前の `Policy` の選択肢は、項目の名前を PascalCase にした型の値の部分集合にします（規則の形ごとに選択肢を絞るのは部分集合なので合う）。形を分けるための `?: never` の項目には TSDoc を付けません（付いていれば、型を分けたときに別の項目の説明がずれている）。規則から機械的に決まらない名前（`rulePath` → `optionPath` など）は、N1 の意味の重なりとしてレビューで決めます
- 外部の名前は N8 で扱えるので、例外の一覧は要りません
- 名前の全面的な整理のバージョンを区切るため、そのバージョンを 0.30.0 にしました（0.23.0〜0.29.0 は欠番）。プレリリースは出さず、旧名を受け付ける移行期間（10 番）そのものを試す期間にしました
- 同じ結果を返す別名は追加しません。例外は、使用頻度の高い `firstBusinessDayOfMonth`・`lastBusinessDayOfMonth`（`nthBusinessDayOfMonth` の引数を固定したもの）と、改名の移行期間の `@deprecated` の別名だけです。文脈（タイムゾーン・営業日）を持つオブジェクトのメソッドは、結果が変わるので別名ではありません

### 10. 改名の旧名は 1.0.0 より前のバージョンで受け付け、1.0.0 で `invalid-option` にする

0.30.0 で改名した旧名を、1.0.0 より前のバージョンでは受け付けます（0.31.0 以降のマイナーバージョンも含む）。

- 改名した設定のキーと値の表は `src/core/renamed.ts` の 1 か所に置き、検証の入口での読み替え・診断の `deprecated-option`・`migrateCalendarOptions`・`migrateScheduleOptions` がこの表だけを使います
- 旧名と新しい名前の両方を書くと `invalid-option` です（どちらを使うか読み取れない）
- 設定の型が旧名を持つのは省略可能なキーだけで、必須のキーの旧名と規則の `day` は実行時だけ受け付けます。旧名の関数・メソッド・型・返す項目は、`@deprecated` を付けた別名として残し、移行ガイドの削除予定の表に修飾名で載せます。型と実行時の一致（6 番）は新しい名前についての約束です
- 位置を表す文字列（`optionPath`・診断の `path`・例外のメッセージ）は、旧名で書いた設定でも新しい名前で返します。`deprecated-option` の `path` だけは、利用者が書いた旧名の位置です
- `migrate…` は、1.0.0 より前に保存した設定を 1.0.0 以降に読み込む利用者のため、1.0.0 以降も残します。診断と同じく開発・移行の道具なので `bizdays-toolkit/diagnose` に置きます
- 1.0.0 で、旧名（関数・メソッド・型・返す項目）を削除し、設定の旧名を `invalid-option` にし、診断コード `deprecated-option` を削除します

**返す値の改名と `kinds` の `"national"`**

- 返す値の改名（理由の `"regular"` → `"default"`、日本の祝日の種別 `"national"` → `"regular"`、エラーコード `invalid-month-day` → `invalid-annual-date`）には、2 つの値を同時に返せないため、移行期間を設けません。また、その値を設定に書いている利用者の結果が変わりうるため、「改名は結果を変えない」という原則の例外です。日本の提供元とほかの提供元を組み合わせた設定では、`kinds` の `"regular"` は、0.22.x ではほかの提供元の祝日だけに当たりましたが、0.30.0 以降は日本の国民の祝日にも当たります。現在の意味（すべての提供元の毎年の祝日）は 24 番（種別の意味は提供元が決める）に沿っているため、挙動は元に戻さず、移行ガイドで知らせます。診断で知らせる案も検討しましたが、新しい名前で正しく書いた設定にも診断が出て、テストの `[]` を壊すため採用しません。提供元で絞り込む項目（`providerIds`）を追加する案も採用しません。和集合の祝日の表では、同じ日付に複数の提供元の祝日がある場合、先の提供元の祝日だけを残すため（24 番）、直感に反する結果になるからです。返す値を変更するバージョンでは、その値を設定に書いている利用者の結果が変わらないかを確認します
- `kinds` の旧名 `"national"` は、ID が `"JP"` と完全に一致する提供元を使う設定でのみ扱います。「種別が `"national"` の祝日、または日本の提供元が返した `"regular"` の祝日」に当てます（0.22.x と同じ意味です）。日本の提供元かどうかは `id` だけで判断し（大文字・小文字を区別し、合成ではカレンダーごとに判断します）、データからは推定しません。データから推定すると、自作の提供元を誤って対象に含めるためです。1.0.0 より前のバージョンでは、和集合の `deprecated-option` のメッセージで、1.0.0 以降の扱いを予告します。`id` を変えて包んだ日本の提供元は対象外です。この場合は、診断の `never-matches` に改名の可能性を添えます（提供元のない設定には添えません。原因は提供元の付け忘れであることのほうが多いためです）
- `migrate…` は、提供元がすべて ID `"JP"` のときだけ `"national"` を書き換えます。和集合では新しい名前で同じ意味を書けないので書き換えません
- 1.0.0 では、ID `"JP"` の提供元を含む設定の `"national"` を `invalid-option` にし、含まない設定では普通の種別の文字列として扱います。和集合で書いた利用者のほとんどは日本の祝日のつもりで、黙って何にも当たらなくすると気付けないためです。厳しい側で出しておけば、需要が示されたときに後のマイナーバージョンで緩められます。例外のメッセージは、日本の提供元を包んで種別を付け替える書き方と、自作の提供元の種別の名前を変えることを示します
- 1.0.0 で行う作業は RELEASING.md の「1.0.0 で行う作業」にまとめます。`never-matches` に添える改名の説明は 1.0.0 以降も残します（`id` を変えて包んだ提供元の利用者には唯一の手がかりになる）

## 判定のモデル

### 11. 判定の順番は固定し、規則と祝日の関係だけを規則ごとに選ばせる

判定の順番は固定で、利用者が全体を並べ替える設定は持ちません。ガイドの「Business-day calendars」では、判定の順番を次の番号で示します。ほかの項目で「11 番の n」と書くときは、この番号を指します。臨時営業日（1）、臨時休業日（2）、毎年の月日（3）、繰り返しの規則（祝日の上）と祝日の規則（4）、祝日（5）、繰り返しの規則（祝日の下・振替先）（6）、曜日（7）、それ以外（8）。

- 全体を並べ替えられると、同じ設定でもカレンダーごとに意味が変わり、診断も順番の組み合わせごとに要ります
- 個別の日付や毎年の月日が祝日より優先されるのは、どの業種でも共通です。店舗によって分かれるのは「繰り返しの規則が祝日に当たったとき」だけなので、そこだけを規則ごとの `holidayOverlapPolicy` で選べるようにしました
- 値は真偽値にせず、3 つの状態を同じ観点で表す言葉（`"under-holiday"`・`"over-holiday"`・`"after-holiday"`）で表します。前への振替（`"before-holiday"`）は状態の数そのものを変えるので足しません。「支払日が休日なら前営業日」は日付の計算（`adjust` の `"preceding"`。21 番）で書けます

### 12. 「第 n 何曜日」は、その月で n 回目のその曜日

`{ weekday: 3, nth: 3 }` は、その月で 3 回目の水曜日（15〜21 日の水曜日）です。

- 「カレンダーの第 3 週の行の水曜日」の意味で使う業種もあり、月初の曜日で結果がずれます。回数で数える定義に統一し、ガイドに明記しています
- その月に存在しない日（`nth: 5` がない月、`dayOfMonth: 31` がない月）は当てはまりません。末日に読み替える便利さより、書いたとおりに当てはまることを優先します（末日は `dayOfMonth: -1`）。読み替えないのは繰り返しの規則だけで、期日と締め日は末日に読み替えます（21・23 番。その月のどこかに必ず決まる必要があるため）
- 「隔週」は第 n 曜日では表せないので、`interval`・`anchor` で書きます（14 番）

### 13. 振替先は「その日以降で最初の祝日でない日」で、飛ばす曜日は規則に書く

`holidayOverlapPolicy: "after-holiday"` の規則は、祝日には適用せず、その日以降で最初の祝日でない日に当てはめます。`skipWeekdays` を書くと、その曜日も飛ばします。

- 振替の判断に使う「祝日」は提供元の祝日だけで、利用者の休業日の設定（`closedWeekdays` など）は見ません。休業日の設定で振替先が変わると、設定の影響が読み取りにくくなるためです
- 土曜日も振替先になりえます。言葉どおりの「翌平日」は `skipWeekdays: [6]` で書きます。就業規則の「土日祝に当たれば翌月曜日」のように毎年必ず起きる需要があり、結果を列挙すると、本来は規則として表すべきものを結果として記述することになるため、飛ばす曜日を規則自身に書けるようにしました。飛ばす曜日は規則に書くので、どの設定が振替先を変えたかも読めます
- `skipWeekdays` は `"after-holiday"` の曜日・日の規則と、祝日の前後の規則（15 番）でだけ使えます。それ以外の形・ほかの `holidayOverlapPolicy` との組み合わせ、曜日の規則でその曜日自身を含めること、すべての曜日は `invalid-option` です（毎回振り替わる規則は意図が読めない）。`holidayOverlapPolicy` の値を増やす案は、曜日の集合を書けないので取りません
- 振替先は繰り返しの規則と同じ段階で判定し、その日に個別の日付や毎年の月日があればそちらが優先です。振替先が別の規則の適用日と重なった場合は、開く規則が閉じる規則より先で、同じ配列の中では先に書いた規則が決めます（11 番の同じ段の中の順）
- 有効期間は、振替元の日（規則が本来当てはまる日）で判定します。`shiftedFrom` は振替元の日です

### 14. 有効期間・隔週・日単位の周期

繰り返しの規則と毎年の月日には、省略可能な有効期間 `effectiveFrom`・`effectiveTo`（両端を含む暦日）を付けられます。曜日の規則では、`{ weekday, interval, anchor }` で n 週おきの周期を、`{ cycle, anchor, positions }` で日単位の周期を表せます。

- 「2027 年 4 月から定休日を月曜から火曜に変える」は、カレンダーを 2 つ作って呼び分けると、切り替え日をまたいで探す計算（`addBusinessDays` など）が正しく動きません。個別の日付で列挙すると件数が膨らみ、個別の日付は祝日より優先されるので意味も変わります。規則そのものに期間を持たせるのが、意味を保てる形です
- 期間の外では、その規則が存在しないものとして扱い、判定の順番には影響しません。個別の日付（それ自体が期間）と `closedWeekdays`（期間付きの毎週の規則で書ける）には付けません
- 名前は、毎年の月日の `from`・`to` と区別するため `effectiveFrom`・`effectiveTo` にしました（業務システムで「有効期間」に広く使われる語）
- `anchor` は「周期を数え始める日」という 1 つの意味に限定しています（隔週では `weekday` と同じ曜日の日付）。周期の位相を決めるだけです（起点より前の日にも当てはまる）。開始日は `effectiveFrom` で書きます。起点を「偶数週・奇数週」や ISO 週番号にしなかったのは、年をまたぐと週の数え方が変わり、店舗の掲示（「○月○日から隔週」）と一致しなくなるためです
- `interval` は 2 以上（1 は毎週と同じ）、`cycle` は 2 以上、`positions` は 1〜`cycle` の重複のない配列で、空とすべての日は `invalid-option` です。位置を 1 始まりにしたのは、このライブラリの位置を表す項目（`dayOfMonth`・`nth`・`businessDayOfMonth`）がすべて 1 始まりで、0 始まりは読み違いを招くためです
- 交替制（4 勤 2 休）や 10 日に 1 度の点検日は、7 日周期の規則では書けないので `cycle` を足しました。`cycle` に `"after-holiday"` は付けられません（周期の日を祝日の後ろへずらす意味がない）

### 15. 祝日に従属する規則（祝日・祝日の翌日・祝前日）と絞り込み

祝日そのもの（`holiday: true`）、祝日の翌日（`dayAfterHoliday: true`）、祝前日（`dayBeforeHoliday: true`）を、繰り返しの規則の形として書けます。絞り込みの配列 `kinds`・`keys`・`weekdays`・`months` と有効期間は AND で組み合わせます。

- 「祝日の翌日休館」「振替休日は診療」「祝前日料金」は、祝日の一覧から日付を生成し、個別の日付として登録する回避策では、年を決めて生成する必要があり、個別の日付が毎年の月日より優先されるので「年末年始は例外」との順番も崩れます。規則であるべきものを結果として書かないため、規則の形にしました。年ごとに日付を列挙する形は、規則の代わりとしては取りません
- 祝日の翌日は「連続する祝日の最後の日の翌日で、その日自身は祝日でない日」、祝前日は「翌日が祝日で、その日自身は祝日でない日」で、振替先（13 番）と同じく提供元の祝日だけで決めます。`skipWeekdays` を書くと「祝日と書いた曜日が続く塊（祝日を 1 日以上含む）の前後の日」になります（祝日を含まない普通の週末は塊にならない）。「飛び石連休の間の日」のように、カレンダー自身の結果に依存する規則は入れません
- 祝日の規則は「祝日の上」の段階（11 番の 4）で判定し、`holidayPolicy: "ignore"` でも当てはまります（無視するのは既定の扱いだけで、祝日を対象にすると書いた規則は書いたとおりに効くべき）。祝日の前後の規則は繰り返しの規則の段階で判定します。当てはまる日は祝日ではないため、どちらの規則でも `holidayOverlapPolicy` を指定すると `invalid-option` になります
- 前後の規則に指定した `kinds`・`keys` は、隣接する祝日に対して判定します（塊なら、その日に最も近い祝日）。連休のどれかを見る案は、「こどもの日の前日」が 5 月 2 日になるなど意図とずれる結果を黙って返すので取りません
- `kinds`・`keys`・`weekdays` は、祝日と祝日の前後の規則にだけ付けられます（ほかの形に付けたら `invalid-option`）。`weekdays` は、「祝日の翌日は休館。土日なら開館」のように、2 条件の論理積（AND）を 1 つの規則で表すためのもので、曜日の規則（`weekday`）と区別するため複数形にしました
- 種別・識別子は開いた型なので文字列の配列であることだけを検証し、提供元にない値は診断で `never-matches` です
- 祝日の名前（`nameEn`）で判定する案は採用しません。名前は公式データの綴りを反映するデータであり、パッチバージョンで変わりうるためです。祝日を個別に指すには `key`（25 番）を使います

### 16. 第 n 営業日の規則（月・週）

`{ businessDayOfMonth: n }` は月の n 番目（負なら後ろから）の営業日、`{ businessDayOfWeek: n, weekStart }` は週の n 番目の営業日に当てはまります。

- 「月末最終営業日は棚卸しで出荷停止」は、暦の末日（`dayOfMonth: -1`）や最終金曜日では数日ずれ、照会用のメソッド（`lastBusinessDayOfMonth`）は設定の規則ではないので書けませんでした
- **数える基準は、そのカレンダーの繰り返しの規則をすべて除外した判定結果**（個別の日付・毎年の月日・祝日（`holidayPolicy` の扱いどおり）・定休日の曜日）です。基準を規則の結果に依存させると「最終営業日は休業」と書いたときに定義が循環します。利用者の言う「最終営業日」も、土日祝と年末年始を除いた暦上の日です。定休日を繰り返しの規則で書いている設定ではその曜日も営業日として数えるので、診断が info の `counting-basis` で知らせます
- 項目名を `businessDay` にしなかったのは、`DayInfo.open`（営業日か）と同じ語が 2 つの意味を持たないようにするためです。メソッド `nthBusinessDayOfMonth` などは規則を適用した後の実際の営業日を返すので、`{ businessDayOfMonth: -1 }` を休業にすると `lastBusinessDayOfMonth` は前日を返します。名前で数え方の違いを示しています
- `holidayOverlapPolicy` は `"under-holiday"`（既定）と `"over-holiday"` を受け、`"after-holiday"` は `invalid-option` です（数えた結果をずらす意味がない）。`holidayPolicy: "open"` では第 n 営業日が祝日に当たることがあり、「祝日でも休業」と書く手段として `"over-holiday"` を残しました
- スケジュールには営業日・休業日の概念がないので、数える基準のカレンダーを規則の `calendar` で必ず指定します（タイムゾーンが同じでなければ `time-zone-conflict`）。スケジュールでの基準は、そのカレンダーの実際の営業日（規則を適用した後）です。参照先は別のカレンダーなので循環しません。カレンダーの規則には付けられません（基準は自分の設定で決まる）
- `holidayPolicy: "closed"` では当てはまる日が祝日になることはないため、`"over-holiday"` は結果を変えず、診断が `redundant` で知らせます
- 週は `weekStart` から 7 日間で、`weekStart` は必須です（業種で週の始まりが分かれ、既定値を持つと決めずに使うため。21 番の `convention` と同じ）。週番号は付けないため、ISO 週番号を採用しなかった理由（14 番）は当たりません
- 月・週の基準は規則ごとに局所的にキャッシュします。判定全体のキャッシュ（営業日表）は、明確な性能の課題が出るまで入れません。判定が入力の値だけで決まること（20 番の `isOpen` の純粋さを含む）が前提になり、その前提を壊す変更を見つけにくくなるためです

### 17. 対応年の外と、未確定の祝日のガード

提供元の対応年の外の日を判定に使うと、既定（`outOfRangePolicy: "throw"`）では `out-of-range` を投げます。`unconfirmedHolidayPolicy: "throw"` では、予測（`confirmed: false`）の祝日を判定に使うと `unconfirmed-holiday` を投げます。

- 例外を投げる箇所は、祝日を引く内部の 1 つの経路（公開のメソッドと判定のすべてがここを通る）に集約し、「評価した日すべて」で止めます。求めた日だけでなく、探索が途中で通る日や、隣の日を見る規則（祝日の前後・`skipWeekdays`・`"after-holiday"` の振替元・週の第 n 営業日）が見る日も含みます。結果を確定できない年や予測に依存しうる経路を、漏れなく止めるためです

投げない場合は、次の 2 つです。

- `holidaysInYear`・`holidaysBetween` は未確定の祝日で投げません。一覧は `confirmed` を確認するための経路であり、例外が発生した後に影響する日を列挙する代替手段になります
- 結果が祝日に依存しない設定（`holidayPolicy: "ignore"` で、祝日に従属する規則も `"after-holiday"`・`"over-holiday"` の規則もない場合）では、値だけを求める判定（営業日かどうか・探索・第 n 営業日の数え方）で、未確定の祝日を理由に例外を投げません。祝日と祝日でない日で判定結果が同じであり、予測が結果に影響しないためです。一方、`dayInfoOn` など、その日の情報を返す処理では、`holiday` を付けるために祝日を参照するので例外を投げます。また、対応年の範囲外や提供元のデータに誤りがある場合は、この設定でも例外を投げます。祝日に依存しないかどうかは、判定と診断で共通の関数（`resultIgnoresHolidays`）を使って判定します。診断では、この設定に対する `"throw"` を `redundant` として知らせます

合成・診断・限界は、次のとおりです。

- 合成の判定と祝日の参照（`dayInfoOn`・`isHoliday`・`holidayOn`・`holidaysInYear`・`holidaysBetween` を含む）は、構成カレンダーのそれぞれで同じ判定・参照をし、どれかが投げるときだけ投げます（そのカレンダーの判定が例外になるため）。祝日の提供元の和集合に方針を一律に当てると、あるカレンダーの方針が別のカレンダーにしか属さない提供元にまで当たり、どの構成カレンダーも投げない日に投げるためです（0.31.2 まではこの形だった）。合成の `outOfRangePolicy`・`unconfirmedHolidayPolicy` の値は、その要約（どれかが `"throw"` なら `"throw"`）です。結果が先のカレンダーで決まった後も残りのカレンダーを判定し、省略しません。省略すると、例外を投げるかどうかが並び順によって変わるためです（判定の費用は合成したカレンダーの数に比例します）
- 診断は常に `"accept"` で評価し、走査の端では外を祝日なしとして扱います。設定の形を調べるもので、祝日の確定や対応年は無関係なためです
- 限界: 検出できるのは「予測された祝日」で、「まだ知らない祝日」（英国の臨時の bank holiday など）ではありません

## 合成とスケジュール

### 18. カレンダーの合成は作成済みのカレンダーに対して行い、判定を決めたカレンダーの結果を引き継ぐ

`combineCalendars(calendars, { open: "all" | "any" })` は、作成済みの営業日カレンダーを合成して、通常の営業日カレンダーを返します。

- 設定を結合して 1 つのカレンダーを作ると、片方の臨時営業日がもう片方の休業日を打ち消します。片方を祝日の提供元として包むと、相手の休業日が祝日になり、振替先まで変わります。祝日と休業日の区別を壊さないため、判定結果を組み合わせます。各カレンダーの中の判定の順番は変わりません
- `dayInfoOn` は `"combined"` のような新しい理由を追加せず、合成結果と同じ判定をした最初のカレンダーの `reason`・`name`・`shiftedFrom`・`optionPath` を引き継ぎます。そのカレンダーの番号を `decidedBy` に、外側から順に並べた番号の列を `decidedByPath` に格納して返します（入れ子でない合成では長さ 1 で、先頭の値が `decidedBy` です。合成していないカレンダーには付きません）。内側の `DayInfo` を入れ子にする案は、利用者側で再帰的な処理が必要になるため採用しません。理由を 1 つの値にまとめるよりも役に立つためです
- 祝日は各カレンダーに聞き、日付ごとに先のカレンダー（その中では先の提供元）の祝日を返します（方針は各カレンダーのもの。17 番）。包んで祝日を除いた提供元と元の提供元を合成すると、除いたはずの祝日が `holiday` に付きますが、営業日の判定には影響しないのでそのままです
- タイムゾーンは同じでなければなりません（`time-zone-conflict`）。探索の上限 `searchDayLimit` は合成でも指定できます。公開インターフェースだけで合成するので、合成したカレンダーをさらに合成できます。設定の診断は合成したカレンダーを対象にしません

### 19. 判定の理由と、決めた設定の位置

`DayInfo`・`ScheduleDayInfo` の `reason` は「値を決めた規則の種類」、`optionPath` は決めた設定の中の位置（診断の `path` と同じ形）です。

- `reason` の意味は変えません。スケジュールで祝日の値が曜日の値と同じ扱いなら、祝日でも `"weekday"` です。祝日かどうかは `holiday` で判定します。「祝日の規則が関わったか」を表す項目は、区別が増えてかえって分かりにくくなるので足しません。営業・休業の状態は `open`、判定理由は `reason` で表すという分担です
- `optionPath` は、`name` が省略可能で重複もできるので、決めた規則を機械的に特定するために返します。個別の日付・毎年の月日・繰り返しの規則（振替先を含む）で決まった日にだけ付け、祝日・曜日で決まった日には付けません（祝日は配列の規則ではなく、曜日はその日の `weekday` で分かる）
- 合成では、判定を決めたカレンダーの位置を引き継ぎ、`decidedBy` と組で読みます（18 番）

### 20. スケジュールから営業日カレンダーを作る

`createCalendarFromSchedule(schedule, isOpen)` は、スケジュールと「値が営業か」を決める関数から営業日カレンダーを作ります。

- 営業時間表のようなスケジュールを設定の正本としている利用者が、営業日カレンダーをもう一式書いて同期を取らずに済むようにするためです
- `isOpen` は値だけを受け取ります。日付や祝日を見られる形にすると「純粋な関数」の前提を利用者が破りやすく、営業日の探索の結果が呼ぶたびに変わる危険があります。日付で変えたい条件はスケジュールの規則に書きます。将来も日付は渡しません
- `reason` は `createCalendar` と同じ対応で、スケジュールの `annualDates` は営業を表す値も持てるので `"open-annual"` があります。曜日の値で営業日になる日は `"open-weekday"` です。営業になる祝日は `"holiday"` のままです（19 番の分担）
- `createCalendar` のオーバーロードにしなかったのは、第 1 引数の形で分岐すると型が複雑になり、設定誤りの診断とも競合するためです。診断はスケジュールの設定に `diagnoseSchedule` を当てます

## 日付の計算

### 21. 日付の調整は方法を必ず指定し、「最も近い営業日」は入れない

`adjust`・`dueDate`・営業日を考慮した締め日の `convention` は必須で、既定値を持ちません。方法は金融で使われる 4 つ（following・preceding・modified-following・modified-preceding）です。

- 休業日の期日を翌営業日にするか前営業日にするかは、契約や業種で決まります。既定値があると、方法を決めずに使ってしまい、誤った期日を出すおそれがあります
- 「最も近い営業日」は入れません。前後が同じ距離にある場合の決め方は業種ごとに異なり、どちらに決めても誤用を招くためです
- 月が変わるか（modified-…）は、調整する前の日付（期日では末日に読み替えた後の日付）の月と比べます。同じ月に反対向きの営業日もないときは、月が変わっても元の向きに調整します（例外にすると、その月が全部休業日の設定で期日が求められなくなる）
- 期日の `dayOfMonth` は、その月にない日を末日に読み替えます（期日はその月のどこかに必ず決まる必要がある。12 番）

### 22. 期間の扱い: `diffBusinessDays` だけが半開区間

期間を指定する API（`…Between`）は両端を含みます。数を返す `diffBusinessDays(from, to)` だけは `from` 以上 `to` 未満で、逆順なら負の値です。

- 半開区間だと `diff(a, b) + diff(b, c) = diff(a, c)` が成り立ち、起点が営業日なら `addBusinessDays` の逆算になります。名前の形（`diff…` は数、`…Between` は両端を含む一覧。9 番）で扱いが分かります
- 起点が休業日のときは逆算になりません。`addBusinessDays` は「翌日以降の n 個目の営業日」で、休業日からは `+0` と `+1` が同じ日です。これは期日計算の慣習（Excel の `WORKDAY`）と同じなので変えず、`addBusinessDays(a, n) = addBusinessDays(businessDayOnOrAfter(a), n − 1)`（n ≥ 1）を性質のテストで固定しています
- `from` が `to` より後の一覧は `invalid-range` です

### 23. 締め日と締め期間

`closingMonth(date, closingDayOfMonth)` は日付が属する締め月、`closingPeriod(monthOrDate, closingDayOfMonth)` はその月分の期間（`{ from, to }`）を返します。カレンダーのメソッドは、締め日を営業日で調整します（`convention` は必須。21 番）。

- 締め日がその月にない場合は末日に読み替えます。読み替えは内部の 1 か所に置き、両方の関数が使います。利用者が期間を自分で組み立てると、2 月の 30 日締めの境界でずれるためです
- 期間は専用の型を足さず、`DateRange` と同じ形にします（日付の期間の語彙を 1 つに保つ）
- 営業日を考慮したバージョンの定義: 月 m の調整後の締め日 D(m)、m の期間は D(m−1) の翌日〜D(m)、`closingMonth(date)` は date ≤ D(m) となる最小の m。前月と当月の両方の調整後の締め日と比べないと境界を誤るので、ライブラリに置きます
- 固有の期間がない月（長期休業で D(m) = D(m−1)）は、定義の帰結として次の月に併合されます（「締め日を過ぎた日は次の月分」という素朴な読み方と一致する）。その月の `closingPeriod` は `no-business-day` を投げます。`from > to` を返すと渡した先で誤りになり、`undefined` は全利用者に null チェックを強いるためです
- 性質のテストで、締め日 1〜31・−1 と 4 つの方法について、期間が隙間や重複なく連続すること、期間内の日で `closingMonth` が往復することを確かめます。ルートの暦日の関数とメソッドは結果が違うので、別名ではありません（9 番）

## 祝日の提供元

### 24. 提供元の契約と検証。祝日データは実行時に取り込まない

`HolidayProvider` が返した祝日は、各年について初めて利用するときに検証し、契約の項目（`date`・`name`・`nameEn`・`kind`・`confirmed`・`key`・`names`）だけを持つ凍結したオブジェクトにします。

- 利用者が実装した提供元の誤り（日付の形式、別の年の日付、重複など）で、判定が黙って狂うのを防ぐためです。検証は年ごとに 1 回なので、速さにはほぼ影響しません
- 種別（`kind`）の意味は提供元が決めます。同梱の提供元は、毎年繰り返される祝日を `"regular"`、振替を `"substitute"`、臨時の日を `"special"` にそろえています
- 名前は `name`（現地語）と `nameEn`、ほかの言語は省略可能な `names`（キーは正規の形の BCP 47 の言語タグ）です。同梱の提供元は、公式の出典があり照合できる言語の名称だけを付けます。出典のない翻訳を同梱すると、照合済みのデータと品質がそろわないためです。表示にどの言語を使うかは、ライブラリでは決めません
- 祝日データはパッケージに含め、実行時にネットワークから取得しません。取得データの改ざんや取得の失敗が、判定の正しさに直結するためです。法改正への対応はバージョンの公開で行い、どうしても必要な利用者は提供元を自分で実装できます
- 祝日を休みにするかは利用者が決めます（`holidayPolicy` と祝日の規則）。提供元は法令・公式データのとおりに返します
- 1 つのカレンダーに複数の提供元を渡すと、祝日は提供元の和集合になります。同じ提供元のオブジェクトは 1 回だけ数え、同じ日付に祝日のある提供元が複数あれば、先に渡した提供元の祝日だけを残します。`holiday` と規則の `kinds` の判定を、その日の 1 つの祝日で決めるためです

### 25. 祝日の識別子 `key`

同梱の提供元は、毎年繰り返す祝日に `key`（`vernal-equinox`・`good-friday` など）を付けます。規則の `keys` は、この識別子で祝日を個別に指します。

- 春分・秋分の日、復活祭に連動する日、太陰暦の祝日は日付の規則では表現できません。`key` は規則から祝日を指すための API で、名前（データ）と違ってバージョンをまたいで変えません。日付の移動や公式の改名があっても、同じ祝日なら同じ `key` です
- 意味は「その日が観測している祝日」で、振替日は元の祝日の `key` です（「成人の日とその振替」を `keys` 1 つで書け、当日だけなら `kinds` で絞れる）。付与する対象は「法令・布告の区分として毎年繰り返し、`kind` では区別できない祝日」で、種別と同じ情報しか持たない日（日本の国民の休日）と一度きりの日には付けません
- 付け方: 初めて付与するときに `nameEn` から導出します（小文字に変換し、空白をハイフンに置き換え、アポストロフィ・先頭の冠詞・括弧書きを除き、末尾の "Day"・"bank holiday" を削除します。途中の冠詞は残します）。例外は `new-year`・`boxing-day`・`labour-day`・`national-day` です。導出は最初の 1 回だけで、以後 `nameEn` が変わっても `key` は変えません。利用者向けの正確な説明は `docs/providers.md`（英日）の 1 か所だけに書きます
- 検証は文字列の形式（`/^[a-z0-9][a-z0-9-]*$/`）だけです。同じ年に同じ `key` が複数回現れるのは正当です（分かれた振替休日、旧正月の 2 日）
- **誤った `key` の直し方**: `key` を変えると、利用者の `keys` の設定が黙って何にも一致しなくなります。そのため前のバージョンとの比較は `key` の変更で失敗にし、誤り（綴りの誤り・付ける範囲の誤り）を直すときは、旧い `key` を受け付ける期間を置いてマイナーバージョンで出します（手順は RELEASING.md の「区分」）。黙って直す案は、利用者が気付けないので取りません

### 26. 提供元を書くための関数（`bizdays-toolkit/provider`）

提供元を実装する利用者のために、復活祭（`easterSunday`）・月の第 n 曜日（`nthWeekdayOfMonth`）・振替の計算（`withSubstituteDays`）などを、サブパス `bizdays-toolkit/provider` で公開します。

- 同じ計算を 1 か所に置き、利用者に再実装させないためです。振替は「翌日も祝日ならさらに翌日」「同じ週末の 2 つの祝日」という連鎖を持ち、境界で誤りやすい部分です。サブパスに分けるのは、ルートのバンドルサイズに影響しないようにするためです
- 公開する関数は入力を検証します（内部の関数は検証済みの値を前提にするので、そのまま公開すると誤りが分かりにくい形で現れる）
- 振替の計算は「曜日 → 向き」の形で受けます。米国の連邦祝日のように向きが分かれる規則を 1 回の呼び出しで書けるためです。国に固有の規則（日本の国民の休日）は含めません
- 振替の定義: 入力を日付順に走査し、指定の曜日に当たる祝日ごとに、指定の向きで「入力された祝日でも、それまでに決めた振替日でも、指定の曜日でもない最初の日」を振替日として割り当てます（英国の附則では土曜日・日曜日の両方を飛ばすため、指定の曜日も飛ばします）。振替日自身は振替の対象になりません（どの国の法律にも振替の振替はありません）。振替日は元の祝日の `key`・`names`・`confirmed` を引き継ぎます（`names` は、名前を関数で変えたときも引き継ぎます）。`kind` は呼び出し側が指定し、名前を省略した場合は元の祝日の名前を使います（関数で変更できます）。週末の元の日を結果から除外することもできます（GOV.UK の一覧には週末の日が掲載されません）。振替日は前後の年に移ることがあります（12 月 31 日の振替日が翌年の 1 月 1 日になる場合と、`"previous"` で 1 月 1 日の振替日が前年の 12 月 31 日になる場合）。その場合に、提供元の `holidaysInYear` の契約（その年の日付だけを返す）とどう整合させるかは呼び出し側に委ね、文書に明記します
- 同梱の提供元の内部をこれらの関数で置き換えることを認めます。照合済みのコードを置き換えることへの懸念は、前のバージョンとの全年の比較（RELEASING.md の「品質の仕組みの理由」の「前のバージョンと比べる」）で払えるためです（条件は RELEASING.md の品質の確認の表）。公開する関数が同梱の提供元と同じ結果を出すことは、テストでも確かめています

## 国ごとのデータ

### 27. 祝日データの持ち方と、国の選び方

同梱の提供元は、規則で計算して公式データと全日分を照合することを基本にします。規則で計算できない国は、公式に告示された日付を年ごとの表で持ちます。

- 規則で計算する国（日本・英国・フランス）は、公式データが古い年を消していっても過去の年を返せます。照合のデータ（フィクスチャ）には出典を年ごとに記録します
- 年ごとの表で持つ国（シンガポール。太陰暦・イスラム暦・ヒンドゥー暦の祝日）は、表のある年だけを対応年にし、後の年は予測せず `out-of-range` にします。祝日が欠けた年を `confirmed: false` で返すのは危険なので、年単位でデータをすべて持つか、持たないかのどちらかにします。振替のように規則で決まる部分だけは計算します
- 出典を示さない民間のまとめサイトは、手がかりにはしても照合には使いません
- **正は公表された一覧（官報の告示・政府の公表）です。** 照合用の機械可読データが公表と食い違う場合は、公表を正とし、食い違いを出典付きの既知の差分としてフィクスチャに記録し、照合ではその差分だけを許します（既知の差分が消えたときも知らせる）。公表された一覧のない年は、法令と布告が正です
- 名前は公式データの綴りを写します（`name` は現地語、`nameEn` は公式の英語名か、ない場合はライブラリの英訳）
- 提供元は 1 日に 1 件を返します（24 番）。2 つの祝日が同じ日に当たる年（フランスの Ascension と 5 月 1 日など）は、照合対象の公式データに合わせて 1 件を選び、選ばなかったほうの祝日を `keys` で指しても当たらないことを文書に明記します
- 規則で計算する国の予測の年（日本の春分・秋分の日、英国の公表前の年）は `confirmed: false` です。年ごとの告示がない国（フランス）は、すべての年が `confirmed: true` で、`confirmedThrough` を持ちません
- **国を足すときの基準**: (1) 公式データと全日照合できること、(2) このライブラリの利用者が扱う国であること、(3) 実装・保守の負荷（規則で計算できるか、年ごとの告示があるか、振替の規則の複雑さ）。地域ごとに祝日が違う国は、地域ごとの提供元にします。4 か国目を選定した際に見送った候補: 香港（公式の JSON は 2023 年分までしか遡れず、それより前は官報での照合になり、太陰暦の祝日は年ごとの表になる。需要が示されれば表の提供元として足せる）、米国（連邦政府の公式な機械可読データがなく、州ごとの違いが大きい）、ドイツ（州ごとに祝日が違い、連邦の公式な機械可読データがない）。フランスは公式の JSON で約 26 年分を照合でき、規則で計算でき、振替も年ごとの告示もないので 3 条件をすべて満たしました。次の国を検討するときは、この比較を見直します。ID は ISO 3166 のコード、ない地域は同じ形の独自の ID（`FR-AM`）で、ISO でないことを文書に書きます。海外県のように祝日もタイムゾーンも違う地域は、需要が見えるまで同梱しません

### 28. 英国の提供元

英国の bank holidays は、地域ごとの 4 つの提供元（`england`・`wales`・`scotland`・`northernIreland`）です。対応年は 1974 年からです。

- 祝日は地域ごとに違うので、国全体の提供元や地域を引数で選ぶ提供元にはしません。England と Wales は、現時点では日付が同じでも、将来異なる日付になった場合に利用者のコードを変更せずに済むよう、別の提供元にします。複数の地域は和集合で使えます（コアに国と地域の親子関係は持たない）。Scotland の council ごとの休日は、照合できないので扱いません
- サブパスは `gb`（Northern Ireland を含まないと読まれる）ではなく `uk`、型の名前は `Uk…` です
- 規則は 1971 年の Banking and Financial Dealings Act の附則と毎年の布告で、布告による移動・臨時の祝日は表で持ちます。Good Friday と Christmas Day（法律上は慣習法上の休日）は、GOV.UK の一覧と同じく含め、種別も区別しません
- 正は、2012 年以降は GOV.UK の一覧、1998〜2011 年は当時の政府の公表一覧、それより前は附則と The Gazette の布告です（27 番の「公表された一覧が正」）。布告（法）を正にする案は取りません。営業日の用途では実務（その日に銀行が閉まったか）が正で、法形式の正しさだけでは日数計算が世間とずれるためです。振替日の割り当てが規則と違う年（2023 年の Scotland など）は公表に合わせます。週末に当たった祝日は、GOV.UK の流儀に合わせて結果に載せません。1974 年は、布告で全日を照合できる下限です
- 布告が見つからなかった日は `unverified` に記録し、規則どおりに返します。出典は `docs/sources/` に収集・記録してあります。過去の記録であるため毎日の監視対象にはせず、読み違いが見つかったときだけ修正します
- Wales の祝日は、GOV.UK のウェールズ語版の名称を `names.cy` に持ちます（`name` は GOV.UK の既定の表記の英語）
- 種別は GOV.UK の注記（`notes`）からは決めません（注記がそろっていないため）
- 臨時の祝日の名前: 布告は名前を持たないので、公式の文書（Hansard・官報の告示）の呼び方を日ごとに確かめて使います。固有の名前が公式の文書にない日は名前を作らず、中立の "Additional bank holiday" に政府が述べた理由を括弧で添えます（GOV.UK の "Early May bank holiday (VE day)" と同じ形）

### 29. 公式データの監視

日本（内閣府）・英国（GOV.UK）・シンガポール（data.gov.sg）・フランス（data.gouv.fr）の公式データを毎日照合し、差分があれば issue を立てます（`data-watch.yml`）。

- 英国の臨時の祝日は 10 日ほど前に発表されることがあり、年に 1 度の確認では間に合いません。日本でも、形式や文字コードの変更は手作業で確認するまで気付けないため、同じ起動で照合します
- 起動は外部の cron（cron-job.org）からの `workflow_dispatch` で、GitHub の schedule は予備です（schedule は遅れたり落ちたりし、このリポジトリでも動かなかった）。ワークフローが動いたことはハートビート（healthchecks.io）で確認し、「来るはずの知らせが来ない」ことで、どこで止まっても気付けます。ハートビートは、すべての照合が動いたときだけ送ります
- 外部に預けるトークンは、このリポジトリの Actions の Read and write だけに絞ります。漏れてもコードは変えられず、npm への公開には 2FA での承認が要ります
- 取得や解析の失敗も issue にします（監視が止まっても気付かない状態を防ぐ）。60 日動きのないリポジトリで定期実行が止まらないよう、実行のたびにワークフローを有効化し直します
- 判定の根拠は外部向けに公開された JSON・CSV で、公式リポジトリのファイル（内部の実装）は手がかりとして issue に添えるだけです。例外はウェールズ語の名称で、ほかに公式の機械可読な出典がないため、GOV.UK のリポジトリの翻訳ファイルで照合します
- 監視のワークフローはリポジトリにコミットしません。フィクスチャは照合テストの入力なので、人が確かめた規則の修正と同じコミットで更新します。照合の報告書の日付は日本時間です
- 退けた案: 主系の照合が成功した日に、予備の `schedule` が取得を省略する形。判定の要点は、`gh run list` でその日（期間）の `workflow_dispatch` の実行を見て、既定の入力で成功したものがあれば飛ばし、飛ばしたときはハートビートを送らない（比較をした実行が送っている）、失敗した実行しかない期間は予備が動く、というもの（0.30.7 の作業の途中で、週 1 回の結果の比較のために作った）。今の 1 日 2 回の取得で困っておらず、issue も内容が同じなら更新しないので重複しないため入れません。データ元から問い合わせを減らすよう求められたら入れます

## 診断

### 30. 規則の診断は例外を投げず、`code` で判定する

`diagnoseCalendar`・`diagnoseSchedule` は、作成時と同じ検証を行い、誤りや知らないキーを集めます。誤りがなければ規則どうしの関係を調べ、問題を配列で返します。

- 例外を投げないのは、すべての問題を一度に見られるようにするためです。テストでは `assert.deepEqual(diagnoseCalendar(options), [])` の 1 行で設定を守れます。設定の誤りは結果で返し、引数（第 2 引数）の誤りは例外です
- 判定は `code` で行い、`message` は API に含みません（3 番）。重さは `error`・`warning`・`info` です
- 結果は決定的です。現在時刻は使わず、終わった規則（`expired`）は基準日 `{ asOf }` を渡したときだけ返します。基準日は暦日の文字列だけです（設定の期間と同じ単位にそろえます）。終わりの日が基準日と同じ場合、その日までは有効なので `expired` ではありません。`"after-holiday"` の規則は、振替先が有効期間の終わりの日より後になることがあります（有効期間は振替元の日で判定します。13 番）。そのため、終わりの日の `MAX_HOLIDAY_RUN`（31）日後を、有効期間の終わりとみなします（安全側の扱いです。実際には振替がなかった規則も、終了から 31 日間は `expired` になりません）。自分の設定を基準に第 n 営業日を数える規則（16 番）がある場合、個別の日付と毎年の月日も数え方の基準に入ります。そのため、終わりの日が属する月の末日（月の規則）と、終わりの日の 6 日後（週の規則）のうち、遅いほうを有効期間の終わりとみなします（繰り返しの規則は基準に含まれないため、扱いは変えません）。判定では日数の比較だけを行い、祝日を参照しないので、基準日が対応年の範囲外でも `out-of-range` にはなりません。第 2 引数に含まれる知らないキーは無視します（8 番と同じ前方互換）
- 知らないキーの候補（「did you mean」）や長い説明は診断時だけ組み立てます。作成時は警告を使わないので、作成処理には含めず、ルートのバンドルを大きくしないためです
- 診断はサブパス（`bizdays-toolkit/diagnose`）に分けます。日本の祝日を使うと全日を調べるため数百ミリ秒から 1 秒ほど（規則が多いほど長い）かかる開発・テスト用の道具で、アプリの本体のバンドルに入らず、リクエストの処理で誤って呼ばれにくくするためです

### 31. 規則どうしの関係の診断（`shadowed`・`redundant` など）

規則どうしの関係は、`shadowed`（同じ種類の先の規則に完全に含まれ決して使われない）と `redundant`（取り除いても結果が変わらない）で知らせます。

- `shadowed` は同じ種類・同じ形の規則どうしに限り、包含で判定します（`kinds`・`keys`・`weekdays`・`months`・有効期間・周期・`holidayOverlapPolicy`・`skipWeekdays`・参照する `calendar`）。祝日に従属する規則は当てはまる日が年ごとの祝日で変わるので、曜日の規則との包含は調べません。種類をまたぐ関係は、判定の順番が固定されているため（11 番）、`redundant` として、実際に取り除いた場合の結果と比べて見つけます
- 日本の提供元だけの設定では、`kinds` の `"regular"` と旧名の `"national"` を、調べる期間に種別 `"national"` の祝日がなければ同じものとして比べます（10 番）
- `redundant` を `info` にするのは、説明のために意図して書いている場合があるためです
- `redundant` の走査の範囲は、提供元の対応年（長すぎれば 1900〜2099 年）、提供元がなければ 2001〜2028 年（年の種類が 28 年でそろう）です。周期のある規則があれば、周期と 28 年の最小公倍数まで広げ（上限 200 年）、範囲の外の有効期間も調べます
- 出た規則は、まとめて取り除いても結果が変わりません（逐次除去）。使われない規則（`shadowed`・`never-matches` など）を先に取り除き、`redundant` は 1 つずつ（毎年の月日と繰り返しの規則を配列の順に、次に個別の日付を）、それまでに出た規則を取り除いた設定で判定し、取り除いた規則があれば、ほかに取り除ける規則がなくなるまで繰り返します（配列の順に 1 回走査するだけでは、後の規則を外すと前の規則が外せるようになる形を取りこぼすため）。個別の日付も同じ走査に含めます（日付と規則が互いを根拠に両方出ると、まとめて取り除いたときに結果が変わりうるため。毎年の月日と繰り返しの規則は個別の日付を除いて判定するので、先に判定します）。結果は、配列の順の走査を固定点まで繰り返したものです。走査の順が決定的なので、結果も決定的です（30 番）。1 回の走査で 1 件以上取り除かなければ終わるので、走査の回数は候補（毎年の月日・繰り返しの規則・個別の日付）の数 + 1 を超えません（超えたら例外にして、作りの誤りを見張る）。報告は配列の順です
- 「その規則を 1 つだけ外したら」の判定（単独除去）は退けました。単独で取り除ける規則が 2 つあっても、両方を取り除くと結果が変わる場合があるためです。同じ規則を 2 つ書いた設定では、後が `shadowed`、前が `redundant` になり、両方を外すと結果が変わっていました。同じ曜日の `"under-holiday"`・`"over-holiday"`・`"after-holiday"` の 3 つの規則では、前の 2 つがそれぞれ単独では取り除けますが、両方を外すと祝日の月曜が変わります（`holidayPolicy: "ignore"` でも、祝日の日は `"over-holiday"` の規則が `"under-holiday"` の規則より先に当たるため）。利用者は出た規則を 1 つずつ外して診断をやり直す必要があり、オラクルの正解の定義（まとめて取り除ける）とも合いませんでした
- `redundant` の `relatedPath` は、取り除いたときに代わりに決める規則で、その規則が決めていた日をすべて 1 つの規則が決めるときだけ付けます（`shadowed` の `relatedPath` と同じ意味）。定休日の曜日や祝日の扱いが決める日があれば付けません（規則ではないため）。決めていた日がない規則にも付けません
- `redundant` は、その項目を取り除くと結果が変わりうる日を調べて判定します。通常は、その項目が結果を決めていた日が対象です。営業日カレンダーの繰り返しの規則（閉じる・開くの両方）に第 n 営業日の規則がある場合、個別の日付と毎年の月日は数え方を変えます（16 番）。そのため、それらが当てはまる日を含む月・週の全日を調べ、規則の判定基準にも個別の日付を残します（結果を決めていない個別の日付も、数え方を変えるためです）。スケジュールの第 n 営業日の規則は別のカレンダーで数えるため、対象外です
- 判定できない日は、取り除けるものとして判定しません。取り除く前と後の片方だけが判定できない日は結果が変わったとみなし、両方とも判定できない日は同じとみなします
- 当てはまる日がない規則は `never-matches`、第 n 営業日の数え方の限界は `counting-basis`、旧名は `deprecated-option` です。新しい種類の問題を見つけるようになるのはマイナーバージョンで、誤った診断を直すのは不具合修正です（33 番）
- オラクル（`test/diagnose-oracle.test.ts`）の完全性（出た項目をまとめて取り除いた設定で、まだ取り除いても結果が変わらない項目）は、診断が規則どうしを調べる期間で判定します。期間は、診断とオラクルが同じ関数（`rulesScanWindow`）で求めます。対応年だけで判定すると、有効期間が対応年の外まで続く規則を、誤って取り除けるものとして数えてしまうためです（0.30.7 で、報告されていた 2 件がこの形だった）
- 診断のオラクルの完全性で、理由が分かって受け入れる項目の一覧（`KNOWN_INCOMPLETE`）に項目を載せるときの手順は、RELEASING.md の「品質の確認」の「診断のオラクル」の行に書きます
- 判定できない月にかかわる規則（有効期間がその月に重なる規則）は、規則どうしの診断の前に決め、`never-matches`・`redundant` を出さず、逐次除去でも取り除きません。診断の後で消すと、ほかの規則が「消した規則を外した設定」で判定されたままになり、まとめて取り除ける約束が破れるためです
- 単位は「その日について、結果を確定できない規則があるか」です（規則が使う月単位ではありません。`redundant`・`never-matches` は、ほかの規則がその日を決めているかどうかに依存するためです）。判定できない日の集合 U は、基準カレンダーを持つ規則ごとに、規則自体を評価せずに基準を直接求めて決めます。月の規則では、有効期間 ∩ 窓のうち `months` に当てはまる月について、基準が例外を投げる月の全日を U に含めます。週の規則では、有効期間 ∩ 窓に 1 日でも含まれる週（`weekStart` で区切る）のうち、`months` に当てはまる日を含む週を対象にします。その週の 7 日が属する月のいずれかで基準が例外を投げる場合、その週の 7 日すべてを U に含めます。U はこれらの和集合です。規則 R が結果を確定できない規則となるのは、R の有効期間 ∩ 窓の日が U と交わる場合です。基準は繰り返しの規則に依存しないため、規則の並びや取り除く順序に左右されません。規則の形を変える場合（例: 月以外の絞り込み条件を追加する）は、この定義も見直します
- 規則の形を調べる代表の 28 年間（2001〜2028 年）は、U に含めません。第 n 営業日の規則の `shadowed` は形の包含（`setCovers`）で決まり、当てはまる日の印（`patternBits`）はどの診断も使わないので、第 n 営業日の規則では印を求めません（代表の 28 年間で基準を評価しない）。第 n 営業日の規則の印を使う診断を足すときは、ここを見直します
- 評価の途中で記録した月（0.31.0-A の `guardBases`）を目標にしないのは、それが評価の順に依存するためです（前の規則がある月の全日を決めていると、後の規則の基準はその月で評価されず、前の規則を取り除くと評価される）。U はその記録の上位集合なので、出る診断は記録だけで決めた場合と同じか少なく、少ないのは、前の規則に覆われていたために基準が評価されなかった日だけです。過剰に判定不能とすることは安全側の扱いなので、検出対象にしません。診断の後の確かめ（`dropUnsure`）は見張りとして残し、事前に判定不能としていなかった月で基準が例外を投げた場合と、判定できない規則についての診断が残った場合に作りの誤りとして例外にします（RELEASING.md の「品質の仕組みの理由」の「規則を 1 か所に書く」）。逐次除去の約束は判定できる日の結果についてのみで、元の設定で判定できなかった日は、規則を取り除いた後に判定できるようになっても比べません
- 限界: 週の第 n 営業日の規則で、窓の両端の週が窓の外（対応年の外）の月にまたぐ場合は、その週の 7 日すべてを判定できない日として扱い、有効期間がその週を含む規則の診断を出しません（安全側。有効期間を窓の端の週の手前までにすれば出る）。0.31.0 で、判定できない月とその前後の月（月の単位）から、日の単位に狭めました

## バージョンと互換性

### 32. バージョンの区分の理由

バージョンの区分（何をどのバージョンで出すか）は RELEASING.md の「区分」に書き、ここにはその理由と退けた案を書きます。

- 公式データの反映をパッチにするのは、`^`・`~` のどちらの利用者にも届けるためです。0.x では `^0.30.0` が 0.31.0 を受け取らないので、マイナーバージョンにすると臨時の祝日が必要な利用者に届かず、メジャーバージョンにすると古い祝日のまま動き続ける利用者が出ます。結果は変わりますが、「その日を正しく判定できていなかった」状態の修正です。年ごとの表で持つ提供元に告示済みの年を足すと、`out-of-range` だった日が結果を返すようになりますが、告示の反映として同じ扱いにします。規則で計算する提供元の対応年の拡大は、計算の範囲そのものを広げる機能の追加なのでマイナーバージョンです
- 1.0.0 以降、長く続いた挙動が文書と違うときは、直すのがコードとは限りません。公開後に複数のマイナーバージョンを経た挙動には、それに依存している利用者がいると考えます。そのうえで、文書どおりの結果を前提にした利用者と、現在の挙動を前提にした利用者のどちらに影響が及ぶかを踏まえ、コードを直す（パッチ）か、文書を挙動に合わせるか、挙動の変更としてマイナーバージョンで扱うかを決めます。決めた結果と理由を CHANGELOG に残すのは、後から「なぜ文書のほうを直したのか」を追えるようにするためです（規則は RELEASING.md の「区分」）。0.x でこの 3 択を使わないのは、まだ利用者が少なく、約束どおりに直すほうが後の利用者を守るためです
- 不具合の修正（RELEASING.md の用語）を区分の表のパッチの行に置くのは、約束どおりの結果を前提にした利用者には影響がなく、修正を利用者に届けるためです。入ったバージョンや先送りの有無で区分を変えないのも同じ理由です。そろっていない結果を不具合に含めるのは、文書が決めていないことを理由に直せないと、同じ種類の誤りを `code` で受けるコードが呼び出しごとに漏れ続けるためです（3 番のクラスと同じ理由）。退けた案: 直前のバージョンで入った退行だけをパッチにする（古い不具合の修正が 0.x では `^` の利用者に届かない）。先送りした項目がある間のパッチを公式データと退行の修正だけにする（0.31.1 の後に、型の説明から外れていた年の `code` の修正を出せなくなった。先送りは次のマイナーバージョンの範囲を固定するための決まりで、修正を届けるのを遅らせる理由にならない）
- 黙って通っていた呼び出しを止める変更（6 番）を区分の表の 2 行目に置くのは、利用者の作業が要るためです。約束していた例外が出ていなかった不具合の修正を不具合の修正の行に置くのは、向きで区分を変えると「投げなくする修正」だけが先に届き、約束どおりに直すのが後回しになるためです
- 性能・サイズの改善をパッチにするのは、利用者に見える変化がないためです

### 33. 互換性の約束の理由

約束の一覧は、README から参照される利用者向けの約束として RELEASING.md の「互換性の約束」に書き、ここにはその理由を書きます。

- 列挙の値・返す項目・省略可能な設定が増えることを約束に含めるのは、機能を足すたびにメジャーバージョンにしないためです。利用者には「その他」の分岐で受けてもらいます（2 番）
- メッセージを約束に含めないのは、判定を `code` で行い、文言を改善できるようにするためです（3 番）
- 診断の結果が「増えるだけ」であるとは約束しません。誤った警告を直せなくなるためで、誤った診断を直したときは前のバージョンの結果が消えることがあります
- 削除の前に非推奨の期間を置くのは、利用者が書き換える時間を取るためです。1.0.0 の前に同じ情報の経路を減らすため、モジュールの定数（`dataVersion`・`confirmedThrough`）と国ごとの変換関数（7 番）を非推奨にしました
- 新しい機能を `@beta` で出すことがあるのは、使われ方が固まる前に形を変えられるようにするためです

### 38. 文書の構成: README は入口、詳しい説明はガイド

README（英語）は、npm で見つけた人のための入口です。導入を決めて設定を書く人には `docs/guide.md`、提供元を書く人には `docs/providers.md`、バージョンを移行する人には `docs/migration.md`、設計の理由にはこの文書を用意します。

- 節の数ではなく読者の種類で文書を切ります。README には、機能の要約・インストール方法・動作確認済みの環境・短いクイックスタート・できることの一覧とガイドへのリンク・バージョンの付け方・出典・ライセンスを置きます
- 英語を既定にし、日本語版（`docs/README.ja.md`・`docs/guide.ja.md`・`docs/providers.ja.md`）も、英語版と内容の分量をそろえて用意します。npm に公開するのは英語の README だけで（パッケージのルートの `README*` は必ず含まれるので、日本語版は `docs/` に置く）、英語の README からのリンクは GitHub の絶対 URL、GitHub でしか読まれない日本語版の中のリンクは相対リンクです。型の説明（TSDoc）・RELEASING.md・この文書は日本語です。CHANGELOG は 0.31.0 から英語です（0.30.9 以前のバージョンの節は日本語のまま）
- 移行ガイドには、マイナーバージョンの間を移るときの作業をバージョンごとにまとめ、CHANGELOG の各マイナーバージョンにも「Migration」の小見出し（0.30.x 以前のバージョンの見出しも 0.31.0 で「移行」から置き換えた）を置きます。複数のバージョンを飛ばして移行する利用者が、CHANGELOG を順に追わずに済むようにするためです
- 折りたたみ表示やドキュメントサイトは採用しません（npm での描画がバージョンで変わる、規模に対して重い）。利用者が読む文書の種類が 3〜4 種類を超えたら、改めて考えます
- 品質の仕組みの変更（公開物の変わらない変更）は、CHANGELOG ではなく開発の記録（docs/development-log.md、日本語）に 1 項目 1 行で書き、経緯・退けた案・測定の詳細はコミットメッセージか PR に書きます。CHANGELOG は利用者がバージョンの間の差を知るためのもので、0.31.0 から英語で書きます（RELEASING.md の「記録の書き分け」）
