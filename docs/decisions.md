# 設計上の決定

「なぜこうなっているのか」を後から迷わないための記録です。変えないと決めたことも、理由と一緒に残します。

## 1. 日付は単なる文字列型（ブランド型にしない）

`DateString` は `string` の別名で、`"YYYY-MM-DD"` 以外の文字列も型の上では受け付けます。

- ブランド型（`string & { __brand: "DateString" }`）にすると型の安全性は上がりますが、利用者が日付を渡すたびに型変換や検証関数を挟む必要が出ます
- 入力はすべて実行時に検証し、誤りは `code: "invalid-date"` の例外になるので、使いやすさを優先します

## 2. 出力の列挙は「開いた型」

`DayReason`・`ScheduleReason`・`JapaneseHolidayKind`・`ErrorCode` は、既知の値の型（`Known…`）と `string & {}` の組です。

- 新しい値をマイナー版で足しても、利用者のコードがコンパイルエラーにならないようにするためです（値を列挙して分岐しているコードは「その他」の分岐で受けます）
- すべての値を網羅したことを型で確かめたい利用者は `Known…` を使えます。その場合、値が増えたときに型エラーで気付くことを利用者自身が選んだことになります
- ライブラリの内部では `Known…` で分岐し、対応漏れを型で検出します

（0.30.0 で追記: `KnownDayReason` の `"regular"` を `"default"` に、`createCalendarFromSchedule` の曜日の値で営業日になる日を `"open-weekday"` に改めた。`"regular"` は祝日の種別（`Holiday.kind`）の語で、一義一語（54 番の N1）に反していたため）

## 3. 例外は従来のクラスのまま、`code` を持つ

例外は `RangeError`・`TypeError`・`Error` のインスタンスで、`code` プロパティを持ちます。`isBizdaysError()` で、このライブラリの例外かを判定できます。

- 独自の例外クラスにすると、`instanceof RangeError` で判定している既存のコードが壊れるため、従来のクラスに `code` を足す形にしました
- メッセージの文言は API に含みません。判定には `code` を使います

## 4. 設定の知らないキーは、作成時に無視する

`createCalendar`・`createSchedule` は、設定の知らないキーで例外を投げません。

- 将来の版で足した設定を古い版に渡しても壊れないようにするためです（前方互換）
- 打ち間違いは TypeScript では型エラーになります。JavaScript から使う場合のために、内部で警告として記録しており、規則の診断（`diagnoseCalendar`・`diagnoseSchedule`）で検出できます（15 番）
- 無視するのは「知らないキー」だけです。知っているキーの無効な組み合わせ（`{ dayAfterHoliday: true, onHolidayRule: "over-holiday" }`・`{ day: 1, interval: 2 }` など）は、設定の意図を読み違えないよう作成時に例外にします（33 番・35 番）。前方互換のための無視と、矛盾の検出は別の目的です

（0.30.0 で追記: 0.30.0 で改名した旧名は、知らないキーではなく知っているキーとして扱う。0.30.x の間は新しい名前に読み替えて `deprecated-option` を記録し、1.0.0 以降は `invalid-option` を投げる（改名の表 `src/core/renamed.ts` は残す））

## 5. 設定は作る時点で取り込み、返すものは変更できない

設定の配列やオブジェクトは作る時点で複製し、返すオブジェクト・配列はすべて `Object.freeze` します。

- 作ったあとに利用者が元の設定を書き換えても結果が変わらないようにし、共有されたカレンダーを誤って書き換えることも防ぎます
- スケジュールの値（`T`）そのものは複製しません。値をあとから書き換えないことは利用者に任せます

## 6. 祝日の提供元が返したデータを検証する

`HolidayProvider` が返した祝日は、年ごとに初めて使うときに検証し、契約の項目（`date`・`name`・`nameEn`・`kind`・`confirmed`。0.7.0 から `names`、7 番）だけを持つ変更できないオブジェクトにします。

- 利用者が実装した提供元の誤り（日付の形式、別の年の日付、重複など）で、判定が黙って狂うのを防ぐためです
- 検証は年ごとに 1 回なので、判定の速さにはほぼ影響しません

（0.21.3 で追記: 0.18.0 から契約の項目に `key` も加わりました。検証するのは文字列の形式だけです。46 番）

## 7. 祝日の名前は `name`（現地語）と `nameEn`、ほかの言語は `names`

ほかの言語の名称は、省略可能な `names`（キーは BCP 47 の言語タグの正規の形）で持ちます（0.7.0）。既存の項目は残します。

- 同梱の日本の祝日には `names` を付けません。日本の祝日の名称は内閣府のデータで照合していますが、ほかの言語の名称には同じ水準の公式の出典がないためです。出典のない翻訳を同梱すると、照合済みのデータと品質がそろいません
- 同梱の英国の祝日では、Wales の提供元だけがウェールズ語の名称（`names.cy`）を持ちます。GOV.UK のウェールズ語版という公式の出典があり、照合できるためです（21 番）
- 利用者が実装した提供元（または同梱の提供元を包んだもの）が `names` を付ければ、契約の項目として検証・複製・凍結して返します（6 番）。言語タグは正規の形（`"zh-Hant"`。`"zh-hant"` は不可）に限り、同じ言語が別の書き方で重複しないようにしています
- どの言語を表示に使うか（フォールバックの順序）は、ライブラリでは決めません

## 8. 型引数 `Kind`（祝日の種別）は残す

`Calendar<Kind>`・`Schedule<T, Kind>` の `Kind` は、日本の祝日で `kind` の補完が効く利点があります。既定値（`string`）があるので、使わない利用者の負担はありません。

## 9. 実行時に外部からデータを取り込まない

祝日データはパッケージに含め、実行時にネットワークから取得する機能は持ちません。

- 取り込むデータの改ざんや取得の失敗が、判定の正しさに直結するためです。法改正への対応は版の公開（staged publishing・provenance 付き）で行います
- どうしても必要な利用者は、`HolidayProvider` を自分で実装できます

## 10. 品質の仕組みに新しい依存を足さない

サイズの検査は minify せずに gzip で測り、API のスナップショットは TypeScript のコンパイラー API で作り、性質のテストの乱数は自前で実装しています。

- 開発用の依存が増えるほど、供給チェーンの管理（熟成ゲート）の対象が増えるためです
- 例外として、ワークフローの検査に actionlint を CI でだけ使います。ワークフローの誤り（ジョブの `env` で `runner` コンテキストを参照するなど）は `pnpm check` でも CI のテストでも見つからず、GitHub に読み込まれて初めて分かります。0.8.0 の準備中に監視のワークフローが読み込めない誤りを main に入れてしまったため、確実に止めることを優先しました。npm の依存にはせず、版と SHA-256 を固定した公式のリリースのバイナリを取得し、手元の環境にも入れません

（0.21.3 で追記: 同じ考え方で、CI でだけ使う道具をほかにも取得しています。いずれも npm の依存にせず、版と SHA-256 を固定した公式のリリースを使います。workerd（26 番）、利用者の型チェックの TypeScript 5.0・5.5・5.8・7.0（38 番）、Bun・Deno（43 番）です。README のサイズの値を測る esbuild は CI でも使わず、手元で一時的に入れて測ります（27 番・RELEASING.md）。actionlint だけを例外として挙げていたのは、0.8.0 の時点の記述です）

## 11. lint は oxlint で、規則は絞って有効にする

lint には、整形の oxfmt と同じプロジェクト（oxc）の oxlint を使います。

- インストール時に実行するスクリプトがなく、依存は各 OS 向けのバイナリだけなので、供給チェーンの管理の手間がほとんど増えません。ESLint と typescript-eslint は依存のパッケージが多く、強みである型情報を使った規則（Promise の扱いの誤りなど）も、非同期の処理がないこのライブラリでは出番が少ないため見送りました
- 規則は「正しさ」の分類を基本に、意味のある規則だけを個別に足します。好みに関わる分類（style・pedantic）は、指摘の大半が書き方の好みで雑音になるため有効にしません
- `unicorn/no-array-sort`（`toSorted()` を使え）は、`toSorted()` が出力の対象（ES2022）より新しい機能のため採用しません

## 12. 判定の順番は固定し、繰り返しの規則と祝日の関係だけを規則ごとに選ばせる

判定の順番（個別の日付 → 毎年の月日 → 繰り返しの規則（祝日の上）→ 祝日 → 繰り返しの規則（祝日の下・振替先）→ 曜日）は固定で、利用者が全体を並べ替える設定は持ちません。

- 全体を並べ替えられると、同じ設定でもカレンダーごとに意味が変わり、判定が予測しにくくなります。規則の診断で「決して使われない規則」を見つけることも、順番の組み合わせごとに必要になります
- 個別の日付や毎年の月日が祝日より優先されるのは、どの業種でも共通です。店舗によって分かれるのは「繰り返しの規則が祝日に当たったとき」だけなので、そこだけを規則ごとの `onHolidayRule` で選べるようにしました
- `onHolidayRule` の値は真偽値にしていません。3 つの状態（祝日の下・祝日の上・祝日の後に振替）があり、真偽値ではどちら向きかも読み取りにくいためです。値は「祝日に対して規則がどこに来るか」という同じ観点の言葉（`"under-holiday"`・`"over-holiday"`・`"after-holiday"`）にそろえています

ガイドの「Business-day calendars」は、この順番を 1〜8 の番号で示しています。個別の日付を臨時営業日（1）と臨時休業日（2）に分け、毎年の月日（3）、繰り返しの規則（祝日の上）と祝日の規則（4）、祝日（5）、繰り返しの規則（祝日の下・振替先）（6）、曜日（7）、それ以外（8）です。ほかの番号で「12 番の n」と書くときは、この番号を指します（0.21.3 で明記）。

（0.30.0 で追記: 規則ごとの選択 `onHolidayRule` を `holidayOverlapPolicy` に改名した（N5: 選択肢の項目は `Policy` で終える）。状態の数は変えていない）

## 13. 「第 n 何曜日」は、その月で n 回目のその曜日

`{ weekday: 3, nth: 3 }` は、その月で 3 回目の水曜日（15〜21 日の水曜日）です。

- 業種によっては「カレンダーの第 3 週の行にある水曜日」の意味で使うことがあり、月初の曜日によって結果がずれます。曖昧さをなくすため、回数で数える定義に固定し、ガイドに明記しています（0.17.1 までは README。45 番）
- その月にない日（`nth: 5` がない月、`day: 31` がない月）は当てはまりません。末日に読み替える便利さより、書いたとおりに当てはまることを優先しました（末日は `day: -1` で指定します）。読み替えないのは繰り返しの規則だけで、期日（`dueDate`）と締め日（`closingMonth`）は同じ `DayOfMonth` を受け取っても末日に読み替えます（16 番）
- 「隔週」は第 n 曜日では表せない（月の長さが一定でないため、`nth` のどの組み合わせでも周期 14 日にならない）ので、別の書き方 `interval`・`anchor` で表します（30 番）

## 14. 振替先は「その日以降で最初の祝日でない日」

`onHolidayRule: "after-holiday"` の規則は、祝日には当てはめず、その日以降で最初の祝日でない日に当てはめます。

- 振替の判断に使う「祝日」は祝日の提供元の祝日だけで、毎年の休業日などは含みません。利用者の休業日の設定によって振替先が変わると、設定の影響が読み取りにくくなるためです
- 振替先は、繰り返しの規則と同じ段階で判定します。その日に個別の日付や毎年の月日の規則があれば、そちらが優先です
- 「翌平日」という言葉は土曜日を含まないこともありますが、このライブラリでは「祝日でない日」とし、土曜日も振替先になりえます。振替先を変える設定は規則にないので、土曜日を避けたい場合は、その回を個別の日付（`openDates`・`closedDates`）で上書きします（土曜日が定休日なら、結果は同じです）。年ごとの列挙は 33・41 番が規則の代わりとしては退けている形ですが、振替先が土曜日に落ちるのは月曜日から金曜日までがすべて祝日のときに限られ（年に 0〜1 回）、規則ではなく列挙で足りると判断しています。規則自身に飛ばす曜日を書く設定は、需要が見えるまで足しません
- 規則に有効期間（30 番）があるときは、振替元の日（規則が本来当てはまる祝日）で期間を判定します。振替先が期間の外に出ても振り替えます。「規則が当てはまるか」を本来の日で決める、という振替の考え方と同じにするためです

（0.19.0 で追記: 規則自身に飛ばす曜日を書く設定 `skipWeekdays` を、毎年必ず起きる需要（創立記念日の就業規則）が示されたので足しました。47 番。`skipWeekdays` のない規則の振替先はこの番号のとおりです）

（0.22.1 で追記: 上の「年に 0〜1 回」は月曜日の規則の場合です。金曜日の規則では、金曜日が祝日のたびに土曜日に振り替わります（日本の祝日で 2028 年は 5 回）。README・ガイドはこの振替を「翌平日」「next weekday」と書いていたので、「次の祝日でない日（土曜日のこともある）」に改め、言葉どおりの翌平日は `skipWeekdays: [6]` で書けると示しました）

## 15. 規則の診断は例外を投げず、code で判定する

`diagnoseCalendar`・`diagnoseSchedule` は、作成時と同じ検証（内部の `IssueCollector`）で誤りと知らないキーを集め、誤りがなければ規則どうしの関係を調べて、問題の配列を返します。

- 例外を投げないのは、すべての問題を一度に見られるようにするためです（作成時は最初の誤りで止まります）。テストでは `assert.deepEqual(diagnoseCalendar(options), [])` の 1 行で設定を守れます
- `message` は英語で、API に含みません。判定は `code` で行います（例外と同じ扱い）。`code` は出力の列挙なので「開いた型」です。重さ（`severity`）は `"error"`・`"warning"`・`"info"` の 3 段階から増やさないため、例外的に閉じた型にしています（利用者が網羅的に分岐できるほうが役に立つため）
- `shadowed` は同じ種類の規則どうしに限ります。判定の順番が固定（12 番）なので、種類をまたぐ関係は「取り除いても結果が変わらない」（`redundant`）として、実際に取り除いた結果と比べて見つけます。種類をまたいで「覆っている規則」を 1 つに決めることはできないため、`redundant` には `relatedPath` を付けません
- `redundant` を `info` にしているのは、意図して書いている場合があるためです（定休日の曜日と同じ繰り返しの規則を、説明のために名前付きで書くなど）
- 毎年の月日・繰り返しの規則は無限に続くので、`redundant` は祝日の提供元の対応年（長すぎる場合は 1900〜2099 年に絞る）を、提供元がなければ 2001〜2028 年を 1 日ずつ調べます。繰り返しの規則の当てはまり方は、年の種類（1 月 1 日の曜日 × うるう年か）の 14 通りで決まり、28 年でそろうためです。ただし周期（`interval`）のある規則は別で、28 年（10,227 日）が 7 × interval 日の倍数とは限らない（隔週の位相は 28 年後に反転する）ので、周期と 28 年の最小公倍数（隔週なら 56 年。上限 200 年）まで広げます。規則の有効期間が調べる範囲の外にあれば、その期間（期限のない側は周期の長さ）も加えます（対応年の外で例外になる設定では加えません）。固定の範囲だけでは、範囲の外にある期間の規則を「使われない」と誤診するためです（30 番）
- 知らないキーの候補（「did you mean」）は診断のときだけ計算します。作成時は警告を使わないので、編集距離の計算をルートのバンドルに入れないためです
- 診断はサブパス（`bizdays-toolkit/diagnose`）に分けています。開発・テスト用の道具で、日本の祝日を使うと全日を調べるため数百ミリ秒かかります。アプリの本体のバンドルに入らず、リクエストの処理で誤って呼ばれにくくするためです

（0.22.0 で追記: 走査の範囲を周期に合わせて広げる扱いは、日単位の周期の規則（`cycle`）にも当てます。53 番）

## 16. 日付の調整は方法を必ず指定し、「最も近い営業日」は入れない

`adjust`・`dueDate` の `convention` は必須で、既定値を持ちません。方法は金融で使われる 4 つ（following・preceding・modified-following・modified-preceding）です。

- 支払期日が休業日のとき翌営業日にするか前営業日にするかは、契約や業種で決まります。既定値があると、決めずに使って誤った期日を出すことになるため、必ず書かせます
- 「最も近い営業日」（nearest）は入れません。前後が同じ距離のときの決め方が業種ごとに違い、どちらに決めても誤用を招くためです
- 月が変わるか（modified-…）は、調整する前の日付の月と比べます。`dueDate` では末日に読み替えた後の日付です。同じ月に反対向きの営業日もないときは、月が変わっても元の向きに調整します（例外にすると、その月が全部休業日の設定で期日が求められなくなるため）
- `dueDate` の `day` はその月にない日を末日に読み替えますが、繰り返しの規則（13 番）は読み替えません。期日は「その月のどこか」に必ず決まる必要がある一方、休業日の規則は書いたとおりに当てはまることを優先するためです。締め日（`closingMonth`）も同じ理由で読み替えます（締め日はその月のどこかに必ず決まる必要があります）
- 月は `"YYYY-MM"` の文字列（`MonthString`）で表します。日付と同じく、ブランド型にはしません（1 番）

## 17. 英国は地域ごとに提供元を分け、England と Wales も分ける

英国の bank holidays は、`bizdays-toolkit/uk` の `england`・`wales`・`scotland`・`northernIreland` の 4 つの提供元です。国全体の提供元や、地域を引数で選ぶ 1 つの提供元にはしていません。

- 英国の bank holidays は地域ごとに異なり、住民は自分の地域に誇りを持っています。地域をはっきり分けて選べるようにしておかないと、ライブラリとして無用な批判を受けかねません
- GOV.UK では England と Wales が 1 つの区分（England and Wales）ですが、別の提供元にしています。日付は現在同じですが、Wales では聖デイヴィッドの日を祝日にする要望が繰り返し出ており、将来分かれても利用者のコードを変えずに済むようにするためです
- ID は ISO 3166-2 のコード（`GB-ENG`・`GB-WLS`・`GB-SCT`・`GB-NIR`）です。地域ごとに完結した祝日の一覧を返すので、コアに国と地域の親子関係は持たせていません。複数の地域にまたがる場合は、和集合（`holidays` に配列で渡す）で使えます
- サブパスは ISO 3166-1 の `gb` ではなく `uk` にしています。`gb` は Great Britain（Northern Ireland を含まない）と読まれるためです。型の名前も同じ理由で `British…` ではなく `Uk…` にしています
- Scotland の地域（council）ごとの休日は扱いません。GOV.UK のデータになく、照合できないためです

（0.30.0 で追記: 日本の型の名前を、ほかの国と同じ略号の流儀（`JpHoliday`・`KnownJpHolidayKind` など）に揃えた（N7））

## 18. 英国の祝日は規則で計算し、GOV.UK のデータで 2012 年から全日照合する

英国の祝日は、1971 年の Banking and Financial Dealings Act の附則と毎年の布告で定まる規則で計算し、布告による移動・臨時の祝日はテーブル（`src/uk/rules.ts` の `MOVED`・`SPECIAL_DAYS`）で持ちます。対応年は 2012 年からです。

- GOV.UK の JSON は古い年が消えていく（2026 年 10 月時点で 2019 年から）ため、データをそのまま同梱せず、日本と同じく規則で計算して公式データで照合する形にしています
- 照合のデータ（`test/fixtures/govuk-bank-holidays.json`）は、2019 年以降が GOV.UK の現在のデータ、2012〜2018 年が GOV.UK の公式リポジトリ（alphagov/calendars・alphagov/frontend）の履歴で、その年が含まれていた最後の版です。年ごとの出典を `years` に記録しています。GOV.UK のデータは Open Government Licence v3.0 で、保存・再配布が認められています（README の出典に帰属表示）
- 2012 年より前は、一覧として機械的に照合できる公式のデータがありません。民間のまとめサイトは手がかりにはなりますが、出典が示されていないため照合には使いません。過去に広げる場合は、布告（The Gazette）で年ごとに確かめた年から足します（対応年の拡大は非破壊）
- England and Wales・Northern Ireland の Good Friday と Christmas Day は、法律上は bank holiday ではなく慣習法上の休日ですが、GOV.UK の一覧と同じく含め、種別も区別しません
- 振替は「土曜日・日曜日に当たる固定日の祝日を、日付順に、その後で最も近い祝日でない平日へ」割り当てます。2023 年の Scotland だけは、GOV.UK が振替の日付は同じまま、どちらの祝日の振替かを附則と逆に割り当てているので、照合の対象である GOV.UK の表記に合わせています（`RENAMED`）
- 種別（`kind`）は GOV.UK の注記（`notes`）からは決めません。注記がそろっていないためです（2012 年の Spring bank holiday の移動を England and Wales・Scotland では「Substitute day」としているが Northern Ireland には注記がない、臨時の祝日の「Extra bank holiday」も 2012 年だけ）。テストでは、注記の「Substitute day」と種別 `"substitute"` が、この 2012 年の 2 件を除いて一致することを確かめています

（0.21.0 で追記: 対応年は 1974 年からになりました。GOV.UK のデータがない年の正の決め方は 49 番です。この番号の「GOV.UK のデータで全日照合する」は 2012 年以降について変わりません）

## 19. GOV.UK との差分を毎日監視し、フィクスチャは人が確かめた修正と一緒に更新する

`.github/workflows/govuk-watch.yml`（0.17.0 で `data-watch.yml` に改名。44 番）が毎日 GOV.UK と照合し、差分があれば issue を立てます。ワークフローはリポジトリにコミットしません。

- 英国の臨時の祝日は、10 日ほど前に発表されることがあります（2022 年の国葬）。年に 1 度の確認では間に合わないため、毎日確かめます
- 判定の根拠は、外部向けに公開されている GOV.UK の JSON です。GOV.UK の公式リポジトリのファイルは内部の実装で、置き場所の移動（calendars から frontend）や形式の変更（名称の翻訳キー化）が実際にあったため、変更の理由の手がかりとして issue に添えるだけにしています。ウェールズ語の名称だけは、ほかに公式の機械可読な出典がないため、リポジトリの翻訳ファイルを照合に使います
- フィクスチャは照合テストの入力なので、データだけを先に更新すると main のテストが失敗します。規則の修正と同じコミットで更新し、履歴には意味のある変更だけが残るようにしています（`--write` は内容が変わった年だけ出典を書き換えます）
- 取得や解析に失敗した場合も issue を立てます。黙って監視が止まるのを防ぐためです。同じ理由で、60 日間動きのないリポジトリで GitHub が定期実行を止めないよう、実行のたびにワークフローを有効化し直します。起動のしかたと、監視が動かなかったことに気付く仕組みは 28 番

## 22. README は英語を既定にし、日本語版はパッケージに含めない

## 23. Node.js の対応は engines で示し、確かめる版を CI で決める

`engines` は `">=22.12"` です。README には、CI で確かめている版（22.12・22・24・26）を書きます。

- 下限の 22.12 は、ESM を `require()` で読み込む機能が既定で有効になった版です。`require()` で読み込めることも CI で確かめています。22.12 では、この読み込みに実験的な機能の警告（ExperimentalWarning）が出ます（26 では出ない）。結果には影響しないので、README で知らせるだけにしています
- 確かめる版: `check` ジョブで 22 系と 24 系の固定版（テストのすべて）、`compat` ジョブで下限の 22.12.0 と 26 系（公開する `dist` の ESM・CommonJS での読み込みと主要な関数）。22.12.0 と 26 系では、テスト（`.ts` の直接実行。型の除去が既定になったのは 22.18）と npm 12（動作要件 `^22.22.2 || ^24.15.0`）が動かないため、ビルドは Node.js 24 で行い、Node.js を切り替えて `dist` だけを確かめます。依存がゼロなので、`dist` だけで確かめられます
- 対象にする系列: LTS の系列と、LTS 入りを控えた系列です。サポートが終了した系列（23・25）は確かめません。新しい系列は LTS に入る時点で `compat` に足します（2027 年からは毎年 4 月に新しい系列が出て、10 月に LTS に入る）
- `engines` を「確かめた版」に狭めることはしません。pnpm の `engine-strict` を使う利用者が、確かめていない版で入れられなくなり、それ自体が互換性を壊すためです。「動くはずの範囲」（`engines`）と「確かめている範囲」（README と CI）を分けて示します。サポートを打ち切る（下限を上げる）のはメジャー版です（RELEASING.md）

## 24. Node.js の警告は失敗として扱い、直す

自前のスクリプト（`scripts/`）とテストで Node.js の警告（非推奨の API・実験的な機能など）が出たら、終了コードを 1 にします（`scripts/strict-warnings.ts`。スクリプトは先頭で import し、テストは `node --import` で読み込む）。どの環境でも同じです。

- 警告は合格のまま通るため、見落とされます。Windows で `npm.cmd` をシェルと引数の配列で起動したときの非推奨の警告（DEP0190）は、手元の出力をたまたま読んで気付きました
- 警告のイベントは非同期に届くので、同期的に `process.exit` するスクリプトでも見落とさないよう、`process.emitWarning` の呼び出しそのものを記録します（Node.js 自身の警告もこの関数を通ります）
- 公開物の互換性の確認（`test/compat`）は対象にしません。利用者の環境で動くかを確かめるもので、Node.js 22.12 の `require()` の実験的な機能の警告は利用者にとって問題ではないためです（23 番）
- Windows の CI は置きません。`dist` はどの OS でも同じに動き、開発用のスクリプトの Windows での問題は、コミットの前に手元（Windows）で通す `pnpm check` がこの仕組みで止めるためです

## 25. 開発用のツールの版を pnpm check で確かめる

`pnpm check` は最初に `scripts/check-toolchain.ts` で、ツールの版を確かめます。

- 固定版でない npm（10）で検査を試して、npm 12 での出力の形の違いを見落としたことがあります。手元と CI の版が違っていたこともあります。どちらも、版を比べれば機械的に分かります
- 確かめること: ワークフローどうしで同じ系列の Node.js の版がそろっていること（`ci.yml` の `check` の行列が基準。版を上げるときの書き換え漏れを防ぐ）、`compat` の行列に engines の下限が入っていること、実行している Node.js・npm・pnpm が固定版と同じこと
- 固定版との違いは、CI ではエラー、手元では注意の表示だけにします。熟成ゲートや別の作業の都合で、手元を先に変えることがあるためです。RELEASING.md の「手元と CI で同じ版を使う」に戻すまでの間も、作業を止めないようにしています
- スクリプトから起動する npm は、Windows でも `cmd.exe` から `npm.cmd` を直接呼ぶので、PowerShell の関数として定義された Safe Chain を通りません。スクリプトからレジストリに接続する npm の操作（`install` など）はしません

## 26. 公開物をブラウザーと Cloudflare Workers でも確かめる

公開する `dist` を、Node.js に加えて Chrome・Firefox・Edge（ubuntu のランナー）、Safari（macOS のランナー）、Cloudflare Workers の実行環境 workerd で確かめます。確認の中身は `test/compat/smoke.mjs` の 1 つで、Node.js・ブラウザー・workerd が同じものを呼びます。

- README に「ブラウザー・エッジランタイムで動く」と書いていましたが、確かめていませんでした。ソースが標準の JavaScript と `Intl` だけで書かれていることは `pnpm check` で確かめ（`src` が `node:` のモジュール・`process`・`Buffer` などを使わない）、実際の動作は CI で確かめます
- 新しい npm の依存は足しません。ブラウザーはランナーに入っているドライバーを WebDriver（HTTP）で操作し（`scripts/test-browsers.ts`。Node.js の `fetch` だけ）、workerd は版と SHA-256 を固定した公式のリリースを取得します（`scripts/test-workerd.ts`）
- ブラウザーの版は固定できません。ランナーのイメージの更新で変わるので、「その時点の最新の安定版」で確かめています（README にもそう書く）
- ブラウザーの側が一時的に止まることがあります（ランナー上の Edge がページの読み込みで応答しなくなった例がある）。結果を受け取る前の段階で止まったときだけ 1 回やり直し、ログに `RETRY` と理由を出します。確認の結果が FAIL のときはやり直しません。本物の失敗を、やり直しで隠さないためです。Edge は 1 回目が止まることが続いたため、起動オプションに `--disable-dev-shm-usage`（共有メモリの代わりに一時ファイルを使う）と `--disable-gpu` を足しています（CI のコンテナでレンダラーが応答しなくなる原因としてよく知られる 2 つへの対策。効いたかは `RETRY` の有無で見る）
- エッジランタイムは Cloudflare Workers だけにしました。workerd は Cloudflare が本番で動かしているのと同じコードで、Deno のチームも Cloudflare に加わって workerd との統合を進めています（2026 年 10 月）。Vercel の Edge Runtime を確かめるには npm の依存（`edge-runtime`）が要るので、確かめません。確かめていない環境は README に書きます
- 本物の Temporal を持つ環境では、Temporal のオブジェクトを入力にした確認も行い、持たない環境では飛ばしたことをログに出します（黙って飛ばすと、確かめたように見えるため）
- 0.16.0 から Bun と Deno でも確かめます（43 番）。workerd と同じく、版と SHA-256 を固定した公式のリリースを取得し、`test/compat/runtime.mjs` から同じ `smoke.mjs` を呼びます。Deno は `--unstable-temporal` で本物の Temporal も確かめます。Vercel の Edge Runtime を確かめない理由は変わりません

## 27. README のコード例を pnpm check で実行する

`pnpm check` は README と `docs/guide`・`docs/providers`（英語・日本語。45 番）の ts のコード例をすべて実行し、コメントに書いた結果（`expr; // "2026-11-02"` や、次の行から続く `// { ... }`）と比べます（`scripts/check-readme-examples.ts`）。

- コード例は利用者が最もよく読む部分で、日英 2 つあるので、仕様の変更で片方だけ古くなりやすいところです
- ブロックは 1 つずつ別のモジュールにして、ビルド済みの `dist` で実行します。ブロックが import していない公開の名前は補い、ほかのブロックで定義した値を使う断片には決まった定義（`FIXTURES`）を補います。利用者のプロジェクトのファイルを import するブロックは実行できないので飛ばします
- 比べないもの: リテラルで始まらないコメント（説明だけのもの）、現在時刻（`new Date()`）を使う式。`{…}` は何にでも一致し、`…` を含む文字列は … 以外の部分を順に含めば一致とします
- README のサイズの値（minify + gzip）は、測るのに新しい依存（esbuild など）が要るので自動では確かめません。測った版を添え、マイナー版で測り直します（RELEASING.md）

## 28. 監視は外部から起動し、動いたことをハートビートで確かめる

GOV.UK の監視（govuk-watch。0.17.0 から data-watch で、シンガポール（44 番）・日本（46 番）・フランス（48 番）の照合も同じ起動で行う）は、外部の cron サービス（cron-job.org）から `workflow_dispatch` を API で呼んで起動します。GitHub の schedule は予備として時刻をずらして残し、動いたことは最後に healthchecks.io へ知らせます（ハートビート）。

- GitHub の schedule は、高負荷時に遅れたり落ちたりするとドキュメントに書かれています。このリポジトリでも、追加してから一度も動きませんでした。3 時間ごとの設定で 4 日間一度も動かなかったという報告もあり、回数を増やしても解決しないと判断しました
- cron-job.org に預けるトークンは、このリポジトリだけ・Actions の Read and write だけに絞ります。漏れた場合にできるのは、`workflow_dispatch` のある監視のワークフローの起動と、ワークフローの無効化・実行の取り消しなどの妨害までです。コードの変更はできず、npm への公開には staged publishing の 2FA での承認が要るので、利用者に悪いパッケージが届くことはありません
- GitHub の「失敗したときだけメール」の通知は、実行がなければ届きません。「来るはずの知らせが来ない」ことに気付くには、それを見張る仕組みが要るので、ハートビートを使います。cron-job.org・GitHub の schedule・ワークフロー・トークンの期限のどこで止まっても、知らせが途絶えて気付けます。healthchecks.io に預けるのは知らせ先の URL だけで、リポジトリを操作する権限は渡しません
- 通知の役割: 差分と監視の故障（取得の失敗など）は GitHub の失敗の通知と issue、監視が動かなかったことは healthchecks.io のメール。照合そのものが失敗したときは、ハートビートでも `/fail` を知らせます

## 29. 利用者からの改善提案への対応

複数頂いた改善提案に対して、0.9.0 で次のように対応しました。

- **`reason` の意味は変えない**: スケジュールの `dayInfo` の `reason` は「値を決めた規則」です。祝日の規則が `"weekday"` のときは、祝日でも `"weekday"` になります。「祝日の規則が関わったか」を表すフィールドは足さず、README に「祝日かどうかは `holiday` で判定する」と書きました。フィールドを足すと、「祝日か」「祝日の規則が値を決めたか」「関わったか」の区別が増えて、かえって分かりにくくなるためです
- **時刻を必ず持つ入力では `time` を `string` にする**: `civilOf`・`toDateTimeParts`・`toJapanDateTime` にオーバーロードを加えました。返す値は変えず、型を正確にするだけなので、既存のコードは壊れません。時刻を持つかどうかは入力の型で決まります（`Date`・Temporal の `Instant`・`ZonedDateTime`・`PlainDateTime`、`"YYYY-MM-DDTHH:mm…"` の文字列）。空白で区切った日時の文字列（`"2026-11-23 10:00"`）は、0.15.0 までは実行時に受け付けていましたが型では `string | null` のままで、0.16.0 で受け付けをやめました（43 番）
- **期間の日ごとの情報（`daysBetween`）**: スケジュールと営業日カレンダーの両方に、同じ名前・同じ範囲の扱い（両端を含む）で足しました。`listBusinessDays` と同じく、`from` が `to` より後なら `invalid-range` です
- **型定義の確認は既存の tsc で**: `@arethetypeswrong/cli` は新しい依存になるので入れず（10 番）、既存の TypeScript で、利用者のプロジェクトとして `moduleResolution` を変えた型チェックを `pnpm check` に入れました。型定義の import が `.ts` の拡張子で書かれているため、利用者の設定で読めることを確かめる意味があります。古い TypeScript は新しい依存を避けるため CI では確かめず、確かめた範囲（0.9.0 の時点の手作業）を README に書きます
- **入れなかったもの**: 締め時刻の数値での指定（`cutoff: 14`）は、`14.5` が 14:30 なのかなどの曖昧さが増えるので入れません。`"14:00"` の文字列なら誤解の余地がありません。年月日と月日を 1 つの配列で渡す形も、今の明示的な分け方のほうが分かりやすいので変えず、README に振り分けの例を足しました
- **移行ガイド**: マイナー版の間を移るときの作業を `docs/migration.md` にまとめ、0.9.0 からは CHANGELOG の各マイナー版にも「移行」の小見出しを設けます。版を飛ばして移る利用者が、CHANGELOG を順に追わずに済むようにするためです

（0.21.3 で追記: 「古い TypeScript は CI では確かめず」は 0.13.0 で改め、CI の `consumer-types` ジョブで 5.0・5.5・5.8・7.0 を確かめています。38 番）

## 30. 規則の有効期間は `effectiveFrom`・`effectiveTo`、隔週は `interval`・`anchor`

繰り返しの規則と毎年の月日の規則に、省略可能な有効期間（両端を含む `"YYYY-MM-DD"`）を付けられます（0.10.0）。曜日の規則には、周期（週数）と起点の日付で「隔週」を書けます。

- 「2027 年 4 月から定休日を月曜から火曜に変える」は、カレンダーを 2 つ作って日付で呼び分けても、`addBusinessDays` のように切り替え日をまたいで探す計算が 1 つのカレンダーの中で完結するため正しく動きません。切り替え後の日付を個別の日付で列挙すると、件数が膨らむうえ、個別の日付は祝日より優先される（12 番）ので意味も変わります。規則そのものに期間を持たせるのが、意味を保てる唯一の形です
- 期間の外では、その規則は書かれていないのと同じに扱い、判定の順番（12 番）には影響しません。設定に省略可能な項目が増えるだけなので、互換性の約束の範囲です
- 項目の名前は、毎年の月日で使っている `from`・`to` と区別するため `effectiveFrom`・`effectiveTo` にしました。「有効期間」に対応する語として、業務システムで広く使われている言葉です
- 個別の日付（`closedDates` など）と定休日の曜日（`closedWeekdays`）には付けません。個別の日付はそれ自体が期間で、定休日の曜日の変更は「期間付きの毎週の規則」で表せるためです（判定の段階は違いますが、`holidayPolicy` のどの値でも営業日の判定は同じです。`reason` は `"closed-recurring"`、`rulePath` も付き、規則の診断の `redundant` の出方も変わります）
- 「隔週」は `{ weekday, interval, anchor }` で書きます。`interval` は 2 以上の整数で、1 は毎週と同じなので受け付けません。`anchor` は `weekday` と同じ曜日の日付で、周期の位相を決めるだけです（起点より前の日にも当てはまります）。開始日を兼ねさせなかったのは、`anchor` の意味を 1 つに保つためで、開始日は `effectiveFrom` で書けます。起点を「偶数週・奇数週」や ISO 週番号にしなかったのは、年をまたぐと週の数え方が変わり、店舗の掲示（「○月○日から隔週」）と一致しなくなるためです
- 有効期間の診断（`never-matches`・`shadowed`・`redundant`・`out-of-range`）は 15 番に書きました。期間の中に当てはまる日がない規則は `never-matches` に含め、新しい code は足していません（message で区別します）

（0.30.0 で追記: `anchor` は、隔週でも日単位の周期でも「周期を数え始める日」の 1 つの意味で用語集に載せた（54 番）。名前は変えていない）

## 31. `businessDaysBetween` だけが半開区間

期間を取る API のうち、`daysBetween`・`listBusinessDays`・`holidaysBetween` は両端を含みますが、`businessDaysBetween(from, to)` は `from` 以上 `to` 未満の営業日の数です。

- 半開区間だと `businessDaysBetween(a, b) + businessDaysBetween(b, c) = businessDaysBetween(a, c)` が成り立ち、**起点 `a` が営業日なら** `addBusinessDays(a, n)` の結果 `b` について `businessDaysBetween(a, b) = n` になります（`addBusinessDays` の逆算）。日数の差を求める `diffDays` も同じ考え方です
- 起点が休業日のときは逆算になりません（0.15.0 で明記）。`addBusinessDays` は「翌日以降の n 個目の営業日」を返し、`n = 0` は `businessDayOnOrAfter` と同じなので、休業日からは `+0` と `+1` が同じ日（翌営業日）です。一方 `businessDaysBetween` は休業日の起点を数えないので、`businessDaysBetween(a, addBusinessDays(a, n)) = n − 1` です。これは期日計算の慣習（Excel の `WORKDAY` と同じ）で、変えると利用者の期日が変わるため挙動は変えず、`addBusinessDays(a, n) = addBusinessDays(businessDayOnOrAfter(a), n − 1)`（n ≥ 1）を性質のテストで固定し、README に書きました
- 「期間の営業日の一覧」を返す `listBusinessDays` は両端を含むほうが自然で、数が要るなら `.length` で求められます。「Between なのに範囲の扱いが違う」という違和感はありますが、名前を変える（`countBusinessDays` など）利用者の作業に見合う利益がないので、名前は変えず、範囲の扱いをガイドに明記しています（0.17.1 までは README。45 番）

（0.30.0 で追記: 半開区間の数の関数を `diffBusinessDays` に改名し、名前の形（`diff…` は数、`…Between` は両端を含む一覧）で区間の扱いが分かるようにした。一覧を返していた `listBusinessDays` は `businessDatesBetween`（54 番の N2））

`bizdays-toolkit/jp` の `toJapanDate`・`toJapanDateTime` を 0.10.0 で `@deprecated` にし、1.0.0 で削除します。移行先はルートの `toDateString(input, "Asia/Tokyo")`・`toDateTimeParts(input, "Asia/Tokyo")`、または営業日カレンダー・スケジュールの `dateOf`・`civilOf` です（同じ変換・同じ型）。

## 33. 「祝日の翌日」は繰り返しの規則の形の 1 つ（`dayAfterHoliday: true`）

公立図書館・美術館の「祝日の翌日休館」のように、祝日そのものに従属する規則を、繰り返しの規則の新しい形として書けるようにしました（0.11.0）。

- 繰り返しの規則は曜日・第 n 曜日・日の形だけで、「祝日の翌日」は書けませんでした。回避策（`holidaysInYear` から翌日を生成して `closedDates` に入れる）は年を決めて生成する必要があり、個別の日付は毎年の月日より優先される（12 番）ので、「年末年始は祝日の翌日でも開館する」のような毎年の例外と順番が崩れます。規則であるべきものを結果として書くことになるため、規則として足しました
- 意味は「祝日の連続の翌日で、その日自身は祝日でない日」で、振替先（14 番）と同じ定義です。「祝日」は提供元の祝日だけで、休業日の設定は含めません（14 番と同じ理由）
- 当てはまる日は定義上祝日でないので、`onHolidayRule` は意味を持ちません。指定されたら `invalid-option` にします。黙って無視すると設定の意図を読み違えるためです。型では `never` にしていません。`{ ...rule, onHolidayRule }` のように既存の規則に `onHolidayRule` を重ねて書く使い方が、形の種類を知らなくてもできるようにするためで、実行時の検証で足ります
- 判定は繰り返しの規則の段階（12 番）で、配列の順番どおりです。月曜の祝日の翌日は「月曜の規則（`"after-holiday"`）の振替先」でも「祝日の翌日」でもあり、先に書いた規則が決めます
- 診断では、当てはまる日が年ごとの祝日で変わるため、曜日の規則との包含（`shadowed`）は判定せず、祝日の翌日の規則どうし（`months` と有効期間）に限ります。種類をまたぐ重なりは `redundant` で見つかります（15 番の考え方と同じ）
- 「祝日の前日」は需要が見えるまで入れませんでしたが、祝前日料金・祝前日の営業時間の延長・締めの繰り上げという需要の例が示されたため、0.16.0 で鏡像の形 `dayBeforeHoliday: true` として足しました（43 番）

（0.22.0 で追記: 祝日の翌日・祝前日の規則に `kinds`・`keys`（隣の祝日で絞る）と `skipWeekdays`（祝日と書いた曜日が続く塊の前後の日）を足しました。定義の「提供元の祝日だけ」は変わりません。53 番）

（0.30.0 で追記: 「祝日の翌日・祝前日・祝日の規則は `holidayOverlapPolicy` を受けない」などの形ごとの制限を、型でも表すようにした。`{ ...rule, onHolidayRule }` と重ねて書けるよう型を緩めた判断は、その書き方が実行時に例外になる以上利点がないので改め、43 番の「型と実行時の食い違いは不具合」に揃えた。旧名の `onHolidayRule` だけは 1.0.0 まで形を問わず受ける）

## 34. カレンダーの合成は作成済みのカレンダーに対して行い、判定を決めたカレンダーの結果を引き継ぐ

`combineCalendars(calendars, { businessDay: "all" | "any" })` は、作成済みの営業日カレンダーを合成して、通常の営業日カレンダーを返します（0.11.0）。

- 設定を結合して 1 つのカレンダーを作る方法では、片方の臨時営業日（`openDates`、最優先）がもう片方の休業日を打ち消し、意味が保てません。片方を祝日の提供元として包む方法は、相手の休業日が `isHoliday()` で true になり、`holidayPolicy: "open"` の設定で相手の休業日に営業し、振替先も相手の休業日まで飛びます（14 番が避けた状態）。祝日と休業日の区別を壊さないため、作成済みのカレンダーの判定結果を組み合わせます。各カレンダーの中の判定の順番（12 番）は変わりません
- `dayInfo` には `"combined"` のような新しい `reason` を足さず、合成結果と同じ判定をした最初のカレンダーの `reason`・`name`・`shiftedFrom` を引き継ぎ、そのカレンダーの番号を `decidedBy` で返します。「年末年始休業（`closed-annual`）で休み、決めたのは 0 番目のカレンダー」と読めるほうが、理由を 1 つの値に潰すより役に立つためです。「合成結果と同じ判定をした最初のカレンダー」は `"all"`・`"any"` のどちらでも、営業日・休業日のどちらでも必ず 1 つに決まります
- 祝日（`holiday`・`isHoliday`・`holidaysInYear`）は、各カレンダーの提供元の和集合で判定します。「和集合」は提供元のオブジェクトの単位で、同じオブジェクトは 1 つに数え、包んだ提供元（README のレシピのように `jp` から種別を除いたもの）は別の提供元として残ります。同じ日付に祝日のある提供元が複数あれば、先のカレンダーの提供元の祝日を返します（`holidayOn` が `providers` を順に見るため）。包んだ `jp` のカレンダーと `jp` そのもののカレンダーを合成すると、営業日の判定は各カレンダーの結果どおり正しいまま、除いたはずの祝日が `holiday` に付きます。祝日の「無い」を表せないのは、`HolidayLookup` の和集合という定義の帰結で、営業日の判定には影響しないため、そのままとしています。`outOfRange` は、どれかが `"throw"` なら `"throw"` です（そのカレンダーの判定が例外になるため）。このために `HolidayLookup` に `outOfRange` を公開しました
- タイムゾーンは同じでなければなりません（既存の `time-zone-conflict`）。日付の文字列を各カレンダーに渡して判定するため、暦日の意味がそろっている必要があります
- 公開インターフェース（`Calendar`）だけで合成するので、合成したカレンダーをさらに合成できます。設定の診断は設定に対するものなので、合成したカレンダーは対象にしません
- 内部では、営業日の探索・調整・月の営業日の実装を `createCalendar` から切り出して共用しています。合成でも `maxSearchDays` を指定できます

（0.30.0 で追記: 合成の設定 `businessDay` を `open` に改めた（`DayInfo.open` と同じ語））

## 35. 祝日を対象にする規則は繰り返しの規則の形の 1 つ（`holiday: true`）で、「祝日の上」の段階で判定する

祝日の既定の扱い（`holidayPolicy`・スケジュールの `holiday`）の例外を、繰り返しの規則の新しい形として書けるようにしました（0.12.0）。

- 「来年度から祝日も営業」「振替休日は診療」「5 月の祝日は特別営業時間」は、既定の扱いが 1 つしか選べない現状では書けませんでした。回避策の `{ day: [1..31], onHolidayRule: "over-holiday", effectiveFrom }` は祝日でない日（定休日の曜日を含む）まで営業にし、提供元を包んで祝日を消す方法は振替・祝日の翌日の判定まで消します。33 番と対になる「祝日に従属する規則」として足すのが、意味を保てる形です
- 書き方は `{ holiday: true, kinds?, months?, effectiveFrom?, effectiveTo? }` です。`kinds` は `months` と同じ「絞り込みの配列」（省略時はすべて）で、`{ holiday: true, kinds: ["substitute"], months: [5] }` と左から読み下せます。種別は開いた型なので文字列の配列としてだけ検証し、提供元にない種別は診断で `never-matches` にします
- 判定は「祝日の上」の段階（12 番の 4。`"over-holiday"` の規則と同じ）で、同じ段階は配列順です。`holidayPolicy: "ignore"` でも当てはまります。無視するのは既定の扱いだけで、祝日を対象にすると書いた規則は書いたとおりに効くべきだからです。内部では `onHolidayRule` を `"over-holiday"` として扱い、`matchPattern` が「祝日である」を条件にするので、祝日でない日の段階では当てはまりません
- 当てはまる日は祝日なので `onHolidayRule` は意味を持たず、指定されたら `invalid-option` です（33 番と同じ理由）
- 診断では、33 番と同じく祝日次第で年ごとに変わるため、`shadowed` は祝日の規則どうし（`kinds`・`months`・有効期間の包含）に限ります。既定の扱いと同じ向きの規則は `redundant` で見つかります
- 名前は `ScheduleOptions.holiday` と同じ語ですが、規則の中では「対象の日」を表し、`dayAfterHoliday: true` と並べて最も読みやすいので、この名前にしました

（0.22.0 で追記: `kinds`・`keys` は祝日の翌日・祝前日の規則でも使えるようになりました。意味は隣の祝日の種別・識別子の絞り込みです。53 番）

（0.30.0 で追記: スケジュールの `holiday` を `holidayPolicy` に、値の `"weekday"` を `"ignore"` に改めた（カレンダーの `holidayPolicy` と同じ扱いの選択なので、同じ名前と同じ語にした。N5））

## 36. 値を決めた規則の位置を `rulePath` で返す

`DayInfo`・`ScheduleDay` に、値を決めた規則の設定の中の位置 `rulePath`（規則の診断の `path` と同じ形）を付けます（0.12.0）。

- `name` は省略可能で重複もできるので、「どの規則が決めたか」を機械的に特定するには位置が要ります。内部の判定結果（`Resolution.rule`）はすでに位置を持っているので、返すだけです
- `dates`・`annual`・`recurring`（振替先を含む）で決まった日にだけ付け、祝日・曜日で決まった日には付けません。祝日は `holidayPolicy`・スケジュールの `holiday` で決まり、規則の配列ではないので位置がありません。曜日は `closedWeekdays[i]`・`weekly[n]` と位置を書けます（設定の検証はその形の `path` を返します）が、その日の `weekday` の項目で分かるので位置は冗長で、付けません
- 合成（34 番）では、判定を決めたカレンダーの `rulePath` を引き継ぎます。位置はそのカレンダーの設定の中のもので、`decidedBy` と組で読みます
- 診断の `path` と同じ形にしたのは、診断の結果と実際の判定を突き合わせられるようにするためです

## 37. モジュールの定数 `dataVersion`・`confirmedThrough` は非推奨にし、提供元の項目に一本化する。性能の退行は CI で前の版との比率で検出する

`bizdays-toolkit/jp`・`bizdays-toolkit/uk` の定数 `dataVersion`・`confirmedThrough` を 0.12.0 で `@deprecated` にし、1.0.0 で削除します。移行先は提供元の項目（`jp.dataVersion`・`england.confirmedThrough` など）です。

- 定数と提供元の項目は同じ値で、英国は 4 つの提供元に対して 1 組の定数という歪みがありました。32 番と同じ理由（1.0.0 で API を固める前に、同じ情報の経路を減らす）で一本化します。削除までは互換性の約束どおり少なくとも 1 つのマイナー版を置きます
- `firstBusinessDayOfMonth`・`lastBusinessDayOfMonth` は `nthBusinessDayOfMonth(month, 1)`・`(month, -1)` の別名ですが、使用頻度が高く残します。別名はこれ以上足しません
- ここでいう「別名」は、同じオブジェクトの上で引数を固定しただけの名前（`first… = nth…(…, 1)`）です。タイムゾーンや営業日のような文脈を持つオブジェクト（カレンダー・スケジュール）からの経路（`instantOf` と `toInstant`、営業日を考慮した `closingMonth` と暦日の `closingMonth`）は、結果が文脈で変わるので別名に当たりません（32 番の「国に依らない 2 経路」・40 番・41 番）。0.15.0 で明記

性能については、営業日表のキャッシュ（年ごとに営業日を前計算する内部の最適化）を、明確な性能の課題が出るまで入れません。実測（1 日の判定 2.6µs、10 年の `businessDaysBetween` 8.6ms）は業務の規模で問題にならないためです。将来入れる場合は、判定が入力の値だけで決まること（38 番の `isOpen` の純粋性）がキャッシュの前提になります。代わりに、課題が出たことを知る手段として CI に `bench` ジョブを置きます。（理由の書き方は 0.18.0 で改めました。以前は「将来の非純粋な判定関数と相性が悪い」と書いていましたが、38 番は非純粋な判定を将来も入れないと決めているので、存在しないものを前提にしていました）

- 公開済みの前の版（npm の `latest`）と今回の `dist` を、同じランナー・同じ Node.js で `scripts/bench.ts` にかけ、比率で比べます（`scripts/bench-compare.ts`）。ランナーの性能は実行ごとに数十%ぶれるので、絶対値では判定しません。同じ実行の中の 2 つの結果の比率にはぶれが現れにくく、安定します
- 判定は「どれかの計測が前の版の 2 倍より遅い」で失敗にします。アルゴリズムの悪化（走査が 2 重になった、など）を捉える粗い線で、数十%の差はノイズとみなします。絶対値は Job Summary に残し、リリースごとの傾向を追えるようにします
- `pnpm check` には含めません（結果が機械に依存するため。RELEASING.md の「品質の確認」）

（0.30.0 で追記: 0.30.0 の改名でも、旧名は `@deprecated` の別名として 1.0.0 まで残す（一時的な重複）。削除予定の表には、型の項目とメソッドを修飾名で載せる）

## 38. スケジュールから営業日カレンダーを作る（`createCalendarFromSchedule`）。利用者の TypeScript の版は CI で確かめる

営業時間表のようなスケジュールが設定の正本である利用者のために、スケジュールと「値が営業か」を決める関数から営業日カレンダーを作る関数を足しました（0.13.0）。

- 営業日カレンダーをもう一式書いて同期を取る必要をなくすためです。内部では、`createCalendar`・`combineCalendars` と共用の `buildCalendar` に、スケジュールの内部の判定（`infoOfSchedule`。公開メソッドの入力の解析を通らない）をつなぎます。作成時のコストは `createCalendar` と同程度です
- 名前は `createCalendarFromSchedule` です。ルートの「作る」関数（`createCalendar`・`createSchedule`・`combineCalendars`）はすべて動詞で始まり、`create` の接頭辞には「引数を検証して不変のものを返す」含みがあります。`createCalendar` のオーバーロードにしなかったのは、第 1 引数の形で分岐すると型が複雑になり、設定の誤りの診断（`options must be an object`）とも衝突するためです
- `isOpen` は値だけを受け取ります（`ScheduleDay` や日付は渡しません）。日付や祝日を見られる形にすると「純粋な関数」の前提を利用者が破りやすく、営業日の探索の結果が呼ぶたびに変わる危険があります。日付で変えたい条件はスケジュールの規則（`dates`・`recurring`）に書くべきもので、値だけで決まるほうが、37 番で見送った営業日表のキャッシュを将来入れる場合の前提も単純です。将来 `ScheduleDay` を渡したい要望が来ても、この理由で断ります。位置引数にしたのは、将来足す項目が `maxSearchDays` 以外に見えないためです（`combineCalendars` のようにオプションの形にする理由が薄い）
- `dayInfo` の `reason` は、`createCalendar` の内部の変換と同じ対応（`date` → `"open-date"`/`"closed-date"` など）です。違いは `annual` だけで、`createCalendar` の `closedAnnual` が休業専用なのに対し、スケジュールの `annual` は営業の値も取れるので `"open-annual"` を足しました。既存の値に押し込むと、`"open-date"` では嘘になり、`"regular"` では規則で決まったことが消えます。`DayReason` は開いた型（2 番）で、`createCalendar` の結果は変わりません
- 営業になる祝日（`holiday: { sameAs: 0 }` で曜日の値が営業、など）の `reason` は `"holiday"` のままです。`createCalendar` の `holidayPolicy: "open"` と同じで、`reason` は「決めた規則」、営業・休業は `businessDay`、という分担を崩しません
- 診断の対象にはしません。スケジュールの設定を `diagnoseSchedule` で診断します
- スケジュールの内部の判定は、スケジュールのオブジェクトリテラルに Symbol の項目（列挙されず、JSON にも出ない）として最初から含めます（0.14.1）。0.13.0 では作成後に `WeakMap` に登録していましたが、`Object.freeze` 済みのオブジェクトに後から印（`WeakMap` のキーのハッシュ、`defineProperty` の項目）を付けると V8 がオブジェクトを遅い形に落とし、`createCalendar`・`createSchedule` の作成が約 30% 遅くなっていました（CI の `bench` が 1.26 倍を検出し、37 番の仕組みが最初の版で役に立ちました）。5 番（返すものは凍結する）と組み合わさるときの一般則として、**凍結するオブジェクトには作ったあとに印を付けず、印はリテラルに含める**を守ります

利用者の TypeScript の版の確認は、0.9.0 の時点で 5.0・5.5・5.8 を手作業で確かめたままになっていたので、CI に `consumer-types` ジョブを置きました。

## 39. 締め期間は `closingPeriod` で返し、締め日の読み替えは `closingMonth` と同じ 1 か所で行う

`closingMonth(date, closingDay)` の逆算として、その月分の期間を返す `closingPeriod(monthOrDate, closingDay)` を足しました（0.14.0）。

- 「11 月分の期間」を利用者が自分で組み立てると、16 番の読み替え（締め日がその月にない場合は末日）を再実装することになり、2 月の 31 日締めや 30 日締めの境界で `closingMonth` とずれる危険があります。読み替えは内部関数 `closingDayIn` の 1 か所に置き、両方の関数がそれを使います
- 返す値は `{ from, to }`（両端を含む暦日）で、`DateRange` と同じ形です。専用の型を足さなかったのは、`etc/api.md` に型を増やさず「日付の期間はこの形」という語彙を 1 つに保つためで、`closedDates` や `listBusinessDays` にそのまま渡せるのは結果です。`name` は付けず、`Object.freeze` します（5 番）
- 月だけでなく暦日も受け付けます（`monthOf` と同じ）。「この日が属する締め期間」は締め処理の最初の一行で、内部は `closingMonth` を通すだけです
- 性質のテストで、締め日 1〜31 と -1 のすべてについて、連続する期間が隙間も重なりもなく敷き詰められること（`to` の翌日が次の `from`）と、期間のすべての日で `closingMonth` が往復することを確かめます。往復だけでは「前月に締め日がなければ当月 1 日」の境界が片側しか試されないためです

## 40. 暦日と時刻から瞬間への変換は `Date` を返し、夏時間の扱いは Temporal の `"compatible"` にそろえる

`civilOf`・`toDateTimeParts` の逆向きとして、ルートの `toInstant(date, time, timeZone)` と、営業日カレンダー・スケジュールの `instantOf(date, time)` を足しました（0.14.0）。

- 返す型は `Date` です。ライブラリで「瞬間」を表す型は入力側で `Date` に決まっていて（`TemporalInstantLike` は受け取る形で、作る形ではない）、`Date` は 1 行でエポックミリ秒にも ISO 文字列にも Temporal の `Instant` にもなります。文字列や両方を返す形は型を増やすだけなので採りません
- 受け付けるのは暦日の文字列だけです。`Date` を受けて「その日の 10:00」に読み替えると、タイムゾーンをまたぐ入力でどの日か曖昧になります。時刻は `civilOf` と同じ `"HH:mm"` に加えて `"HH:mm:ss"` も受け付けます（「営業開始の瞬間」で秒まで指定したい要望は自然で、受け付ける側だけ広げても型は変わりません）
- `instantOf` をメソッドとしても置くのは、主な用途（次に開く瞬間）がカレンダーのタイムゾーンで完結し、`dateOf`・`civilOf`・`instantOf` と並ぶと往復の対称性が名前で分かるためです。`HolidayLookup` に置くので、合成したカレンダーとスケジュールからのカレンダーにも付きます。ルートの関数は `toDateString`・`toDateTimeParts` と対になり、32 番（国に依らない 2 経路）と同じ構成です
- 夏時間の飛び・重複は Temporal の既定 `disambiguation: "compatible"`（飛びは切り替え前のオフセットで解釈して飛んだ分だけ後ろへ、重複は先のほう）と同じにします。Temporal・Luxon・date-fns-tz の既定と一致し、利用者が別の道具と突き合わせても食い違いません。選択肢は需要が見えるまで足しません（16 番で `nearest` を入れなかった姿勢と同じ）
- 実装は `Intl` だけで、前後 1 日のオフセットを候補にして、暦日と時刻に戻して一致する候補を選びます（重複は小さいほうの瞬間、飛びは切り替え前のオフセット）。オフセットの差が 1 時間でないゾーン（`Australia/Lord_Howe`。30 分）と南半球（`Pacific/Auckland`）でも確かめ、英国の例はテストで固定しています

## 41. 祝日・祝日の翌日の規則に曜日の絞り込み `weekdays` を足す。営業日を考慮した締め日はカレンダーのメソッドで、固有の期間がない月は次の月に併合する

0.15.0 で、規則の形の拡張を 1 つと、カレンダーのメソッドを 2 つ足しました。

**`weekdays`**（祝日・祝日の翌日の規則の絞り込み）

- 「祝日の翌日は休館（土曜・日曜に当たる場合は開館）」「祝日は休診、土曜の祝日は午前診療」は、2 条件の AND を 1 つの規則で表す手段がなく書けませんでした。`openRecurring` で土日を開ける回避策は同じ段階のすべての休業の規則に勝つので、ほかの土日の休業まで打ち消し、意図が設定に残りません。年ごとに日付を列挙する回避策は 33 番が退けた形です
- `months`・`kinds` と同じ「絞り込みの配列」として足し（35 番の書き方の方針）、判定の段階（12 番）と祝日の翌日・祝日の定義（33・35 番）は変えません。曜日の規則（`weekday`）と区別するため複数形にし、曜日・日の規則には付けません（複数の曜日の規則は規則を 2 つ書く。37 番）
- 診断は、当てはまる日がなければ `never-matches`（振替休日は土日に来ないので `{ holiday: true, kinds: ["substitute"], weekdays: [0, 6] }` は日本では当てはまらない）、同じ形の規則どうしの `shadowed` に曜日の集合の包含を加えます

**営業日を考慮した締め日**（`calendar.closingMonth(input, closingDay, { convention })`・`calendar.closingPeriod(…)`）

- 「20 日締め、締め日が土日祝なら前営業日締め」は、前月と当月の両方の調整後の締め日と比べる必要があり、片方向の調整だけでは境界を誤ります。39 番がライブラリに閉じ込めた「期間が隙間も重なりもなく敷き詰められる」の保証も、利用者側では再演になります
- 定義: 月 m の調整後の締め日 D(m) = adjust(その月の締め日（読み替えは 39 番の `closingDayIn`）, convention)。m の期間は D(m−1) の翌日〜D(m)。`closingMonth(date)` は date ≤ D(m) となる最小の m。`convention` は `adjust` と同じく必須で既定値なし（16 番）
- 固有の期間がない月（D(m) = D(m−1)。前月の締め日から当月の締め日までに営業日がない、1 か月前後の長期休業）は、定義の帰結として次の月に併合されます。`closingMonth` はその月を返さず、その日は m+1 の期間に含まれます。併合の規則を別に足すと「どちらに併合するか」という業種依存の判断（16 番が `nearest` を入れなかったのと同じ種類）を背負うため、定義から出る形に任せます。ただし、定義「date ≤ D(m) となる最小の m」自体が次の月に寄せる側を選んでいます（最大の m で定義すれば前の月に併合される）。次の月を選んだ理由は、D が月とともに単調に増えるので `closingMonth` を暦日の締めの月から順に探せること、「締め日を過ぎた日は次の月分」という締めの素朴な読み方と一致することです
- 空の月の `closingPeriod` は `no-business-day` を投げます。`from > to` の値を返すと `closedDates` などに渡した先で `invalid-range` になる罠になり、`undefined` を返すと滅多に起きない事態のために全利用者に null チェックを強いる（29 番の方針と逆向き）ためで、`nthBusinessDayOfMonth` が営業日のない月に同じ code で投げるのとそろえました。利用者がこの例外に出会うのは月を自分で列挙する場面だけで、`closingMonth` 経由では出会いません
- `"following"` で前月の締め日が長期休業を越えて当月以降に来ることがあります。期間は空にならず長くなります。D は月とともに単調に増える（減らない）ので、`closingMonth` は暦日の締めの月から後ろ・前へ順に探せば求まります
- 性質のテストで、複数のカレンダー × 4 つの方法 × 締め日 1〜31・−1 について、空でない期間を順に並べると敷き詰められること、期間内の日で `closingMonth` が往復すること、空は `no-business-day` でだけ表れることを確かめます。この事態は呼び出し時の組み合わせで決まるので規則の診断では検出できず、README に書きました
- 置き場所はカレンダー（営業日が要る）で、`buildCalendar` に置くので合成したカレンダー・スケジュールからのカレンダーにも付きます。ルートの暦日の版は別の結果を返すので別名ではありません（37 番）

## 42. `kinds` は提供元の種別の型で受け、`cutoff` は時刻のない入力と組み合わせたら例外にする

- `HolidayPattern<Kind>.kinds` を `readonly Kind[]` にし、`RecurringRule<Kind>`・`RecurringValue<T, Kind>` を通して `CalendarOptions<Kind>`・`ScheduleOptions<T, Kind>` に型引数を流します（0.15.0）。8 番が型引数 `Kind` を残した理由（日本の祝日で種別の補完が効く）が、`kinds` には届いていませんでした。種別は開いた型（2 番）なので、提供元にない文字列も型では通り（診断で `never-matches`）、既定値付きの型引数の追加は `RecurringRule` を単独で使うコードを壊しません
- `businessDayOnOrAfter` の `cutoff` を、時刻を持たない入力（暦日の文字列・Temporal の `PlainDate` など）と組み合わせると `invalid-argument` にします（0.15.0）。それまでは暦日を 0 時として扱い、締め時刻は黙って無視されていました。注文の受付時刻を `Date` で渡すつもりがフォームの日付文字列をそのまま渡した、という事故が、出荷が間に合わなかったあとにしか分からないためです。4 番の「知っているキーの無効な組み合わせは例外」と同じ性格で、黙って通っていた呼び出しを止める変更なので CHANGELOG の「移行」と docs/migration.md に書きました（0.x のマイナー版で行える。1.0.0 以降なら行えない）。型では区別できません（文字列は暦日も日時も `string`）

（0.30.0 で追記: 日本の祝日の種別 `"national"` を `"regular"` に改めた（英国・シンガポール・フランスと同じ語。毎年繰り返す祝日の種別）。`kinds` の `"national"` は、日本の提供元を使う設定でだけ 0.30.x の間読み替える）

（0.30.1 で追記: 和集合の設定で読み替えると他国の `"regular"` にも当たったので、読み替えをやめ、0.22.x と同じ意味で判定するようにした。54・55 番）

## 43. 祝前日の規則、提供元の実装者向けのサブパス、入れ子の合成の経路、空白区切りの日時の廃止、Bun・Deno の確認

0.16.0 で、利用者からの機能拡張提案（4 通目）のうち、既存の API を組み合わせても書けないもの 3 つと、品質の項目 2 つを入れました。

**祝前日の規則**（`{ dayBeforeHoliday: true }`）

- 33 番で保留していた「祝日の前日」を、需要の例（宿泊・温浴の祝前日料金、飲食店の祝前日の営業時間の延長、祝前日の出荷の締めの繰り上げ、博物館の祝前日の夜間開館）が示されたので足しました。意味は「翌日が提供元の祝日で、その日自身は祝日でない日」で、連休なら連休の初日の前日だけです。`dayAfterHoliday` の鏡像で、同じ項目（`weekdays`・`months`・有効期間・`name`）を持ち、当てはまる日は祝日でないので `onHolidayRule` は `invalid-option` です。判定の段階（12 番）は変えません
- 「飛び石連休の間の日」のような規則は入れません。前後が休業かどうかがカレンダー自身の結果に依存し、14 番の「提供元の祝日だけ」と相容れないためです。祝前日は提供元の祝日だけで決まるので、この問題はありません
- 祝日と祝日の間が 1 日の年（2027 年 9 月 21 日と 23 日の間の 22 日など）には、その日が祝日の翌日でも祝前日でもあります。配列で先に書いた規則が決めます（33 番の月曜の振替先との関係と同じ）
- 診断は祝日の翌日と同じ扱いです。祝前日の規則どうし（曜日・月の絞り込み・有効期間の包含）だけ `shadowed` を調べ、祝日の翌日とは別の形として比べません（種類をまたぐ重なりは `redundant` で見つかります）

**提供元の実装者向けのサブパス**（`bizdays-toolkit/provider`）

- 多くの国・地域の祝日は「月の第 n 何曜日」と「復活祭からの日数」で書けますが、復活祭の計算は公開しておらず、提供元を書く利用者が各自に実装して検証することになっていました。内部の実装（`easterSunday` は英国の祝日で GOV.UK のデータと 2012 年から全日照合済み）をそのまま公開します。39 番の「同じ計算を 1 か所に置き、利用者に再実装させない」という考え方と同じです
- サブパスに分けたのは、診断と同じく、ルートのサイズに影響させないためです（15 番の分け方）。`easterSunday` は `src/uk/rules.ts` から `src/core/date.ts` に移し、サブパスが英国の祝日のデータを引き込まないようにしました
- 公開する関数は入力を検証します（年は 1000〜9999 の整数、月は 1〜12、曜日は 0〜6、n は 1〜5 と -1）。内部の関数は呼び出し側が検証済みの値を渡す前提で検証しないので、そのまま公開すると `nthWeekdayOfMonth(2026, 2, 0, 5)` が日付の文字列の検証で `invalid-date` になるなど、誤りが分かりにくい形で現れるためです。その月にない回は `invalid-argument` です。`-1`（最後）は、米国の Memorial Day（5 月最終月曜）のように最終の曜日で決まる祝日が多いので、規則の `nth: -1` と同じ意味で足しました
- RELEASING.md の安定度の表示どおり `@beta` で出し、使われ方が固まってから `@public` にします。37 番の「別名はこれ以上足さない」は同じ結果を返す名前の重複についてで、未公開の関数の公開は別名ではありません

**入れ子の合成の経路**（`decidedByPath`）

- 34 番の合成は、判定を決めたカレンダーの `rulePath` を引き継ぎながら `decidedBy` を外側の番号で上書きし、内側の `decidedBy` を捨てていました。合成したカレンダーをさらに合成すると、`rulePath` がどのカレンダーの設定の位置か結果だけからは分からず、36 番の「`rulePath` は `decidedBy` と組で読む」という約束が入れ子では閉じていませんでした
- `DayInfo` に `decidedByPath`（外側から順の番号の列。凍結した配列）を足しました。入れ子でない合成では長さ 1 で先頭は `decidedBy` と同じ、合成していないカレンダーには付きません。`decidedBy` の意味は変えません。内側の `DayInfo` を入れ子にする案は、読む側が再帰になり凍結したオブジェクトの入れ子も深くなるので取りませんでした

**空白区切りの日時の廃止**

## 44. 未確定の祝日のガード、診断の基準日、シンガポールの祝日

0.17.0 で、4 通目の機能拡張提案の残り 2 つ（P2・P4）と、3 つ目の国としてシンガポールを入れました。

**未確定の祝日のガード**（`unconfirmedHolidays: "accept" | "throw"`）

- 日本の春分の日・秋分の日は翌年分が毎年 2 月の官報で公表され、それより後の年は予測（`confirmed: false`。6 番）です。5 年の返済予定や契約書の日付のように、予測に依存した結果を黙って出したくない場面があるため、`outOfRange` と並ぶ設定として足しました。既定は `"accept"`（これまでどおり）です
- 止める場所は祝日を引く経路（`holidayOn`）の 1 か所です。「評価した日すべて」で止めます。求めた日だけでなく、探索が途中で通る日や、祝日の翌日・祝前日の規則が見る隣の日も含みます。結果が予測に依存しうる経路を漏れなく止めるためで、どの経路が祝日を引くかを列挙して特別扱いするより単純です
- `holidaysInYear`・`holidaysBetween` は投げません。一覧は `confirmed` を見るための経路で、例外を受けたあとに影響する日を列挙する逃げ道になります（README のレシピ）。例外の判定は `code`（`unconfirmed-holiday`）で行い、メッセージには日付・祝日名・提供元の `confirmedThrough` を入れます（3 番）
- `holidayPolicy: "ignore"`（スケジュールなら `holiday: "weekday"`）で祝日に従属する規則もない設定では、未確定の祝日は結果に影響しません。しかし `dayInfo` は `holiday` を付けるために祝日を引くので、素直に実装すると投げます。実行時に特別扱いを入れる案は退け、「判定に祝日を使う設定でだけ意味がある」と文書に書き、診断でそのような設定の `"throw"` を `redundant`（info）にしました。仕組みを増やさず、意図と違う設定を診断で知らせる形です
- 診断は常に `"accept"` で評価します。診断は設定の形を調べるもので祝日の確定は無関係であり、`"throw"` のまま評価すると振替元をさかのぼる `holidayOfSafe` が例外を握りつぶして「当てはまらない」と誤判定するためです。`holidayOfSafe` が飲み込む例外も `out-of-range` だけに絞りました（それ以外は投げ直す）
- 合成は `outOfRange` と同じく「どれかが `"throw"` なら `"throw"`」です。そのカレンダーの判定が例外になるので、合成の `holiday` の判定だけ通しても意味がありません
- 限界: 捕まえるのは「予測された祝日」で「まだ知らない祝日」ではありません。英国の臨時の bank holiday は予測に含まれず、シンガポールは予測を持ちません（後の年は `out-of-range`）

**診断の基準日**（`asOf` と `expired`）

- 設定が年を追って溜まる場面（店舗ごとの設定を JSON で持つサービスなど）で、終わった規則を見つけたいという要望です。`redundant` は「取り除いても結果が変わらない」で、過去には効いていた規則とは別の意味なので、別の code `expired`（info）にしました
- 診断の第 2 引数 `{ asOf }` で渡したときだけ返します。省略時の結果はこれまでと同じで、現在時刻は使いません（15 番の決定性。`assert.deepEqual(diagnoseCalendar(options), [])` のようなテストが日付で変わらない）
- `asOf` は暦日の文字列だけを受け付けます。診断は設定の形を調べるもので現在時刻を使わず（15 番の決定性）、基準日は設定の `effectiveFrom`・`effectiveTo`・個別の日付と同じ暦日の文字列に統一します。（理由の書き方は 0.18.0 で改めました。以前は「`Date` を受けるとどのタイムゾーンで暦日にするかが要る」と書いていましたが、診断の設定には `timeZone` と提供元があり、カレンダーの `today(now?)` は同じ情報から `Date` を暦日にしているので、その理由では `Date` を断れませんでした）。第 2 引数の知らないキーは 4 番と同じく無視し（前方互換）、既知のキーの型違いは `invalid-date`、第 2 引数自体がオブジェクトでなければ `invalid-argument` の例外です。設定の側の誤り（`options must be an object` など）は診断結果で返す現状のままで、「設定の誤りは結果、引数の誤りは例外」と線を引いています（README に 1 行書きました）
- `expired` の判定は、取り込み済みの終わりの日（`effectiveTo`、個別の日付・期間の `to`）と `asOf` の日数の大小比較だけで祝日を引かないので、`asOf` が提供元の対応年の外でも `out-of-range` にはなりません。終わりの日が `asOf` と同じ日は、その日まで有効なので `expired` ではありません

**シンガポールの祝日**（`bizdays-toolkit/sg`）

- 旧正月・Hari Raya Puasa・Hari Raya Haji・Vesak Day・Deepavali は太陰暦・イスラム暦・ヒンドゥー暦で決まり、規則では計算できません。日本・英国の「規則で計算して公式データで照合する」形（18 番）は取れないので、MOM（Ministry of Manpower）が官報で告示した日付を正とする年ごとの表を同梱します。振替だけは Holidays Act 第 4 条の規則（日曜日に当たる祝日は、その翌日のうちそれ自体が祝日でない最初の日が祝日。土曜日は振り替えない）で計算し、表には書きません。英国の振替と同じ扱いで、`kind: "substitute"` の名前は元の祝日のままです（data.gov.sg の "(Observed)" は照合で読み替える）
- 対応年は表のある年（2020〜2027 年）だけで、それより後は予測せず `out-of-range` です。固定日の祝日（元日・Labour Day・National Day・Christmas Day）と Good Friday だけなら計算できますが、祝日が欠けた年を `confirmed: false` で返すのは危険なので、年ごと丸ごと持つか持たないかにしました。2020 年より前は、MOM の報道発表で確かめた年から足します（英国の 2012 年以前と同じ運用）
- 照合用のデータは data.gov.sg のコレクション 691（MOM 提供。認証なしの API）です。ただし 2022 年分は、MOM が 2021 年 10 月 21 日の報道発表で改定した告示（Hari Raya Puasa を 5/3、Hari Raya Haji を 7/10 に改め、日曜日の祝日は翌月曜日が祝日）と食い違います。data.gov.sg は改定前の形（5/2 Hari Raya Puasa、5/3 Labour Day の振替）で、5/16・7/11 の振替も落としています。祝日法の振替の規則から導いた結果と全年を突き合わせても、食い違うのはこの 2022 年だけでした。**正は告示**で、data.gov.sg は照合用です。食い違いは英国の `RENAMED` と同じく既知の差分としてフィクスチャに出典付きで記録し、照合ではその差分だけを許し、既知の差分が消えたとき（data.gov.sg が直ったとき）も知らせます。data.gov.sg をそのまま同梱する案は、2022 年の 2 日が祝日でなくなるので退けました
- 名称は MOM の報道発表の綴り（英語のみ。アポストロフィは `’`。英国が GOV.UK の綴りをそのまま使うのと同じ）です。`names` は付けません（7・18 番）。data.gov.sg は年によって `'` と `’` が揺れるので、照合で読み替えます。Polling Day（選挙の投票日）は `special` です
- 監視は `govuk-watch.yml` を `data-watch.yml` に改名し、英国とシンガポールの照合を 1 回の起動で順に行います。別のワークフローにすると cron-job.org のジョブと healthchecks.io のチェックがもう 1 組要るためです。ハートビートは両方の照合が動いたときだけ送り、issue はラベルを分けて別々に立てます（`datagovsg-data`）。改名により cron-job.org の URL を 1 度直す必要があります（RELEASING.md）

## 46. 祝日を個別に指す識別子 `key` と絞り込み `keys`、提供元向けの振替の計算 `substituteDays`、内閣府 CSV の毎日の照合

0.18.0 で、5 通目の機能拡張提案のうち、既存の API を組み合わせても書けないもの 2 つと、品質の項目 1 つを入れました。あわせて、同じ提案書が指摘した決定の文書どうしの食い違い 3 点（RELEASING.md の区分の表、37 番の理由、44 番の理由）を直しました。

**祝日の識別子**（`Holiday.key`）**と絞り込み**（`{ holiday: true, keys: [...] }`）

- 祝日の規則の絞り込みは `kinds`・`weekdays`・`months` だけで、「どの祝日か」は指せませんでした。固定日の祝日は毎年の月日で、第 n 曜日の祝日は `{ weekday, nth, months }` で書けますが、春分・秋分の日（天文計算）、復活祭に連動する英国の 2 日、シンガポールの太陰暦・イスラム暦・ヒンドゥー暦の祝日は規則で書けず、年ごとに `dates` に列挙するしかありませんでした（33・41 番が規則の代わりとしては退けた形）。需要の例は、花屋・霊園の「祝日は定休だが彼岸の中日は営業」、英国のパブの「bank holiday は営業するが Good Friday と Easter Monday だけ休む」、シンガポールの個人商店の「Hari Raya だけ休業」、スケジュールの「海の日・山の日はプール料金を夏季料金に」です
- `nameEn` で判定する案は取りません。名称は公式データの綴りを写すデータで（18・44 番）、パッチ版で変わりうるので判定の根拠にできません（3・15 番の「メッセージの文言は API に含めない」と同じ考え方）。`key` は規則から祝日を指すための API で、提供元が決め、版をまたいで変えません。日付の移動や公式の改名があっても、同じ祝日なら同じ `key` です（天皇誕生日は 4/29・12/23・2/23 とも `emperors-birthday`、体育の日とスポーツの日は `sports`、布告で移った年の Early May bank holiday も `early-may`）
- **`key` の意味は「その日が観測している祝日」**で、国をまたいで同じにします（32 番の「国に依らない」と同じ姿勢）。付ける範囲は「法令・布告の区分として毎年繰り返し、`kind` では区別できない祝日」に限り、次の 2 つは省略します。種別と同じ情報しか持たないもの（日本の国民の休日。`kinds: ["citizens"]` で指せる）と、一度きりの日（日本の即位の礼など、英国の臨時の bank holiday、シンガポールの Polling Day。`dates` で書け、種別全体は `kinds: ["special"]` で指せる）です。年付きの識別子（`enthronement-2019` など）は使われない識別子とレビューの手間だけが増えるので付けません
- **振替日は 3 か国とも元の祝日の `key`** です（2020-02-24 の振替休日は `emperors-birthday`）。英国・シンガポールは名前も元の祝日なので `key` と `name` がそろい、日本は名前が「振替休日」なので `key ≠ name` になりますが、これは名前の側の非対称です。`substitute` という `key` にすると、提供元が計算している「どの祝日の振替か」を捨てて `kind` と同じ情報を 2 回返すことになります。元の `key` なら両方向に書けます: 「成人の日とその振替」は `{ holiday: true, keys: ["coming-of-age"] }`、「春分の日の当日だけ（振替の月曜は含めない）」は `{ holiday: true, keys: ["vernal-equinox"], kinds: ["national"] }`。前者は `substitute` という `key` では書けません
- **`key` の付け方の規則**: 最初に付けるときに、その時点の `nameEn` から導きます。小文字にし、空白をハイフンに、アポストロフィ・先頭の冠詞（"The"）・括弧書きを除き、末尾の "Day"・"bank holiday" を落とします。途中の冠詞は残します（`coming-of-age`、`respect-for-the-aged`、`early-may`、`st-patricks`、`constitution-memorial`、`emperors-birthday`、`battle-of-the-boyne`）。綴りは提供元の `nameEn` に従うので、日本は `labor-thanksgiving`、シンガポールは `labour-day` で、提供元をまたいでは揃えません。規則の結果が祝日を指さない一般語や複数形になる場合だけ例外を置きます。例外は次の 4 つです: `new-year`（"New Year’s Day" を `new-years` としない。国をまたいで同じ）と、`boxing-day`・`labour-day`・`national-day`（"Day" を落とすと `boxing`・`labour`・`national` になる）。**導出は最初の 1 回だけ**で、以後 `nameEn` が公式データに合わせて変わっても（3・18 番）`key` は変えません（`key` は API、`nameEn` はデータ。1966〜2019 年の体育の日（"Health and Sports Day"）も、同じ祝日の 0.18.0 の時点の名称 "Sports Day" から導いた `sports` です）。この規則は 0.18.0 で初めて付けるときの判断を残すもので、将来の提供元で同じ規則を当てて迷いを減らすためです。規則と例外を利用者向けに正確に書くのは `docs/providers.md`（英日）の 1 か所だけで、ガイドはそこを指します（0.22.1 で書き方を改めました。以前は「冠詞を除く」と書き、`emperors-birthday`・`battle-of-the-boyne` を例外に挙げていましたが、途中の冠詞を残す `respect-for-the-aged`・`battle-of-the-boyne` と両立せず、挙げた 2 つは先頭の冠詞・括弧書きの規則どおりの結果でした。ガイドと `docs/providers.md` もそれぞれ別の不正確な規則を書いていました。付いている `key` は変わりません）
- 提供元の検証（6 番）で確かめるのは文字列の形式（`/^[a-z0-9][a-z0-9-]*$/`）だけです。同じ年に同じ `key` が複数回現れることは正当で、2019 年の国民の休日は 4/30 と 5/2（間の 5/1 は即位の日）に分かれ（ただし国民の休日は `key` を持たない）、2020 年の振替休日は 2/24 と 5/6 に分かれ、旧正月の 2 日も同じ `key` です。一意性を検証すると同梱の提供元で偽陽性になるので、`key` は「集合に含まれるか」の判定にだけ使います。利用者の提供元・包んだ提供元が付けた `key` も複製・凍結して返します
- `keys` は `kinds`・`weekdays`・`months` との AND です。判定の段階は祝日の規則と同じ「祝日の上」（35 番）で、順番（12 番）は変えません。`holiday` 以外の規則に付けたら `invalid-option`（4 番）です。`key` を持たない祝日には当てはまりません
- 診断は、提供元の対応年に現れない `key` を `never-matches`（`kinds` と同じ扱い）、祝日の規則どうしの `shadowed` に `key` の集合の包含を加えます（41 番の `weekdays` と同じ）
- 型は `string` のままです。`Kind` のような型引数（42 番）を増やすと `Calendar`・`Schedule` から規則の型まで 2 つ目の引数が波及するので、補完のために各提供元に既知の値の型 `KnownJapaneseHolidayKey`・`KnownUkHolidayKey`・`KnownSgHolidayKey` を `@beta` で添えるにとどめます（型だけなのでサイズに影響しません）
- 互換性: 返すオブジェクトへの省略可能な項目の追加と、規則への省略可能な項目の追加だけです（RELEASING.md の約束の範囲）。`HolidayProvider` に必須の項目は増えません。`dayInfo` の結果を `deepEqual` で比べているテストは `holiday.key` が増えるので期待値に足す必要があります（43 番の `decidedByPath` と同じ移行の注記）。7 番（名称は公式の出典に限る）とは別のもので、`key` は翻訳ではなく識別子です

**提供元向けの振替の計算**（`substituteDays`。`bizdays-toolkit/provider`）

- 同梱の 3 つの提供元はいずれも週末に当たった祝日の振替を計算していますが（日本の振替休日、英国の substitute day、シンガポールの Holidays Act 第 4 条）、同じ計算を書く道具が公開されていませんでした。振替は「翌日も祝日ならさらに翌日」「同じ週末に 2 つの祝日が重なれば日付順に先へ送る」という連鎖を持ち、境界で誤りやすい部分です。43 番が `easterSunday` を公開した理由（同じ計算を 1 か所に置き、利用者に再実装させない。39 番）がそのまま当てはまります
- 定義: 入力を日付順に走査し、`rules` の曜日に当たる祝日ごとに、指定の向き（`"next"`・`"previous"`）で「入力の祝日でも、それまでに決めた振替日でも、`rules` の曜日でもない最初の日」を振替日にします。「`rules` の曜日でもない」を含めるのは、英国の附則が土曜日・日曜日の両方を飛ばす（Boxing Day が土曜日なら月曜日）ためで、日曜日だけを振り替える日本・シンガポールでは結果に影響しません。振替日自身は別の祝日の振替の対象になりません（どの国の法律でも振替の振替はない）。振替日は元の祝日の `key`・`names`・`confirmed` を引き継ぎ、`kind` は呼び出し側が与え、名称は省略時は元の祝日のもの（GOV.UK・MOM の流儀）で、変えるなら関数で与えます（日本の「振替休日」、米国の "(observed)"）。`original: "drop"` で週末の元の日を結果から外せます（GOV.UK の一覧は週末の日を載せない）
- `rules` を「曜日 → 向き」の形にしたのは、米国の連邦祝日（土曜日は前の金曜日、日曜日は次の月曜日）のように向きが分かれる規則を 1 回の呼び出しで書けるようにするためです。日本の祝日法 3 条 3 項（2 つの祝日に挟まれた日）のような国に固有の規則は含めず、需要が見えたら別に足します
- **同梱の提供元の内部は置き換えません。** 置き換えても利用者に見える利益はなく、照合済みのコードを動かすリスクだけが残ります。照合テスト（フィクスチャ）の役割は「公式データと一致しているか」であって、リファクタリングの安全網に使うものではありません。代わりに、公開する関数が照合済みの実装と同じ結果を出すことをテストで示します: 日本（2007 年以降の全年。2006 年以前の祝日法は「翌日が祝日なら振り替えない」という別の規則）、シンガポール（全年）、英国の 4 地域（2012〜2099 年。2023 年の Scotland は 18 番の `RENAMED` で割り当てだけ GOV.UK に合わせているので、日付だけを比べる）で、提供元の結果から振替日を元の日に戻した入力に `substituteDays` を当て、提供元の結果と一致することを確かめます
- 入力は検証します（配列であること、各要素が契約の項目を持つこと、同じ年であること、重複のないこと。43 番と同じ）。振替日は年をまたぐことがあり（12 月 31 日が祝日の国で日曜日なら翌年の 1 月 1 日）、提供元の `holidaysInYear` の契約（その年の日付だけ）との扱いは呼び出し側に任せ、文書に書きます。`@beta` で出します

**内閣府 CSV の毎日の照合**（`data-watch.yml`）

- 英国（19 番）とシンガポール（44 番）は毎日照合していましたが、日本は RELEASING.md の「毎年の作業」で 2 月に手で `pnpm verify:cao` を実行する運用でした。日本の祝日の変更は法改正で決まり急な発表はありませんが、2019〜2021 年には特別法で祝日の新設・移動が続き、内閣府の CSV は法の施行後に更新されました。また、CSV の形式・文字コード・列の変更は 2 月の作業まで気付けません（解析に失敗していても分からない）。19 番の「黙って監視が止まるのを防ぐ」は日本にもそのまま当てはまり、日本を除外する理由は書かれていませんでした

## 47. 月の第 n 営業日の規則 `businessDayOfMonth`、振替で曜日も飛ばす `skipWeekdays`

0.19.0 で、5 通目の機能拡張提案の残り 2 つ（P2・P3）を入れました。どちらも既存の規則の形では書けず、年ごとに日付を列挙するしかなかったものです（33・41 番が規則の代わりとしては退けた形）。

**月の第 n 営業日**（`{ businessDayOfMonth: n }`）

- 需要の例は、銀行の支店の「月末最終営業日と月初第 1 営業日は来店予約を止める」、経理の「第 5 営業日は締め処理で電話受付のみ」、倉庫の「月末最終営業日は棚卸しで出荷停止」、スケジュールの「最終営業日は短縮営業」です。`{ day: -1 }` は暦の末日、`{ weekday: 5, nth: -1 }` は最終金曜日で、末日が月曜日なら最終営業日と 4 日ずれます。`nthBusinessDayOfMonth`・`lastBusinessDayOfMonth` は問い合わせで、設定の規則ではありません
- **項目名は `businessDayOfMonth`** にしました（提案書は `businessDay`）。`closedRecurring: [{ businessDay: -1 }]` と `dayInfo(d).businessDay === false` が同じ画面に並ぶと、同じ語が「月の何番目の営業日か」と「営業日かどうか」の 2 つの意味を持ちます。型は `number` と `boolean` で別なので実行時の誤りにはなりませんが、`{ businessDay: true }`（「営業日なら」のつもり）のような書き間違いは `unknown-option` で捉えられません。41 番で `weekdays`（絞り込み）と `weekday`（規則）を区別したのと同じ種類の問題です。`businessDayOfMonth` は位置を表す名詞として読め、メソッド名 `…BusinessDayOfMonth` と語が揃うので両者の関係（下記）を 1 文で説明でき、既存の `day`・`weekday` より長いのは、規則の中で唯一「数える」形なので目立ってよい、という理由です。`nthBusinessDay` は `-1` と "nth" の組み合わせが読みにくく、`weekday` + `nth` の既存の形とも混ざるので取りません
- **数える基準は、そのカレンダーの繰り返しの規則をすべて除いた判定**（個別の日付 → 毎年の月日 → 祝日（`holidayPolicy`）→ 定休日の曜日）です。0.15.0 時点の提案書が「カレンダー自身の規則に『最終営業日は休業』と書くと最終営業日が前にずれて定義が循環する」としてスケジュール限定にしていた問題は、基準を規則の結果に依存させるから起きるもので、設定の定数部分に固定すれば閉じます。利用者が「月末最終営業日は出荷停止」と言うときの「最終営業日」は土日祝と年末年始を除いた暦上の日で、「出荷停止の規則を適用した後の最終営業日」ではありません。14・33 番が「祝日は提供元の祝日だけ」で振替先・祝日の翌日を決めたのと同じく、「設定の定数で決まる部分だけ」を基準にします。この定義で年末年始休業（`closedAnnual`）や臨時休業日（`closedDates`）は数えから外れ、12 月 30 日が最終営業日になります
- **メソッドとの関係は名前で示す。** `nthBusinessDayOfMonth`・`lastBusinessDayOfMonth` は規則を適用した後の実際の営業日を返すので、`{ businessDayOfMonth: -1 }` を休業にすると `lastBusinessDayOfMonth` は前日を返します。これは「最終営業日が休みなら実際の最終営業日はその前日」という当然の結果で、直すべき不整合ではありませんが、名前が同じ語だと「同じものを指すはず」と読まれるので、文書に書くだけでなく項目名で数え方の違いを示します（上の項目名の理由の 2 つ目）
- **定義の限界**: 定休日を `closedRecurring` の曜日の規則で書いている設定（30 番の「期間付きの定休日の変更」など）では、その曜日も営業日として数えます。文書に明記し、診断で「`businessDayOfMonth` の規則と、同じ設定の毎週の曜日の規則（`{ weekday }` で `nth`・`interval`・`months` のないもの）が同居する設定」を info の新しい code `counting-basis` で知らせます（`redundant` とは別の意味なので別の code）
- **判定の段階と `onHolidayRule`**: 繰り返しの規則の段階（12 番の 6。`"over-holiday"` なら 4）で、配列の順番どおりです。`onHolidayRule` は他の繰り返しの規則と同じく `"under-holiday"`（既定）と `"over-holiday"` を受け、`"after-holiday"` だけを `invalid-option` にします（営業日の数え方の結果をずらす意味がない）。提案書は `onHolidayRule` をすべて `invalid-option` としていましたが、`holidayPolicy: "open"` のカレンダーでは祝日も営業日として数えるので第 n 営業日が祝日に当たることは正当に起こり、既定ではその日は祝日の段階が先に決めてこの規則は当てはまりません（曜日の規則 `{ weekday: 1 }` が祝日の月曜日に当てはまらないのと同じ優先順位で、この規則だけの特別扱いはありません）。「第 1 営業日は棚卸しで休業。祝日でも」と書きたい利用者には書く手段が要り、祝日の規則 `{ holiday: true, keys: [...] }` では「その祝日が第 n 営業日に当たるとき」という条件が表せないので、`"over-holiday"` で書けるようにしました。12 番の「規則が段階を選ぶ」設計にそのまま乗る形です。`holidayPolicy: "closed"` では当てはまる日が祝日になりえないので `"over-holiday"` は結果を変えない no-op で、診断が `redundant`（info。path は `….onHolidayRule`）で知らせます
- **効率**: その月の 1 日から末日までを基準で数えるだけで、月あたり高々 31 日の判定です。基準は月ごとにキャッシュします（`basisFromPredicate`。上限を超えたら捨てる単純な Map）。37 番の「営業日表のキャッシュは入れない」は判定の全体に対するもので、ここでは 1 つの規則が自分の月を数えるための局所的なもので、判定は入力の値だけで決まります
- **スケジュール**: スケジュールには営業・休業の概念がなく（38 番の `isOpen` は作成後に与えられる）、スケジュール単体では数える基準が決められません。0.15.0 の提案書のとおり、作成済みの `Calendar` を規則の `calendar` で参照する形にします（必須）。基準はそのカレンダーの実際の営業日（`isBusinessDay`。規則を適用した後）です。設定に作成済みのオブジェクトの参照を持つのは `holidays` に提供元を持つのと同じ性格で、5 番の範囲です。`calendar` のタイムゾーンはスケジュールと同じでなければなりません（`time-zone-conflict`。34 番の合成と同じ理由）。`createCalendarFromSchedule` でそのスケジュールからカレンダーを作ることはできます（参照先は別のカレンダーなので循環しません）。カレンダーの側の規則には `calendar` を付けられません（`invalid-option`。基準は自分の設定で決まるため）。診断では `calendar` は不透明な値として扱い、`shadowed` は同じ `calendar` を参照する規則どうし（n・months・有効期間の包含）に限ります
- **診断**: `never-matches`（その月にない回。`businessDayOfMonth: 24` は 24 営業日ある月が存在しないので常に当てはまらない。基準は祝日次第で年ごとに違うので、祝日の規則と同じく調べる期間の全日を走査する）、同じ形の規則どうしの `shadowed`、種類をまたぐ重なりは `redundant`（15 番の考え方）
- 型は `BusinessDayOfMonth = number`（1〜31 と -1〜-31 の 62 値のリテラル型は重いだけ）で、`BusinessDayOfMonthPattern` を `RecurringPattern` の合併型に足しました。`calendar` は型では「省略可能」としか書けず（カレンダーとスケジュールで規則の型を分けていない）、スケジュールで必須・カレンダーで不可は実行時の検証です

**振替で曜日も飛ばす**（`skipWeekdays`）

- 14 番は「振替先は『その日以降で最初の祝日でない日』で、土曜日・日曜日を飛ばさない。規則自身に飛ばす曜日を書く設定は、需要が見えるまで足さない」と保留していました（0.9.1・0.15.0 の提案書でも 2 度言及）。需要として示されたのは、月曜定休の店の振替先（年 0〜1 回。列挙で足りる）ではなく、日本の企業で広く見られる就業規則の文言「6 月 15 日は創立記念日で休業。土曜日・日曜日・祝日に当たる場合は翌月曜日（翌営業日）を休業日とする」のように**毎年必ず起きる**ものです。0.18.0 で確かめると、`closedWeekdays: [0, 6]` と `{ day: 15, months: [6], onHolidayRule: "after-holiday" }` の組み合わせで、6 月 15 日が土曜日の 2030 年は 15 日が `closed-weekday`（もともと休み）、17 日（月）は `regular` で、創立記念日の休業が消えます。33 番が祝日の翌日を規則にした理由（規則であるべきものを結果として書くことになる）がそのまま当てはまります
- 意味: `skipWeekdays` は `"after-holiday"` の曜日・日の規則と組でだけ使えます。規則は「本来の日が祝日か `skipWeekdays` の曜日なら、その日以降で最初の、祝日でも `skipWeekdays` の曜日でもない日に当てはまる」になります。14 番の「振替の判断は提供元の祝日だけで、利用者の休業日の設定（`closedWeekdays` など）は見ない」は保ちます。飛ばす曜日は規則自身に書くので、設定の読みやすさ（どの設定が振替先を変えたか）も保たれます。`shiftedFrom` は本来の日、有効期間は本来の日で判定します（30 番）。振替先が別の規則の日と重なれば、配列で先に書いた規則が決めます（33 番と同じ）
- ほかの値との組み合わせ: `"under-holiday"`・`"over-holiday"`・祝日の規則・祝日の前後の規則・第 n 営業日の規則に付けたら `invalid-option`（4・33 番）。`onHolidayRule` を省略した規則（既定の `"under-holiday"`）に付けた場合も `invalid-option` です。曜日の規則で、その曜日自身を `skipWeekdays` に含めたら `invalid-option`（毎回振り替える規則は意図が読めない）
- 名前: `weekdays`（絞り込み。41 番）と区別するため `skipWeekdays` にしました。`onHolidayRule` の値を増やす案（`"after-closed-weekday"`）は曜日の集合を書けないので取りません
- 診断: `shadowed` の包含判定に `skipWeekdays` の一致を加えます（飛ばす曜日が違えば当てはまる日が違うので覆いません。違う規則どうしの重なりは `redundant` で見つかります）
- `skipWeekdays` のない `"after-holiday"` の結果は変わりません。14 番の表題（振替先は「その日以降で最初の祝日でない日」）は、`skipWeekdays` のない規則については変わらず、同番に追記しました

**監視の報告書の日付**（版の変更なし）

- `verify-govuk.ts`・`verify-datagovsg.ts`・`verify-cao.ts` の「確認した日付」（報告書の 1 行目・フィクスチャの「取得」）は UTC の日付でした。issue のコメントの日付（`TZ=Asia/Tokyo date`）と基準が違ったので、3 つを同時に日本時間に揃えました（`Intl.DateTimeFormat("en-CA", { timeZone: "Asia/Tokyo" })`）

（0.22.0 で追記: `skipWeekdays` を祝日の翌日・祝前日の規則にも付けられるようにしました。「振替先と同じ定義」（33 番）を共有する規則に同じ項目を付けるもので、意味は「祝日と書いた曜日が続く塊の前後の日」です。53 番）

## 48. フランスの祝日（`bizdays-toolkit/fr`。本土と Alsace-Moselle）と、4 か国目の選び方

0.20.0 で 4 か国目の提供元としてフランスを足しました（5 通目の提案の P5。改定版で香港から変更）。

**選定の基準**: 次の提供元を足すときにも使えるよう、5 通目の提案書で挙げた 3 つの条件を基準に書き残します。

1. 公式データと全日照合できること（照合できなければ「公式データで全日照合」という約束（19・44 番）を守れない）
2. 利用者層の重なり（このライブラリの利用者が扱う国。香港は日本の企業の拠点として多いが、下の理由で見送った）
3. 実装と保守の重さ（規則で計算できるか、年ごとの表か。年ごとの告示の有無。振替の規則の複雑さ）

**候補の比較**:

- **香港**: data.gov.hk の「Hong Kong Public Holidays Data」（Digital Policy Office・1823・JSON）は実在し、1 を満たしますが、データセットの作成が 2024 年で過去の版で遡れるのは 2023 年分まで、それより前は官報（Government Gazette）での照合になり、英国より重い作業でした。太陰暦の祝日は年ごとの表になり（シンガポールと同じ）、3 を満たしません。1 のための作業量の割に照合できる年数が少ないので見送りました（需要が示されれば表の提供元として足せる）
- **米国**: 連邦祝日は規則で計算でき、"observed" の振替は 0.18.0 の `substituteDays` で書けますが、連邦政府の公式な機械可読データ（OPM の一覧は HTML）がなく 1 が弱く、州ごとの祝日の違いが大きい
- **ドイツ**: 州ごとに祝日が違い（16 州）、連邦の公式な機械可読データがない
- **フランス**: DINUM が data.gouv.fr で「Jours fériés en France」を公開し（Licence Ouverte 2.0）、ゾーンごとの JSON（`{ "YYYY-MM-DD": "名称" }`）が過去 20 年・未来 5 年の窓で得られます。祝日は労働法典 L3133-1 の 11 日で、固定日 8 日と復活祭からの日数 3 日なので規則で計算でき（英国と同じ型）、振替はなく、年ごとの告示もありません。1〜3 をすべて満たし、約 26 年分を照合できます

**設計**:

- 提供元は `metropole`（ID `FR`）と `alsaceMoselle`（ID `FR-AM`）の 2 つ。data.gouv.fr のゾーンに対応します。Alsace-Moselle（Bas-Rhin・Haut-Rhin・Moselle の 3 県）には ISO 3166-2 のコードが 1 つなく（Grand Est の `FR-GES` は範囲が広すぎる）、県の列挙（`FR-57-67-68`）は読めないので、このライブラリの ID として `FR-AM` を決め、ISO でないことを文書に書きます。海外県・海外領土は祝日もタイムゾーンも違い（data.gouv.fr に 11 ゾーン）、需要が見えるまで同梱しません
- 名称は data.gouv.fr の表記（`1er mai`・`Lundi de Pentecôte`。18 番の「公式データの綴りを写す」）、`nameEn` はライブラリの英訳、`key` は英語名から 46 番の規則で導きます（`labour-day`・`pentecost-monday`・`victory-in-europe`・`bastille`・`all-saints`・`saint-stephens` など）。Lundi de Pentecôte の英語名は "Whit Monday" も一般的ですが、`key` を提案書の `pentecost-monday` に合わせ、英語名も "Pentecost Monday" にしました
- `kind` は `regular` だけです（振替も臨時の祝日もない）。将来の値の追加に備えて型は開いたままです（42 番）
- **2 つの祝日が同じ日に当たる年**（復活祭が 3 月 23 日なら Ascension が 5 月 1 日 = 2008 年、3 月 30 日なら 5 月 8 日 = 2059 年）は、提供元の契約（1 日に 1 件。6 番）に従い、復活祭から決まる祝日の名称・`key` で 1 件を返します。data.gouv.fr の JSON（date → name の写像）も同じ日付に Ascension を載せており、照合の対象に合わせました。`keys: ["labour-day"]` が 2008 年の 5 月 1 日に当てはまらない点は文書に書きます
- **すべての年が `confirmed: true`** で、`confirmedThrough` は持ちません。日本の春分・秋分の日（官報）や英国の bank holiday（GOV.UK の公表・布告による移動）と違い、フランスの祝日は法令で定まり、年ごとの告示や移動がありません。変わるのは法改正のときだけで、それは予測ではなく反映の対象です（パッチ版）。対応年は 2000〜2099 年（復活祭の計算は 43 番の `easterSunday`）
- **連帯の日**（journée de solidarité。2004 年の法で、Lundi de Pentecôte を出勤日にする企業が多い）: 法律上は祝日のままで（労働法典 L3133-1 にある）、出勤日にするかは企業の取り決めなので、提供元は祝日として返し、例外は祝日の規則 `{ holiday: true, keys: ["pentecost-monday"] }` で書きます。「祝日を休みにするかは利用者が決める」というライブラリ全体の分担（9 番）のとおりで、0.18.0 の `key` がちょうどこの用途を満たします
- **照合と監視**: data.gouv.fr が「安定した URL」として案内する公式のエクスポート（`https://etalab.github.io/jours-feries-france-data/json/{zone}.json`。DINUM の生成）を照合に使います。`calendrier.api.gouv.fr` も同じ生成物を配信していますが、データセットのページが案内する URL を正とします。`scripts/verify-datagouv.ts` を英国・シンガポール・日本と同じ形（`--report`・`--simulate`、終了コード 0・1・2）で書き、`data-watch.yml` に 4 つ目の照合として足しました（ラベル `datagouv-data`）。JSON の窓は毎年 1 月に 1 年ずつ動くので、そのときはフィクスチャの差分だけが出る想定で（版は要らない）、RELEASING.md に書きました。「公表済みの年」の節はありません（年ごとの告示がないため）

## 49. 英国の対応年を 1974 年まで広げる（GOV.UK のない年は「公表された一覧があればそれが正、なければ The Gazette の布告が正」）

0.21.0 で、英国の 4 つの提供元の対応年を 2012 年から 1974 年に広げました（5 通目の提案の P6。マイナー版）。出典の収集は 2000〜2011 年（段階 1）、1978〜1999 年（段階 2）、1974〜1977 年（段階 3）の順に行い、1 つの版にまとめました。

- **なぜ 1974 年か**: 英国の bank holiday は Banking and Financial Dealings Act 1971 の Schedule 1（毎年の日）と、年ごとの国王の布告（週末に当たった日の振替、毎年指定される日、臨時の祝日、移動）で決まり、布告は The Gazette に載ります。England・Wales・NI の New Year's Day は 1974 年から、Early May は 1978 年から、Scotland の Spring bank holiday（5 月最終月曜日）は 1978 年から、Scotland の Boxing Day は 1974 年（布告で見つかった最初の年。Hansard は 1973 年と答弁しているが、その布告は見つからない）から、毎年布告されています。1974 年より前は、England・Wales・NI と Scotland 向けの Royal Proclamation が見つからず（1972・1973 年）、1971 年は 1871 年法の下にあるので、布告で全日を照合できる下限が 1974 年です。提供元の `year >= 1974`・`year >= 1978` の条件は、附則の変更ではなく「毎年布告される日が増えた」慣行の始まりを符号化したもので、New Year's Day は今も附則にはなく毎年の布告です
- **GOV.UK のデータは 2012 年から**: alphagov/calendars の履歴を確かめると、最初のデータは 2012 年分で、それより前の年は一度も入っていません。18 番が 2012 年を下限にしたのはこのためで、2000〜2011 年には GOV.UK に代わる正が要ります
- **正は当時の政府の公表一覧、布告は照合の第二の出典**（方針 B。一覧のない年は布告が正）。候補は 2 つありました。A: 布告（法）を正にする。B: 当時の政府の一覧（DTI・BERR・directgov・Scottish Executive/Government・nidirect。Wayback Machine の保存）を正にする。B を採った理由は、(1) ライブラリの原則がすでに B であること（18 番は GOV.UK の一覧を「そのまま」使い、2023 年の Scotland の割り当てが規則と違っても GOV.UK に合わせた。44 番も data.gov.sg と MOM が食い違えば MOM の公表を正にした。2000〜2011 年だけ「布告が正」に切り替えると原則が年で変わる）、(2) 営業日ライブラリの用途では実務が正であること（2010 年・2011 年の 1 月 4 日に Scotland の銀行は閉まり、他のあらゆる記録もその日を祝日とした。A では日数計算が世間と 1 日ずれ、得られるのは法形式の正しさだけ）、(3) 出典を 2 層にすれば「The Gazette で照合が閉じない」懸念は解けること、です。したがって約束は「当時の政府の公表一覧を正とし、布告で全日を照合する」で、2012 年以降（GOV.UK が正、規則で照合）と同じ形です。**一覧が存在しない年**（1974〜1997 年。政府の Web の一覧は 1998 年以降にしかなく、Wayback の最初の保存は 2000 年）は、Schedule 1 と布告が唯一の公式の出典として正になります。これは方針を年で変えるものではなく、方針 B の「一覧があればそれが正」の自然な帰結です。その年に Hansard の書面答弁（翌年の日付の発表。1976〜1995 年に断続的にある）があれば第二の出典として記録し、日付の食い違いはありませんでした
- **1974〜1999 年のフィクスチャ**（`test/fixtures/uk-1974-1999-proclamations.json`）は、年・区分ごとに布告・Order で指定された日（追加か、どの日の代わりか）と出典（号・頁または notice ID）を持ちます。テストは、Schedule 1 とコモン・ローの休日をライブラリとは別に書いた規則で計算し（復活祭の日付もフィクスチャの表から取り、ライブラリの `easterSunday` を使わない。表は米国海軍天文台の計算で、米国国勢調査局と NOAA の表、Hansard の 1977・1992 年の Good Friday の日付と一致）、それに布告の日を足した集合が提供元の結果と一致することを確かめます（26 年 × 3 区分）。布告が見つからなかった日は `unverified` に記録し、規則どおりに返します: 1987 年分の毎年の布告（1986 年に出るはずのもの。London・Edinburgh・Belfast のどの検索にもなく、Privy Council Office の告示の形の語でも見つからず、Hansard は "To be declared by royal proclamation" とする）と、北アイルランドの Order（1986〜1990 年の 7 月 12 日、1990 年 3 月 17 日の振替、1975 年の 7 月 12 日）です。これらは「布告がなかった」と確かめられたものではありません。1986〜1990 年の北アイルランドの Order は The Gazette のオンラインにない号に載っているもので（The Gazette の「Missing Gazette issues」が Belfast Gazette の 4660〜5171 号（1985-12-27〜1991-01-04）をオンライン未収録として一覧し、オフラインでは保有している）、1987 年分の布告は、出るはずの時期に London Gazette のオンラインにない号（50761〜50763・50779〜50790 号。1986-12-30〜1987-01-02）がありますが、その号に載っているかは確かめられていません。1975 年の Order はオンラインの号の範囲で見つからなかったものです（0.21.3 で書き方を改めました。以前は 1975 年の Order と 1987 年分の布告もオンラインにない号に載っていると書いていました）。いずれも毎年の慣行が途切れていないので祝日として返します。`unverified` は日付の確からしさで 2 つに分けています: 日付そのものに選択の余地がない 9 件（`fixed`）と、土日に当たった日の振替先を、見つかった Order がすべて翌月曜日に振り替えていることから推定した 4 件（`substitute-inferred`: 1975-07-14・1986-07-14・1987-07-13・1990-03-19）で、後者は欠けている号が復元されたときに確かめる対象です。Scotland の土曜日の祝日（1 月 1 日・2 日・12 月 25 日が土曜日の年）は 1974〜1999 年のすべてで指定が見つかり（`unproclaimed` は空）、2010・2011 年の抜けが例外であることが確かめられました
- **出典の 2 層をフィクスチャに記録**: `test/fixtures/uk-2000-2011-government-lists.json` は、年・区分ごとに当時の一覧の日付と表記、その Web Archive の URL（取得日時つき）、対象期間の布告・Order の一覧（notice ID または号・頁）を持ち、各年の `record` が収集の記録（`docs/sources/uk-bank-holidays-2000-2011.md` のその年の節）を指します。「布告がない」ことが一覧との食い違いとして見えたのは一覧があったからなので、一覧のない年の範囲（段階 2 以降）では、Scotland の土曜日の祝日に布告も一覧も見つからなかった場合を `unproclaimed`（祝日にしていない）として明示的に書き、沈黙と区別できるようにしてあります（2000〜2011 年は空）。出典の収集の記録（検索した URL、見つからなかったもの、布告の原文の転記、年ごとの照合）は `docs/sources/uk-bank-holidays-2000-2011.md` に残しました。2001 年の Scotland だけは当時の一覧が見つからず（DTI は 2000 年まで、Scottish Executive の FAQ は電話番号の案内のみ）、Schedule 1 と布告（5 月 28 日・12 月 26 日）から組み立てています
- **布告のない 3 日**: Scotland の 2010-01-04・2011-01-04（Matthew Somerville 氏が 2014 年にスコットランド政府の確認を得たもの。Schedule 1 は土曜日に当たった 1 月 1 日・2 日を振り替えず、布告も作られなかった）と、今回の収集で新たに見つかった 2010-12-27（12 月 25 日が土曜日。布告は 28 日を追加しているだけで、27 日を指定するものがない。同氏の記事にはない）は、「布告がない」とは The Gazette の 4 種類の検索（通知検索・種類だけの検索・版ごとの紙面検索・code 1106）で見つからなかったという意味で、記録にそう書いてあります。いずれも 1971 年法の文言どおりなら bank holiday ではありません。方針 B に従い、当時の政府の一覧どおり `substitute` の祝日として返し、フィクスチャの `knownDifferences` に出典つきで記録しました。同じ曜日の並びの 2000 年・2005 年には布告があり（1 月 4 日を 1 月 1 日の代わりに）、2010・2011 年だけが例外であることも確かめました
- **振替日の割り当てが今と違う年**: 当時の一覧と布告は、振替日の名前の割り当てが今の GOV.UK の流儀と違う年があります。12 月 25 日が土曜日の年（1976・1982・1993・1999・2004）は 27 日が Boxing Day（Schedule 1 の「25・26 日が日曜日の年の 27 日」）で 28 日が Christmas Day の代わりです。ただし割り当ての文言があるのは 1982・1999 年の Scotland の布告（"in place of Saturday, 25th December"）、2004 年の政府の一覧、1976 年の Hansard 1976-07-27 だけで、1993 年（Scotland は 27・28 日とも追加）と England・Wales・NI の 28 日（布告はどの日の代わりかを書かない）は、文言のある年の割り当てに揃えたものです。名前はデータなので結果の日付には影響しませんが、年ごとの根拠の強さの違いは出典の記録の付録 C に残しています。GOV.UK は同じ並びの 2021 年で 27 日を Christmas Day、28 日を Boxing Day とします。1 月 1 日が土曜日の年の Scotland（1977・1983・1994・2000・2005）は 3 日が 2nd January（附則）で 4 日が New Year's Day の代わり（布告）。GOV.UK は 2022 年で逆です。12 月 25 日が日曜日の年の Scotland（1977・1983・1988・1994・2005）は 26 日が Christmas Day（附則）で 27 日が Boxing Day（布告）。2011 年は directgov・Scottish Government・nidirect のいずれも 26 日を Christmas Day、27 日を Boxing Day の振替とします。これらは 18 番の `RENAMED`（2023 年の Scotland）と同じ仕組みで、日付はそのままに名称・種別・`key` を当時の一覧に合わせます（`RENAMED` は区分の配列を取る形に広げた）。利用者が `key` で指す場合に影響するので、文書に書きました
- **週末に当たった祝日を載せない約束**: 提供元は土曜日・日曜日に当たった祝日を結果に載せません。これは GOV.UK の一覧の慣行（2015 年 12 月 26 日（土）の件で確かめた、週末の日を載せず振替日だけを載せる流儀）に合わせたライブラリの約束で、附則の帰結ではありません。附則は 12 月 26 日を「日曜日でなければ」としか書かず、土曜日の 26 日は法律上 bank holiday のまま残り、追加（section 1(3)）としてしか布告されなかった年の土曜日（Scotland の 1988 年 1 月 2 日、1993 年 12 月 25 日、1994 年 1 月 1 日、1976 年 12 月 25 日）も同じです。テストの「附則を独立に計算する」規則はこの約束を共有しており、その旨をテストのコメントに書いています
- **臨時の祝日の名称**: 布告は日付と地域だけを指定し、名称を持ちません。`name` は公式の出典の呼び方に限る（7 番）ので、政府の答弁の呼び方を日ごとに確かめました。1977 年は Hansard 1975-12-18 の公式プログラム "Tuesday 7th (Silver Jubilee Bank Holiday)" と 1977-01-19 "a special Silver Jubilee Bank Holiday"、1981 年は The London Gazette 48690（1981-07-27）の官報事務所の告示の見出し "ROYAL WEDDING BANK HOLIDAY PUBLISHING ARRANGEMENTS 1981" と、Hansard 1981-07-30（環境大臣の答弁本文）"the public holiday on 29 July for the Royal Wedding"、1981-05-06 の見出し "Royal Wedding (Public Holiday)" があり、それぞれ "Silver Jubilee bank holiday"・"Royal Wedding bank holiday" としました。1995 年 5 月 8 日の Scotland（政府は "an additional day's bank holiday" とだけ呼ぶ）と 1999 年 12 月 31 日（"a one-off additional Bank Holiday"。"Millennium" は質問と Hansard の見出しにあるだけ）は固有の名称が公式の文書になく、中立の "Additional bank holiday" に、政府の答弁が述べた理由を括弧で添えました: "Additional bank holiday (VE Day 50th anniversary)"（Hansard 1993-12-16 の "commemorating the 50th anniversary of the ending of the second world war"）と "Additional bank holiday (Millennium)"（Hansard 1998-06-03 の "the year 2000 will be heralded by"）。括弧で理由を添える形は GOV.UK が 2020 年に用いた "Early May bank holiday (VE day)" と同じで、固有名を発明せずに何の日かを示せます（0.21.0 では括弧なしで出し、0.21.1 で添えた）

## 53. 日単位の周期の規則と、祝日の翌日・祝前日の絞り込み・`skipWeekdays`

0.22.0 で、6 通目の機能拡張提案（提案書（乙））の P1 と、決定の文言と衝突するため提案から外されていた 3 案（E1〜E3）のうち 2 つを入れました。

**日単位の周期の規則**（`{ cycle, anchor, positions }`）

- 4 勤 2 休のような交替制や、10 日に 1 度の点検日は、7 日周期の曜日の規則でも、n 週おきの規則（30 番。周期は 7 の倍数）でも書けず、年ごとに `closedDates` に列挙するしかありませんでした（33・41 番が規則の代わりとして退けた形）。個別の日付は毎年の月日より優先される（12 番）ので、「年末年始は全面停止」との順番も崩れます
- 意味: 起点（`anchor`）を 1 日目として `cycle` 日ごとに繰り返し、`positions` に書いた何日目かに当てはまります。提案書は 0 始まりの `phases` でしたが、1 始まりの `positions` にしました。このライブラリの位置を表す項目（`day`・`nth`・`businessDayOfMonth`）はすべて 1 始まりで、提案書の例自身も 0 始まりの位置 4（5 日目）を「4 日目」と書いていたように、0 始まりは読み違いを招きます。`days` は `day` と紛れるので避けました
- `anchor` は必須です（30 番の `interval` と同じく、位相を決めるだけで、起点より前の日にも当てはまる。開始日は `effectiveFrom`）。`cycle` は 2 以上の整数、`positions` は 1〜`cycle` の重複のない配列で、空とすべての日は `invalid-option`（30 番が `interval: 1` を退けたのと同じ理由）。ほかの形の項目（`weekday`・`day`・`weekdays` など）との同居は `invalid-option`（4 番）です
- `onHolidayRule` は `"under-holiday"`（既定）と `"over-holiday"` で、`"after-holiday"` は `invalid-option`（周期の日を祝日の後ろへずらす意味がない。47 番の `businessDayOfMonth` と同じ判断）。判定の段階（12 番）は他の繰り返しの規則と同じです
- 診断: `shadowed` は周期の規則どうしだけで調べ、後の周期が先の周期の倍数で、後の規則のどの日も先の規則の日に当たるときに覆うとみなします（周期が異なる曜日・日の規則との重なりは `redundant`。15 番の考え方）。`redundant` の走査の範囲は、15 番の `interval` と同じく周期と 28 年の最小公倍数まで広げます（上限 200 年）

**祝日の翌日・祝前日の `kinds`・`keys`**

- 旧正月の前日（シンガポールの半日営業）、Good Friday の前日、春分の日の前日のように、日付が毎年動く祝日の前後は、年ごとの列挙しか手段がありませんでした。46 番で `key` を足した目的（規則で書けない祝日を規則で書く）が、前後の日について残っていました
- 46 番の「`holiday` 以外の規則に付けたら `invalid-option`」は、0.18.0 の時点で前後の規則に付ける意味を検討しなかったための制限で、前後の規則は「祝日に従属する規則」（33・43 番）なので、祝日を指す絞り込みが付くのは自然な拡張です。`kinds` も同じ定義なので一緒に入れ、絞り込みの項目を祝日の規則とそろえました（35 番の書き方の方針）
- 絞り込みは隣の祝日に当てます（祝前日なら翌日の祝日、祝日の翌日なら前日の祝日）。連休のどれかを見る案は寛容ですが、「こどもの日の前日」が 5 月 2 日になるなど、意図とずれる結果を黙って返します。隣の祝日だけを見れば今の定義をそのまま延ばせ、当てはまらない設定は既存の `never-matches` で見つかります

**祝日の翌日・祝前日の `skipWeekdays`**

- 英国の bank holiday の大半と、日本の月曜日の祝日では、祝前日が日曜日になり、「連休前の最終出荷日」のような最も需要のある形が書けませんでした
- 33 番は祝日の翌日を「振替先（14 番）と同じ定義」とし、47 番の `skipWeekdays` はその振替先の定義を「祝日でもなく、書いた曜日でもない日」に変える項目です。同じ定義を共有する前後の規則に同じ項目を付けました。意味は「祝日と書いた曜日が続く塊（祝日を 1 日以上含む）の前後の日」で、祝日を含まない普通の週末は塊になりません。`kinds`・`keys` は塊の中でその日に最も近い祝日に当てます（上の「隣の祝日」を塊に延ばしたもの）
- 規則に書いた曜日だけを見て、カレンダー自身の休業日は見ないので、14 番の「提供元の祝日だけ」は保てます。43 番が退けた「飛び石連休の間の日」（カレンダー自身の結果に依存する）とは性質が違います。すべての曜日は `invalid-option`（塊が終わらない）です

**前への振替（`onHolidayRule: "before-holiday"`）は足さない**

- 「15 日が祝日なら前日に繰り上げ」は、12 番の状態の数そのものを変えます。前倒しの需要の中心である「支払日・締め日が休日なら前営業日」は、`adjust`・`closingMonth` の `convention: "preceding"`（16 番）で日付の計算として書けます。カレンダーの休業日を前倒しする需要の例は弱く、示されるまで足しません（14・33 番の姿勢）

**提供元向けの関数と識別子の型を `@public` にする**

- `bizdays-toolkit/provider` の関数（43・46 番）と `Known…HolidayKey` の型は、公開してから（0.16.0〜0.20.0）形が変わらず、同梱の 4 か国の実装で使われ方が固まりました。`key` は 46 番で版をまたいで変えないと約束しているので、型の安定度もそろえて `@public` にしました。新しい国の key は型に値を足すだけで、互換性の約束の範囲です
- 非推奨の API（32・37 番）は 1.0.0 で削除する前提を変えず、移行ガイドに削除予定の一覧を 1 か所にまとめました

サイズは、ルートが 15,438 → 16,074 バイト、`./jp` が 17,654 → 18,293 バイト、`./diagnose` が 20,648 → 21,445 バイト（いずれも gzip）に増え、3 つの上限を上げました。

## 54. 公開する名前の規則を先に決め、0.30.0 ですべての名前を規則に合わせる

名前の揺れ（`businessDaysBetween` が数を返し、`listBusinessDays` が一覧を返すなど）は、名前の付け方の規則を最初に決めていなかったことが原因でした。1.0.0 の前に一度だけ、規則を先に作ってから、すべての名前を規則に合わせて改めます。

- 規則（N1〜N9）・用語集・外部の名前の出典は `etc/naming.md` に置き、`scripts/check-names.ts` がビルド済みの型定義に当てて確かめます。過去の経緯は考慮せず、名前を許す一覧（例外）は持ちません。対象は export・項目・メソッド・引数・型引数・文字列の値のすべてです
- 規則から機械的に決まらない新しい名前（`rulePath` → `optionPath`、`invalid-month-day` → `invalid-annual-date`）は、N1 の意味の重なりとしてレビューで決めました
- 改名した設定のキーと値の表は `src/core/renamed.ts` の 1 か所に置き、検証の入口での読み替え・診断の `deprecated-option`・移行の関数がこの表だけを使います。0.30.x の間は旧名を受け付け、旧名と新しい名前の両方を書くと `invalid-option` です。旧名の関数・メソッド・型・返す項目は `@deprecated` の別名として残し、すべて移行ガイドの削除予定の表に修飾名で載せます。設定の型が旧名のキーを持つのは省略可能なキーだけで、必須のキー（`weekly`・合成の `businessDay`・期日の `day`・振替の `rules`）と規則の `day` は実行時だけ受け付けます
- 位置を表す文字列（`optionPath`・診断の `path`・例外のメッセージ）は、旧名で書いた設定でも新しい名前で返します。`deprecated-option` の `path` だけは、利用者が書いた旧名の位置です
- 型と実行時の一致（33・43 番）は新しい名前についての約束で、旧名の経路は 1.0.0 で消えます

**規則の要点**（本文は `etc/naming.md`）

- N1 一語一義・一義一語（用語集）、N2 関数・メソッドの名前の形が返すものと引数を約束する（`is…` は真偽値、`diff…` は数、`…Between` は両端を含む一覧、`…On` はその日のもの、`with…` は足した新しい一覧など。逆向きの約束も持つ）、N3 真偽値の項目は形容詞か過去分詞、N4 単数・複数は型の形に合わせる、N5 選択肢の項目は `Policy` で終える、N6 関数を受ける項目は動詞で始める、N7 国の型の頭・設定の型の名前、N8 外部の名前は写す（`@namingSource`）、N9 スケジュール版の型は `Schedule` で始める
- 意味の重なりのうち型で表せるもの（`day` を項目の名前の最後に使わない、`rule` は繰り返しの規則の型だけ、など）は、用語集の「型」の列で機械的に確かめる（C12）。同じ名前の `Policy` の選択肢は、項目の名前を PascalCase にした型の値の部分集合にする（規則の形ごとに選択肢を絞るのは部分集合なので合う）

**同じ版に入れたもの**

- 型と実行時の一致（33 番の見直し）: 規則の形ごとに受ける項目を型で分けた。型を狭める変更は 1.0.0 の後ではメジャー版になるので、改名と同じ版で行った

**0.30.1 で追記**

- 和集合での `kinds` の `"national"`（0.30.0 の退行。55 番）: 0.30.0 は「提供元のどれかが日本なら `"regular"` に読み替える」としたので、日本と他国の和集合で他国の毎年の祝日にも当たった。改名は結果を変えない約束だったので、0.30.1 で読み替えをやめ、0.22.x の意味「種別が `"national"` の祝日、または日本の提供元が返した `"regular"` の祝日」で判定する（自作の提供元が `"national"` を返す和集合も 0.22.x と同じ結果になる）。祝日の出どころは、和集合の祝日の表に残った祝日がどの提供元のものかを年ごとの日付で記録する（祝日のオブジェクトに印を付けない。0.14.1 の性能の知見）。期待値は公開済みの 0.22.2 の結果（確定した年）と、日本の提供元を包んで種別を付け替えた設定との関係（データに依存しない）で確かめる
- 日本の提供元かどうかの判定: `id` が `"JP"` と完全に一致するかで決め、大文字・小文字は区別する（`id` は ISO 3166 のコードの形で大文字で書く。同梱の `FR-AM` のように ISO にない ID も同じ形にしている）。中のデータは見ないので、包んだ `jp` も、利用者が自作した ID `"JP"` の提供元も日本の提供元として扱う。規則は合成の前の各カレンダーの作成時に検査するので、合成ではカレンダーごとに決まる
- 判定の限界: `id` を変えて包んだ日本の提供元（`{ ...jp, id: "JP-company" }` など）は対象外で、0.30.0 から `"national"` は何にも当たらない（0.22.x では当たっていた）。祝日のデータから日本の提供元かを推し量ると判定が複雑になり、自作の提供元を誤って拾うので行わない。この場合の診断の `never-matches` に、改名の前の名前の可能性を添える（提供元のない設定では添えない。原因は提供元の付け忘れのほうが多いため）
- `migrate…` は、提供元がすべて ID `"JP"` のときだけ `"national"` を書き換える。和集合では新しい名前で同じ意味を書けないので書き換えず、`changes` にも出さない。保存した設定に提供元がなければ書き換えないので、読み込み時に付ける提供元を入れてから呼ぶ（ガイドに書いた）
- 週の第 n 営業日も、週の一部が対応年の外にかかる日は `outOfRangePolicy: "throw"` で `out-of-range` になる（週の 7 日を数えるため。上の「隣の日を見る規則と対応年の端」と同じ理由。シンガポールの最後の年の 12 月の最後の週が毎年当たる）。挙動は変えず、文書と型の説明に書いた
- 規則どうしの診断: 先に `"regular"`、後に旧名の `"national"` の規則は、`kinds` を集合で比べる `shadowed` には出ないが、1 日ずつ比べる `redundant` で見つかるので、このままにする
- 1.0.0 での `"national"`: ID `"JP"` の提供元を含む設定（日本だけでも和集合でも）では `invalid-option` にし、含まない設定では普通の種別の文字列として扱う。和集合で `"national"` を書いた利用者のほとんどは日本の祝日のつもりで、黙って何にも当たらなくすると D1 を 1.0.0 で繰り返すことになる。厳しい側で出しておけば、需要が示されたときに後のマイナー版で緩められる（互換の変更）が、逆は 1.0.0 の後はメジャー版でしかできない。困るのは、日本の提供元と `"national"` を返す自作の提供元の和集合だけで、自作の提供元の種別の名前を変えれば直る。0.30.x の間は、和集合の `deprecated-option` のメッセージでこのことを予告する。1.0.0 の例外のメッセージは次の趣旨にする: `"national" was renamed to "regular" in 0.30.0. To select only Japanese holidays together with other providers, wrap the Japanese provider (see the migration guide). A provider of your own that returns "national" must use another kind name.`
- 1.0.0 の作業に加えるもの: 上の例外、旧名の照合のテスト（`test/national-union.test.ts` などの旧名を使うテスト）の削除。`never-matches` に添える改名の説明は残す（`id` を変えて包んだ提供元の利用者には、旧名を消した後はこれが唯一の手がかりになる）

## 55. 直前の版で入った退行の修正はパッチ

パッチの区分（RELEASING.md）は公式データの反映と、法令・公式データと食い違っていた計算の誤りの修正を挙げていましたが、ライブラリ自身の不具合をどの版で直すかは決めていませんでした。これまで挙動を変える修正は、42・43 番の前例どおりマイナー版で出してきました。0.30.0 の和集合での `"national"`（54 番の 0.30.1 の追記）を直すにあたって、次のように決めました。

- 直前のマイナー版が、文書・決定・CHANGELOG で約束した挙動から外れていたとき（退行）、約束どおりに戻す修正はパッチで出す。約束どおりの結果を前提にした利用者には影響がなく、外れた結果を前提にした利用者は、その版に上げてからまだ日が浅い（20 番の「その日を正しく判定できていなかった状態の修正」と同じ性格）。`^`・`~` のどちらの利用者にも届けるため
- 約束していなかった挙動を変える修正と、例外を新たに投げるようにする修正は、これまでどおりマイナー版（42・43 番の前例）
- CHANGELOG には Fixed の区分で、どの版のどの約束から外れていたかを書く
