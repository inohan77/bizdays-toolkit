# 設計上の決定

「なぜこうなっているのか」を後から迷わないための記録です。変えないと決めたことも、理由と一緒に残します。

## 1. 日付は単なる文字列型（ブランド型にしない）

`DateString` は `string` の別名で、`"YYYY-MM-DD"` 以外の文字列も型の上では受け付けます。

- ブランド型（`string & { __brand: "DateString" }`）にすると型の安全性は上がりますが、利用者が日付を渡すたびに型変換や検証関数を挟む必要が出ます
- 入力はすべて実行時に検証し、誤りは `code: "invalid-date"` の例外になるので、使いやすさを優先します

## 2. 出力の列挙は「開いた型」

`DayReason`・`ScheduleReason`・`JapaneseHolidayKind`・`ErrorCode` は、既知の値の型（`Known…`）と `string & {}` の組です。

- 新しい値をマイナー版で足しても、利用者のコードがコンパイルエラーにならないようにするためです（値を列挙して分岐しているコードは「その他」の分岐で受けます）
- すべての値を網羅したことを型で確かめたい利用者は `Known…` を使えます。その場合、値が増えたときに型エラーで気付くことを利用者自身が選んだことになります
- ライブラリの内部では `Known…` で分岐し、対応漏れを型で検出します

## 3. 例外は従来のクラスのまま、`code` を持つ

例外は `RangeError`・`TypeError`・`Error` のインスタンスで、`code` プロパティを持ちます。`isBizdaysError()` で、このライブラリの例外かを判定できます。

- 独自の例外クラスにすると、`instanceof RangeError` で判定している既存のコードが壊れるため、従来のクラスに `code` を足す形にしました
- メッセージの文言は API に含みません。判定には `code` を使います

## 4. 設定の知らないキーは、作成時に無視する

`createCalendar`・`createSchedule` は、設定の知らないキーで例外を投げません。

- 将来の版で足した設定を古い版に渡しても壊れないようにするためです（前方互換）
- 打ち間違いは TypeScript では型エラーになります。JavaScript から使う場合のために、内部で警告として記録しており、規則の診断（`diagnoseCalendar`・`diagnoseSchedule`）で検出できます（15 番）

## 5. 設定は作る時点で取り込み、返すものは変更できない

設定の配列やオブジェクトは作る時点で複製し、返すオブジェクト・配列はすべて `Object.freeze` します。

- 作ったあとに利用者が元の設定を書き換えても結果が変わらないようにし、共有されたカレンダーを誤って書き換えることも防ぎます
- スケジュールの値（`T`）そのものは複製しません。値をあとから書き換えないことは利用者に任せます

## 6. 祝日の提供元が返したデータを検証する

`HolidayProvider` が返した祝日は、年ごとに初めて使うときに検証し、契約の項目（`date`・`name`・`nameEn`・`kind`・`confirmed`）だけを持つ変更できないオブジェクトにします。

- 利用者が実装した提供元の誤り（日付の形式、別の年の日付、重複など）で、判定が黙って狂うのを防ぐためです
- 検証は年ごとに 1 回なので、判定の速さにはほぼ影響しません

## 7. 祝日の名前は `name`（現地語）と `nameEn`、ほかの言語は `names`

ほかの言語の名称は、省略可能な `names`（キーは BCP 47 の言語タグの正規の形）で持ちます（0.7.0）。既存の項目は残します。

- 同梱の日本の祝日には `names` を付けません。日本の祝日の名称は内閣府のデータで照合していますが、ほかの言語の名称には同じ水準の公式の出典がないためです。出典のない翻訳を同梱すると、照合済みのデータと品質がそろいません
- 同梱の英国の祝日では、Wales の提供元だけがウェールズ語の名称（`names.cy`）を持ちます。GOV.UK のウェールズ語版という公式の出典があり、照合できるためです（21 番）
- 利用者が実装した提供元（または同梱の提供元を包んだもの）が `names` を付ければ、契約の項目として検証・複製・凍結して返します（6 番）。言語タグは正規の形（`"zh-Hant"`。`"zh-hant"` は不可）に限り、同じ言語が別の書き方で重複しないようにしています
- どの言語を表示に使うか（フォールバックの順序）は、ライブラリでは決めません

## 8. 型引数 `Kind`（祝日の種別）は残す

`Calendar<Kind>`・`Schedule<T, Kind>` の `Kind` は、日本の祝日で `kind` の補完が効く利点があります。既定値（`string`）があるので、使わない利用者の負担はありません。

## 9. 実行時に外部からデータを取り込まない

祝日データはパッケージに含め、実行時にネットワークから取得する機能は持ちません。

- 取り込むデータの改ざんや取得の失敗が、判定の正しさに直結するためです。法改正への対応は版の公開（staged publishing・provenance 付き）で行います
- どうしても必要な利用者は、`HolidayProvider` を自分で実装できます

## 10. 品質の仕組みに新しい依存を足さない

サイズの検査は minify せずに gzip で測り、API のスナップショットは TypeScript のコンパイラー API で作り、性質のテストの乱数は自前で実装しています。

- 開発用の依存が増えるほど、供給チェーンの管理（熟成ゲート）の対象が増えるためです
- 例外として、ワークフローの検査に actionlint を CI でだけ使います。ワークフローの誤り（ジョブの `env` で `runner` コンテキストを参照するなど）は `pnpm check` でも CI のテストでも見つからず、GitHub に読み込まれて初めて分かります。0.8.0 の準備中に監視のワークフローが読み込めない誤りを main に入れてしまったため、確実に止めることを優先しました。npm の依存にはせず、版と SHA-256 を固定した公式のリリースのバイナリを取得し、手元の環境にも入れません

## 11. lint は oxlint で、規則は絞って有効にする

lint には、整形の oxfmt と同じプロジェクト（oxc）の oxlint を使います。

- インストール時に実行するスクリプトがなく、依存は各 OS 向けのバイナリだけなので、供給チェーンの管理の手間がほとんど増えません。ESLint と typescript-eslint は依存のパッケージが多く、強みである型情報を使った規則（Promise の扱いの誤りなど）も、非同期の処理がないこのライブラリでは出番が少ないため見送りました
- 規則は「正しさ」の分類を基本に、意味のある規則だけを個別に足します。好みに関わる分類（style・pedantic）は、指摘の大半が書き方の好みで雑音になるため有効にしません
- `unicorn/no-array-sort`（`toSorted()` を使え）は、`toSorted()` が出力の対象（ES2022）より新しい機能のため採用しません

## 12. 判定の順番は固定し、繰り返しの規則と祝日の関係だけを規則ごとに選ばせる

判定の順番（個別の日付 → 毎年の月日 → 繰り返しの規則（祝日の上）→ 祝日 → 繰り返しの規則（祝日の下・振替先）→ 曜日）は固定で、利用者が全体を並べ替える設定は持ちません。

- 全体を並べ替えられると、同じ設定でもカレンダーごとに意味が変わり、判定が予測しにくくなります。規則の診断で「決して使われない規則」を見つけることも、順番の組み合わせごとに必要になります
- 個別の日付や毎年の月日が祝日より優先されるのは、どの業種でも共通です。店舗によって分かれるのは「繰り返しの規則が祝日に当たったとき」だけなので、そこだけを規則ごとの `onHolidayRule` で選べるようにしました
- `onHolidayRule` の値は真偽値にしていません。3 つの状態（祝日の下・祝日の上・祝日の後に振替）があり、真偽値ではどちら向きかも読み取りにくいためです。値は「祝日に対して規則がどこに来るか」という同じ観点の言葉（`"under-holiday"`・`"over-holiday"`・`"after-holiday"`）にそろえています

## 13. 「第 n 何曜日」は、その月で n 回目のその曜日

`{ weekday: 3, nth: 3 }` は、その月で 3 回目の水曜日（15〜21 日の水曜日）です。

- 業種によっては「カレンダーの第 3 週の行にある水曜日」の意味で使うことがあり、月初の曜日によって結果がずれます。曖昧さをなくすため、回数で数える定義に固定し、README に明記しています
- その月にない日（`nth: 5` がない月、`day: 31` がない月）は当てはまりません。末日に読み替える便利さより、書いたとおりに当てはまることを優先しました（末日は `day: -1` で指定します）

## 14. 振替先は「その日以降で最初の祝日でない日」

`onHolidayRule: "after-holiday"` の規則は、祝日には当てはめず、その日以降で最初の祝日でない日に当てはめます。

- 振替の判断に使う「祝日」は祝日の提供元の祝日だけで、毎年の休業日などは含みません。利用者の休業日の設定によって振替先が変わると、設定の影響が読み取りにくくなるためです
- 振替先は、繰り返しの規則と同じ段階で判定します。その日に個別の日付や毎年の月日の規則があれば、そちらが優先です
- 「翌平日」という言葉は土曜日を含まないこともありますが、このライブラリでは「祝日でない日」とし、土曜日も振替先になりえます。土曜日を避けたい場合は、別の規則と組み合わせて調整します

## 15. 規則の診断は例外を投げず、code で判定する

`diagnoseCalendar`・`diagnoseSchedule` は、作成時と同じ検証（内部の `IssueCollector`）で誤りと知らないキーを集め、誤りがなければ規則どうしの関係を調べて、問題の配列を返します。

- 例外を投げないのは、すべての問題を一度に見られるようにするためです（作成時は最初の誤りで止まります）。テストでは `assert.deepEqual(diagnoseCalendar(options), [])` の 1 行で設定を守れます
- `message` は英語で、API に含みません。判定は `code` で行います（例外と同じ扱い）。`code` は出力の列挙なので「開いた型」です。重さ（`severity`）は `"error"`・`"warning"`・`"info"` の 3 段階から増やさないため、例外的に閉じた型にしています（利用者が網羅的に分岐できるほうが役に立つため）
- `shadowed` は同じ種類の規則どうしに限ります。判定の順番が固定（12 番）なので、種類をまたぐ関係は「取り除いても結果が変わらない」（`redundant`）として、実際に取り除いた結果と比べて見つけます。種類をまたいで「覆っている規則」を 1 つに決めることはできないため、`redundant` には `relatedPath` を付けません
- `redundant` を `info` にしているのは、意図して書いている場合があるためです（定休日の曜日と同じ繰り返しの規則を、説明のために名前付きで書くなど）
- 毎年の月日・繰り返しの規則は無限に続くので、`redundant` は祝日の提供元の対応年（長すぎる場合は 1900〜2099 年に絞る）を、提供元がなければ 2001〜2028 年を 1 日ずつ調べます。繰り返しの規則の当てはまり方は、年の種類（1 月 1 日の曜日 × うるう年か）の 14 通りで決まり、28 年でそろうためです
- 知らないキーの候補（「did you mean」）は診断のときだけ計算します。作成時は警告を使わないので、編集距離の計算をルートのバンドルに入れないためです
- 診断はサブパス（`bizdays-toolkit/diagnose`）に分けています。開発・テスト用の道具で、日本の祝日を使うと全日を調べるため数百ミリ秒かかります。アプリの本体のバンドルに入らず、リクエストの処理で誤って呼ばれにくくするためです

## 16. 日付の調整は方法を必ず指定し、「最も近い営業日」は入れない

`adjust`・`dueDate` の `convention` は必須で、既定値を持ちません。方法は金融で使われる 4 つ（following・preceding・modified-following・modified-preceding）です。

- 支払期日が休業日のとき翌営業日にするか前営業日にするかは、契約や業種で決まります。既定値があると、決めずに使って誤った期日を出すことになるため、必ず書かせます
- 「最も近い営業日」（nearest）は入れません。前後が同じ距離のときの決め方が業種ごとに違い、どちらに決めても誤用を招くためです
- 月が変わるか（modified-…）は、調整する前の日付の月と比べます。`dueDate` では末日に読み替えた後の日付です。同じ月に反対向きの営業日もないときは、月が変わっても元の向きに調整します（例外にすると、その月が全部休業日の設定で期日が求められなくなるため）
- `dueDate` の `day` はその月にない日を末日に読み替えますが、繰り返しの規則（13 番）は読み替えません。期日は「その月のどこか」に必ず決まる必要がある一方、休業日の規則は書いたとおりに当てはまることを優先するためです
- 月は `"YYYY-MM"` の文字列（`MonthString`）で表します。日付と同じく、ブランド型にはしません（1 番）

## 17. 英国は地域ごとに提供元を分け、England と Wales も分ける

英国の bank holidays は、`bizdays-toolkit/uk` の `england`・`wales`・`scotland`・`northernIreland` の 4 つの提供元です。国全体の提供元や、地域を引数で選ぶ 1 つの提供元にはしていません。

- 英国の bank holidays は地域ごとに異なり、住民は自分の地域に誇りを持っています。地域をはっきり分けて選べるようにしておかないと、ライブラリとして無用な批判を受けかねません
- GOV.UK では England と Wales が 1 つの区分（England and Wales）ですが、別の提供元にしています。日付は現在同じですが、Wales では聖デイヴィッドの日を祝日にする要望が繰り返し出ており、将来分かれても利用者のコードを変えずに済むようにするためです
- ID は ISO 3166-2 のコード（`GB-ENG`・`GB-WLS`・`GB-SCT`・`GB-NIR`）です。地域ごとに完結した祝日の一覧を返すので、コアに国と地域の親子関係は持たせていません。複数の地域にまたがる場合は、和集合（`holidays` に配列で渡す）で使えます
- サブパスは ISO 3166-1 の `gb` ではなく `uk` にしています。`gb` は Great Britain（Northern Ireland を含まない）と読まれるためです。型の名前も同じ理由で `British…` ではなく `Uk…` にしています
- Scotland の地域（council）ごとの休日は扱いません。GOV.UK のデータになく、照合できないためです

## 18. 英国の祝日は規則で計算し、GOV.UK のデータで 2012 年から全日照合する

英国の祝日は、1971 年の Banking and Financial Dealings Act の附則と毎年の布告で定まる規則で計算し、布告による移動・臨時の祝日はテーブル（`src/uk/rules.ts` の `MOVED`・`SPECIAL_DAYS`）で持ちます。対応年は 2012 年からです。

- GOV.UK の JSON は古い年が消えていく（2026 年 10 月時点で 2019 年から）ため、データをそのまま同梱せず、日本と同じく規則で計算して公式データで照合する形にしています
- 照合のデータ（`test/fixtures/govuk-bank-holidays.json`）は、2019 年以降が GOV.UK の現在のデータ、2012〜2018 年が GOV.UK の公式リポジトリ（alphagov/calendars・alphagov/frontend）の履歴で、その年が含まれていた最後の版です。年ごとの出典を `years` に記録しています。GOV.UK のデータは Open Government Licence v3.0 で、保存・再配布が認められています（README の出典に帰属表示）
- 2012 年より前は、一覧として機械的に照合できる公式のデータがありません。民間のまとめサイトは手がかりにはなりますが、出典が示されていないため照合には使いません。過去に広げる場合は、布告（The Gazette）で年ごとに確かめた年から足します（対応年の拡大は非破壊）
- England and Wales・Northern Ireland の Good Friday と Christmas Day は、法律上は bank holiday ではなく慣習法上の休日ですが、GOV.UK の一覧と同じく含め、種別も区別しません
- 振替は「土曜日・日曜日に当たる固定日の祝日を、日付順に、その後で最も近い祝日でない平日へ」割り当てます。2023 年の Scotland だけは、GOV.UK が振替の日付は同じまま、どちらの祝日の振替かを附則と逆に割り当てているので、照合の対象である GOV.UK の表記に合わせています（`RENAMED`）
- 種別（`kind`）は GOV.UK の注記（`notes`）からは決めません。注記がそろっていないためです（2012 年の Spring bank holiday の移動を England and Wales・Scotland では「Substitute day」としているが Northern Ireland には注記がない、臨時の祝日の「Extra bank holiday」も 2012 年だけ）。テストでは、注記の「Substitute day」と種別 `"substitute"` が、この 2012 年の 2 件を除いて一致することを確かめています

## 19. GOV.UK との差分を毎日監視し、フィクスチャは人が確かめた修正と一緒に更新する

`.github/workflows/govuk-watch.yml` が毎日 GOV.UK と照合し、差分があれば issue を立てます。ワークフローはリポジトリにコミットしません。

- 英国の臨時の祝日は、10 日ほど前に発表されることがあります（2022 年の国葬）。年に 1 度の確認では間に合わないため、毎日確かめます
- 判定の根拠は、外部向けに公開されている GOV.UK の JSON です。GOV.UK の公式リポジトリのファイルは内部の実装で、置き場所の移動（calendars から frontend）や形式の変更（名称の翻訳キー化）が実際にあったため、変更の理由の手がかりとして issue に添えるだけにしています。ウェールズ語の名称だけは、ほかに公式の機械可読な出典がないため、リポジトリの翻訳ファイルを照合に使います
- フィクスチャは照合テストの入力なので、データだけを先に更新すると main のテストが失敗します。規則の修正と同じコミットで更新し、履歴には意味のある変更だけが残るようにしています（`--write` は内容が変わった年だけ出典を書き換えます）
- 取得や解析に失敗した場合も issue を立てます。黙って監視が止まるのを防ぐためです。同じ理由で、60 日間動きのないリポジトリで GitHub が定期実行を止めないよう、実行のたびにワークフローを有効化し直します

## 20. 公式データの反映はパッチ版

法改正・官報公表・布告による祝日の新設・移動・臨時の祝日、春分・秋分の日の確定、GOV.UK の新しい年の公表は、パッチ版で公開します（RELEASING.md）。

- 0.x の期間は `^0.8.0` が 0.9.0 を受け取らないため、マイナー版で出すと、臨時の祝日が必要な利用者に届きません。パッチ版なら、0.x でも 1.0.0 以降でも `^`・`~` のどちらの指定にも届きます
- API が変わらず、「その日を正しく判定できていなかった」状態の修正にあたるためでもあります

## 21. Wales の祝日にだけウェールズ語の名称を付け、`name` は英語のまま

Wales の提供元の祝日は、GOV.UK のウェールズ語版の名称を `names.cy` に持ちます。`name`（現地語）と `nameEn` は英語です。

- ウェールズ語の名称は GOV.UK のウェールズ語版（alphagov/frontend の翻訳ファイル）という公式の出典があり、照合できます（7 番）
- England の提供元には付けません。同じ日付でも地域を分けた（17 番）のと同じ考え方です
- `name` を英語にしているのは、Wales の公用語は英語とウェールズ語の両方で、GOV.UK の既定の表記が英語だからです

## 22. README は英語を既定にし、日本語版はパッケージに含めない

`README.md` は英語、`docs/README.ja.md` は日本語で、内容の量をそろえます。npm に公開するのは `README.md` だけです。

- 英国に対応して英語圏の利用者が主な対象に入ったため、GitHub と npm で既定に表示される README を英語にしました
- `node_modules` には必要最低限のファイルだけを入れる方針のため、日本語版はパッケージに含めません。npm はパッケージのルートにある `README*` を `files` の指定にかかわらず必ず含めるので、日本語版は `docs/` に置きます（ルートに置いた最初のステージでパッケージに入ったため、公開前に却下して直しました）。`pnpm check` は実際の `npm pack --dry-run` の結果で中身を確かめますnpm のページからも辿れるよう、英語版からのリンクは GitHub の絶対 URL にしています
- 2 つの README が食い違うのを防ぐため、`pnpm check` が見出しの数（段ごと）とコードブロックの数を比べます。文章の中身までは比べられませんが、節や例の足し忘れは見つかります
- 型のコメント（TSDoc）・CHANGELOG・RELEASING.md・この文書は日本語のままです

## 23. Node.js の対応は engines で示し、確かめる版を CI で決める

`engines` は `">=22.12"` です。README には、CI で確かめている版（22.12・22・24・26）を書きます。

- 下限の 22.12 は、ESM を `require()` で読み込む機能が既定で有効になった版です。`require()` で読み込めることも CI で確かめています
- 確かめる版: `check` ジョブで 22 系と 24 系の固定版（テストのすべて）、`compat` ジョブで下限の 22.12.0 と 26 系（公開する `dist` の ESM・CommonJS での読み込みと主要な関数）。22.12.0 と 26 系では、テスト（`.ts` の直接実行。型の除去が既定になったのは 22.18）と npm 12（動作要件 `^22.22.2 || ^24.15.0`）が動かないため、ビルドは Node.js 24 で行い、Node.js を切り替えて `dist` だけを確かめます。依存がゼロなので、`dist` だけで確かめられます
- 対象にする系列: LTS の系列と、LTS 入りを控えた系列です。サポートが終了した系列（23・25）は確かめません。新しい系列は LTS に入る時点で `compat` に足します（2027 年からは毎年 4 月に新しい系列が出て、10 月に LTS に入る）
- `engines` を「確かめた版」に狭めることはしません。pnpm の `engine-strict` を使う利用者が、確かめていない版で入れられなくなり、それ自体が互換性を壊すためです。「動くはずの範囲」（`engines`）と「確かめている範囲」（README と CI）を分けて示します。サポートを打ち切る（下限を上げる）のはメジャー版です（RELEASING.md）
