# 設計上の決定

「なぜこうなっているのか」を後から迷わないための記録です。変えないと決めたことも、理由と一緒に残します。

## 1. 日付は単なる文字列型（ブランド型にしない）

`DateString` は `string` の別名で、`"YYYY-MM-DD"` 以外の文字列も型の上では受け付けます。

- ブランド型（`string & { __brand: "DateString" }`）にすると型の安全性は上がりますが、利用者が日付を渡すたびに型変換や検証関数を挟む必要が出ます
- 入力はすべて実行時に検証し、誤りは `code: "invalid-date"` の例外になるので、使いやすさを優先します

## 2. 出力の列挙は「開いた型」

`DayReason`・`ScheduleReason`・`JapaneseHolidayKind`・`ErrorCode` は、既知の値の型（`Known…`）と `string & {}` の組です。

- 新しい値をマイナー版で足しても、利用者のコードがコンパイルエラーにならないようにするためです（値を列挙して分岐しているコードは「その他」の分岐で受けます）
- すべての値を網羅したことを型で確かめたい利用者は `Known…` を使えます。その場合、値が増えたときに型エラーで気付くことを利用者自身が選んだことになります
- ライブラリの内部では `Known…` で分岐し、対応漏れを型で検出します

## 3. 例外は従来のクラスのまま、`code` を持つ

例外は `RangeError`・`TypeError`・`Error` のインスタンスで、`code` プロパティを持ちます。`isBizdaysError()` で、このライブラリの例外かを判定できます。

- 独自の例外クラスにすると、`instanceof RangeError` で判定している既存のコードが壊れるため、従来のクラスに `code` を足す形にしました
- メッセージの文言は API に含みません。判定には `code` を使います

## 4. 設定の知らないキーは、作成時に無視する

`createCalendar`・`createSchedule` は、設定の知らないキーで例外を投げません。

- 将来の版で足した設定を古い版に渡しても壊れないようにするためです（前方互換）
- 打ち間違いは TypeScript では型エラーになります。JavaScript から使う場合のために、内部で警告として記録しており、規則の診断（`diagnoseCalendar`・`diagnoseSchedule`）で検出できます（15 番）

## 5. 設定は作る時点で取り込み、返すものは変更できない

設定の配列やオブジェクトは作る時点で複製し、返すオブジェクト・配列はすべて `Object.freeze` します。

- 作ったあとに利用者が元の設定を書き換えても結果が変わらないようにし、共有されたカレンダーを誤って書き換えることも防ぎます
- スケジュールの値（`T`）そのものは複製しません。値をあとから書き換えないことは利用者に任せます

## 6. 祝日の提供元が返したデータを検証する

`HolidayProvider` が返した祝日は、年ごとに初めて使うときに検証し、契約の項目（`date`・`name`・`nameEn`・`kind`・`confirmed`。0.7.0 から `names`、7 番）だけを持つ変更できないオブジェクトにします。

- 利用者が実装した提供元の誤り（日付の形式、別の年の日付、重複など）で、判定が黙って狂うのを防ぐためです
- 検証は年ごとに 1 回なので、判定の速さにはほぼ影響しません

## 7. 祝日の名前は `name`（現地語）と `nameEn`、ほかの言語は `names`

ほかの言語の名称は、省略可能な `names`（キーは BCP 47 の言語タグの正規の形）で持ちます（0.7.0）。既存の項目は残します。

- 同梱の日本の祝日には `names` を付けません。日本の祝日の名称は内閣府のデータで照合していますが、ほかの言語の名称には同じ水準の公式の出典がないためです。出典のない翻訳を同梱すると、照合済みのデータと品質がそろいません
- 同梱の英国の祝日では、Wales の提供元だけがウェールズ語の名称（`names.cy`）を持ちます。GOV.UK のウェールズ語版という公式の出典があり、照合できるためです（21 番）
- 利用者が実装した提供元（または同梱の提供元を包んだもの）が `names` を付ければ、契約の項目として検証・複製・凍結して返します（6 番）。言語タグは正規の形（`"zh-Hant"`。`"zh-hant"` は不可）に限り、同じ言語が別の書き方で重複しないようにしています
- どの言語を表示に使うか（フォールバックの順序）は、ライブラリでは決めません

## 8. 型引数 `Kind`（祝日の種別）は残す

`Calendar<Kind>`・`Schedule<T, Kind>` の `Kind` は、日本の祝日で `kind` の補完が効く利点があります。既定値（`string`）があるので、使わない利用者の負担はありません。

## 9. 実行時に外部からデータを取り込まない

祝日データはパッケージに含め、実行時にネットワークから取得する機能は持ちません。

- 取り込むデータの改ざんや取得の失敗が、判定の正しさに直結するためです。法改正への対応は版の公開（staged publishing・provenance 付き）で行います
- どうしても必要な利用者は、`HolidayProvider` を自分で実装できます

## 10. 品質の仕組みに新しい依存を足さない

サイズの検査は minify せずに gzip で測り、API のスナップショットは TypeScript のコンパイラー API で作り、性質のテストの乱数は自前で実装しています。

- 開発用の依存が増えるほど、供給チェーンの管理（熟成ゲート）の対象が増えるためです
- 例外として、ワークフローの検査に actionlint を CI でだけ使います。ワークフローの誤り（ジョブの `env` で `runner` コンテキストを参照するなど）は `pnpm check` でも CI のテストでも見つからず、GitHub に読み込まれて初めて分かります。0.8.0 の準備中に監視のワークフローが読み込めない誤りを main に入れてしまったため、確実に止めることを優先しました。npm の依存にはせず、版と SHA-256 を固定した公式のリリースのバイナリを取得し、手元の環境にも入れません

## 11. lint は oxlint で、規則は絞って有効にする

lint には、整形の oxfmt と同じプロジェクト（oxc）の oxlint を使います。

- インストール時に実行するスクリプトがなく、依存は各 OS 向けのバイナリだけなので、供給チェーンの管理の手間がほとんど増えません。ESLint と typescript-eslint は依存のパッケージが多く、強みである型情報を使った規則（Promise の扱いの誤りなど）も、非同期の処理がないこのライブラリでは出番が少ないため見送りました
- 規則は「正しさ」の分類を基本に、意味のある規則だけを個別に足します。好みに関わる分類（style・pedantic）は、指摘の大半が書き方の好みで雑音になるため有効にしません
- `unicorn/no-array-sort`（`toSorted()` を使え）は、`toSorted()` が出力の対象（ES2022）より新しい機能のため採用しません

## 12. 判定の順番は固定し、繰り返しの規則と祝日の関係だけを規則ごとに選ばせる

判定の順番（個別の日付 → 毎年の月日 → 繰り返しの規則（祝日の上）→ 祝日 → 繰り返しの規則（祝日の下・振替先）→ 曜日）は固定で、利用者が全体を並べ替える設定は持ちません。

- 全体を並べ替えられると、同じ設定でもカレンダーごとに意味が変わり、判定が予測しにくくなります。規則の診断で「決して使われない規則」を見つけることも、順番の組み合わせごとに必要になります
- 個別の日付や毎年の月日が祝日より優先されるのは、どの業種でも共通です。店舗によって分かれるのは「繰り返しの規則が祝日に当たったとき」だけなので、そこだけを規則ごとの `onHolidayRule` で選べるようにしました
- `onHolidayRule` の値は真偽値にしていません。3 つの状態（祝日の下・祝日の上・祝日の後に振替）があり、真偽値ではどちら向きかも読み取りにくいためです。値は「祝日に対して規則がどこに来るか」という同じ観点の言葉（`"under-holiday"`・`"over-holiday"`・`"after-holiday"`）にそろえています

## 13. 「第 n 何曜日」は、その月で n 回目のその曜日

`{ weekday: 3, nth: 3 }` は、その月で 3 回目の水曜日（15〜21 日の水曜日）です。

- 業種によっては「カレンダーの第 3 週の行にある水曜日」の意味で使うことがあり、月初の曜日によって結果がずれます。曖昧さをなくすため、回数で数える定義に固定し、README に明記しています
- その月にない日（`nth: 5` がない月、`day: 31` がない月）は当てはまりません。末日に読み替える便利さより、書いたとおりに当てはまることを優先しました（末日は `day: -1` で指定します）。読み替えないのは繰り返しの規則だけで、期日（`dueDate`）と締め日（`closingMonth`）は同じ `DayOfMonth` を受け取っても末日に読み替えます（16 番）
- 「隔週」は第 n 曜日では表せない（月の長さが一定でないため、`nth` のどの組み合わせでも周期 14 日にならない）ので、別の書き方 `interval`・`anchor` で表します（30 番）

## 14. 振替先は「その日以降で最初の祝日でない日」

`onHolidayRule: "after-holiday"` の規則は、祝日には当てはめず、その日以降で最初の祝日でない日に当てはめます。

- 振替の判断に使う「祝日」は祝日の提供元の祝日だけで、毎年の休業日などは含みません。利用者の休業日の設定によって振替先が変わると、設定の影響が読み取りにくくなるためです
- 振替先は、繰り返しの規則と同じ段階で判定します。その日に個別の日付や毎年の月日の規則があれば、そちらが優先です
- 「翌平日」という言葉は土曜日を含まないこともありますが、このライブラリでは「祝日でない日」とし、土曜日も振替先になりえます。振替先を変える設定は規則にないので、土曜日を避けたい場合は、その回を個別の日付（`openDates`・`closedDates`）で上書きします（土曜日が定休日なら、結果は同じです）
- 規則に有効期間（30 番）があるときは、振替元の日（規則が本来当てはまる祝日）で期間を判定します。振替先が期間の外に出ても振り替えます。「規則が当てはまるか」を本来の日で決める、という振替の考え方と同じにするためです

## 15. 規則の診断は例外を投げず、code で判定する

`diagnoseCalendar`・`diagnoseSchedule` は、作成時と同じ検証（内部の `IssueCollector`）で誤りと知らないキーを集め、誤りがなければ規則どうしの関係を調べて、問題の配列を返します。

- 例外を投げないのは、すべての問題を一度に見られるようにするためです（作成時は最初の誤りで止まります）。テストでは `assert.deepEqual(diagnoseCalendar(options), [])` の 1 行で設定を守れます
- `message` は英語で、API に含みません。判定は `code` で行います（例外と同じ扱い）。`code` は出力の列挙なので「開いた型」です。重さ（`severity`）は `"error"`・`"warning"`・`"info"` の 3 段階から増やさないため、例外的に閉じた型にしています（利用者が網羅的に分岐できるほうが役に立つため）
- `shadowed` は同じ種類の規則どうしに限ります。判定の順番が固定（12 番）なので、種類をまたぐ関係は「取り除いても結果が変わらない」（`redundant`）として、実際に取り除いた結果と比べて見つけます。種類をまたいで「覆っている規則」を 1 つに決めることはできないため、`redundant` には `relatedPath` を付けません
- `redundant` を `info` にしているのは、意図して書いている場合があるためです（定休日の曜日と同じ繰り返しの規則を、説明のために名前付きで書くなど）
- 毎年の月日・繰り返しの規則は無限に続くので、`redundant` は祝日の提供元の対応年（長すぎる場合は 1900〜2099 年に絞る）を、提供元がなければ 2001〜2028 年を 1 日ずつ調べます。繰り返しの規則の当てはまり方は、年の種類（1 月 1 日の曜日 × うるう年か）の 14 通りで決まり、28 年でそろうためです。ただし周期（`interval`）のある規則は別で、28 年（10,227 日）が 7 × interval 日の倍数とは限らない（隔週の位相は 28 年後に反転する）ので、周期と 28 年の最小公倍数（隔週なら 56 年。上限 200 年）まで広げます。規則の有効期間が調べる範囲の外にあれば、その期間（期限のない側は周期の長さ）も加えます（対応年の外で例外になる設定では加えません）。固定の範囲だけでは、範囲の外にある期間の規則を「使われない」と誤診するためです（30 番）
- 知らないキーの候補（「did you mean」）は診断のときだけ計算します。作成時は警告を使わないので、編集距離の計算をルートのバンドルに入れないためです
- 診断はサブパス（`bizdays-toolkit/diagnose`）に分けています。開発・テスト用の道具で、日本の祝日を使うと全日を調べるため数百ミリ秒かかります。アプリの本体のバンドルに入らず、リクエストの処理で誤って呼ばれにくくするためです

## 16. 日付の調整は方法を必ず指定し、「最も近い営業日」は入れない

`adjust`・`dueDate` の `convention` は必須で、既定値を持ちません。方法は金融で使われる 4 つ（following・preceding・modified-following・modified-preceding）です。

- 支払期日が休業日のとき翌営業日にするか前営業日にするかは、契約や業種で決まります。既定値があると、決めずに使って誤った期日を出すことになるため、必ず書かせます
- 「最も近い営業日」（nearest）は入れません。前後が同じ距離のときの決め方が業種ごとに違い、どちらに決めても誤用を招くためです
- 月が変わるか（modified-…）は、調整する前の日付の月と比べます。`dueDate` では末日に読み替えた後の日付です。同じ月に反対向きの営業日もないときは、月が変わっても元の向きに調整します（例外にすると、その月が全部休業日の設定で期日が求められなくなるため）
- `dueDate` の `day` はその月にない日を末日に読み替えますが、繰り返しの規則（13 番）は読み替えません。期日は「その月のどこか」に必ず決まる必要がある一方、休業日の規則は書いたとおりに当てはまることを優先するためです。締め日（`closingMonth`）も同じ理由で読み替えます（締め日はその月のどこかに必ず決まる必要があります）
- 月は `"YYYY-MM"` の文字列（`MonthString`）で表します。日付と同じく、ブランド型にはしません（1 番）

## 17. 英国は地域ごとに提供元を分け、England と Wales も分ける

英国の bank holidays は、`bizdays-toolkit/uk` の `england`・`wales`・`scotland`・`northernIreland` の 4 つの提供元です。国全体の提供元や、地域を引数で選ぶ 1 つの提供元にはしていません。

- 英国の bank holidays は地域ごとに異なり、住民は自分の地域に誇りを持っています。地域をはっきり分けて選べるようにしておかないと、ライブラリとして無用な批判を受けかねません
- GOV.UK では England と Wales が 1 つの区分（England and Wales）ですが、別の提供元にしています。日付は現在同じですが、Wales では聖デイヴィッドの日を祝日にする要望が繰り返し出ており、将来分かれても利用者のコードを変えずに済むようにするためです
- ID は ISO 3166-2 のコード（`GB-ENG`・`GB-WLS`・`GB-SCT`・`GB-NIR`）です。地域ごとに完結した祝日の一覧を返すので、コアに国と地域の親子関係は持たせていません。複数の地域にまたがる場合は、和集合（`holidays` に配列で渡す）で使えます
- サブパスは ISO 3166-1 の `gb` ではなく `uk` にしています。`gb` は Great Britain（Northern Ireland を含まない）と読まれるためです。型の名前も同じ理由で `British…` ではなく `Uk…` にしています
- Scotland の地域（council）ごとの休日は扱いません。GOV.UK のデータになく、照合できないためです

## 18. 英国の祝日は規則で計算し、GOV.UK のデータで 2012 年から全日照合する

英国の祝日は、1971 年の Banking and Financial Dealings Act の附則と毎年の布告で定まる規則で計算し、布告による移動・臨時の祝日はテーブル（`src/uk/rules.ts` の `MOVED`・`SPECIAL_DAYS`）で持ちます。対応年は 2012 年からです。

- GOV.UK の JSON は古い年が消えていく（2026 年 10 月時点で 2019 年から）ため、データをそのまま同梱せず、日本と同じく規則で計算して公式データで照合する形にしています
- 照合のデータ（`test/fixtures/govuk-bank-holidays.json`）は、2019 年以降が GOV.UK の現在のデータ、2012〜2018 年が GOV.UK の公式リポジトリ（alphagov/calendars・alphagov/frontend）の履歴で、その年が含まれていた最後の版です。年ごとの出典を `years` に記録しています。GOV.UK のデータは Open Government Licence v3.0 で、保存・再配布が認められています（README の出典に帰属表示）
- 2012 年より前は、一覧として機械的に照合できる公式のデータがありません。民間のまとめサイトは手がかりにはなりますが、出典が示されていないため照合には使いません。過去に広げる場合は、布告（The Gazette）で年ごとに確かめた年から足します（対応年の拡大は非破壊）
- England and Wales・Northern Ireland の Good Friday と Christmas Day は、法律上は bank holiday ではなく慣習法上の休日ですが、GOV.UK の一覧と同じく含め、種別も区別しません
- 振替は「土曜日・日曜日に当たる固定日の祝日を、日付順に、その後で最も近い祝日でない平日へ」割り当てます。2023 年の Scotland だけは、GOV.UK が振替の日付は同じまま、どちらの祝日の振替かを附則と逆に割り当てているので、照合の対象である GOV.UK の表記に合わせています（`RENAMED`）
- 種別（`kind`）は GOV.UK の注記（`notes`）からは決めません。注記がそろっていないためです（2012 年の Spring bank holiday の移動を England and Wales・Scotland では「Substitute day」としているが Northern Ireland には注記がない、臨時の祝日の「Extra bank holiday」も 2012 年だけ）。テストでは、注記の「Substitute day」と種別 `"substitute"` が、この 2012 年の 2 件を除いて一致することを確かめています

## 19. GOV.UK との差分を毎日監視し、フィクスチャは人が確かめた修正と一緒に更新する

`.github/workflows/govuk-watch.yml` が毎日 GOV.UK と照合し、差分があれば issue を立てます。ワークフローはリポジトリにコミットしません。

- 英国の臨時の祝日は、10 日ほど前に発表されることがあります（2022 年の国葬）。年に 1 度の確認では間に合わないため、毎日確かめます
- 判定の根拠は、外部向けに公開されている GOV.UK の JSON です。GOV.UK の公式リポジトリのファイルは内部の実装で、置き場所の移動（calendars から frontend）や形式の変更（名称の翻訳キー化）が実際にあったため、変更の理由の手がかりとして issue に添えるだけにしています。ウェールズ語の名称だけは、ほかに公式の機械可読な出典がないため、リポジトリの翻訳ファイルを照合に使います
- フィクスチャは照合テストの入力なので、データだけを先に更新すると main のテストが失敗します。規則の修正と同じコミットで更新し、履歴には意味のある変更だけが残るようにしています（`--write` は内容が変わった年だけ出典を書き換えます）
- 取得や解析に失敗した場合も issue を立てます。黙って監視が止まるのを防ぐためです。同じ理由で、60 日間動きのないリポジトリで GitHub が定期実行を止めないよう、実行のたびにワークフローを有効化し直します。起動のしかたと、監視が動かなかったことに気付く仕組みは 28 番

## 20. 公式データの反映はパッチ版

法改正・官報公表・布告による祝日の新設・移動・臨時の祝日、春分・秋分の日の確定、GOV.UK の新しい年の公表は、パッチ版で公開します（RELEASING.md）。

- 0.x の期間は `^0.8.0` が 0.9.0 を受け取らないため、マイナー版で出すと、臨時の祝日が必要な利用者に届きません。パッチ版なら、0.x でも 1.0.0 以降でも `^`・`~` のどちらの指定にも届きます
- API が変わらず、「その日を正しく判定できていなかった」状態の修正にあたるためでもあります

## 21. Wales の祝日にだけウェールズ語の名称を付け、`name` は英語のまま

Wales の提供元の祝日は、GOV.UK のウェールズ語版の名称を `names.cy` に持ちます。`name`（現地語）と `nameEn` は英語です。

- ウェールズ語の名称は GOV.UK のウェールズ語版（alphagov/frontend の翻訳ファイル）という公式の出典があり、照合できます（7 番）

## 22. README は英語を既定にし、日本語版はパッケージに含めない

`README.md` は英語、`docs/README.ja.md` は日本語で、内容の量をそろえます。npm に公開するのは `README.md` だけです。

- 英国に対応して英語圏の利用者が主な対象に入ったため、GitHub と npm で既定に表示される README を英語にしました
- `node_modules` には必要最低限のファイルだけを入れる方針のため、日本語版はパッケージに含めません。npm はパッケージのルートにある `README*` を `files` の指定にかかわらず必ず含めるので、日本語版は `docs/` に置きます（ルートに置いた最初のステージでパッケージに入ったため、公開前に却下して直しました）。`pnpm check` は実際の `npm pack --dry-run` の結果で中身を確かめますnpm のページからも辿れるよう、英語版からのリンクは GitHub の絶対 URL にしています
- 2 つの README が食い違うのを防ぐため、`pnpm check` が見出しの数（段ごと）とコードブロックの数を比べます。文章の中身までは比べられませんが、節や例の足し忘れは見つかります
- 型のコメント（TSDoc）・CHANGELOG・RELEASING.md・この文書は日本語のままです

## 23. Node.js の対応は engines で示し、確かめる版を CI で決める

`engines` は `">=22.12"` です。README には、CI で確かめている版（22.12・22・24・26）を書きます。

- 下限の 22.12 は、ESM を `require()` で読み込む機能が既定で有効になった版です。`require()` で読み込めることも CI で確かめています。22.12 では、この読み込みに実験的な機能の警告（ExperimentalWarning）が出ます（26 では出ない）。結果には影響しないので、README で知らせるだけにしています
- 確かめる版: `check` ジョブで 22 系と 24 系の固定版（テストのすべて）、`compat` ジョブで下限の 22.12.0 と 26 系（公開する `dist` の ESM・CommonJS での読み込みと主要な関数）。22.12.0 と 26 系では、テスト（`.ts` の直接実行。型の除去が既定になったのは 22.18）と npm 12（動作要件 `^22.22.2 || ^24.15.0`）が動かないため、ビルドは Node.js 24 で行い、Node.js を切り替えて `dist` だけを確かめます。依存がゼロなので、`dist` だけで確かめられます
- 対象にする系列: LTS の系列と、LTS 入りを控えた系列です。サポートが終了した系列（23・25）は確かめません。新しい系列は LTS に入る時点で `compat` に足します（2027 年からは毎年 4 月に新しい系列が出て、10 月に LTS に入る）
- `engines` を「確かめた版」に狭めることはしません。pnpm の `engine-strict` を使う利用者が、確かめていない版で入れられなくなり、それ自体が互換性を壊すためです。「動くはずの範囲」（`engines`）と「確かめている範囲」（README と CI）を分けて示します。サポートを打ち切る（下限を上げる）のはメジャー版です（RELEASING.md）

## 24. Node.js の警告は失敗として扱い、直す

自前のスクリプト（`scripts/`）とテストで Node.js の警告（非推奨の API・実験的な機能など）が出たら、終了コードを 1 にします（`scripts/strict-warnings.ts`。スクリプトは先頭で import し、テストは `node --import` で読み込む）。どの環境でも同じです。

- 警告は合格のまま通るため、見落とされます。Windows で `npm.cmd` をシェルと引数の配列で起動したときの非推奨の警告（DEP0190）は、手元の出力をたまたま読んで気付きました
- 警告のイベントは非同期に届くので、同期的に `process.exit` するスクリプトでも見落とさないよう、`process.emitWarning` の呼び出しそのものを記録します（Node.js 自身の警告もこの関数を通ります）
- 公開物の互換性の確認（`test/compat`）は対象にしません。利用者の環境で動くかを確かめるもので、Node.js 22.12 の `require()` の実験的な機能の警告は利用者にとって問題ではないためです（23 番）
- Windows の CI は置きません。`dist` はどの OS でも同じに動き、開発用のスクリプトの Windows での問題は、コミットの前に手元（Windows）で通す `pnpm check` がこの仕組みで止めるためです

## 25. 開発用のツールの版を pnpm check で確かめる

`pnpm check` は最初に `scripts/check-toolchain.ts` で、ツールの版を確かめます。

- 固定版でない npm（10）で検査を試して、npm 12 での出力の形の違いを見落としたことがあります。手元と CI の版が違っていたこともあります。どちらも、版を比べれば機械的に分かります
- 確かめること: ワークフローどうしで同じ系列の Node.js の版がそろっていること（`ci.yml` の `check` の行列が基準。版を上げるときの書き換え漏れを防ぐ）、`compat` の行列に engines の下限が入っていること、実行している Node.js・npm・pnpm が固定版と同じこと
- 固定版との違いは、CI ではエラー、手元では注意の表示だけにします。熟成ゲートや別の作業の都合で、手元を先に変えることがあるためです。RELEASING.md の「手元と CI で同じ版を使う」に戻すまでの間も、作業を止めないようにしています
- スクリプトから起動する npm は、Windows でも `cmd.exe` から `npm.cmd` を直接呼ぶので、PowerShell の関数として定義された Safe Chain を通りません。スクリプトからレジストリに接続する npm の操作（`install` など）はしません

## 26. 公開物をブラウザーと Cloudflare Workers でも確かめる

公開する `dist` を、Node.js に加えて Chrome・Firefox・Edge（ubuntu のランナー）、Safari（macOS のランナー）、Cloudflare Workers の実行環境 workerd で確かめます。確認の中身は `test/compat/smoke.mjs` の 1 つで、Node.js・ブラウザー・workerd が同じものを呼びます。

- README に「ブラウザー・エッジランタイムで動く」と書いていましたが、確かめていませんでした。ソースが標準の JavaScript と `Intl` だけで書かれていることは `pnpm check` で確かめ（`src` が `node:` のモジュール・`process`・`Buffer` などを使わない）、実際の動作は CI で確かめます
- 新しい npm の依存は足しません。ブラウザーはランナーに入っているドライバーを WebDriver（HTTP）で操作し（`scripts/test-browsers.ts`。Node.js の `fetch` だけ）、workerd は版と SHA-256 を固定した公式のリリースを取得します（`scripts/test-workerd.ts`）
- ブラウザーの版は固定できません。ランナーのイメージの更新で変わるので、「その時点の最新の安定版」で確かめています（README にもそう書く）
- ブラウザーの側が一時的に止まることがあります（ランナー上の Edge がページの読み込みで応答しなくなった例がある）。結果を受け取る前の段階で止まったときだけ 1 回やり直し、ログに `RETRY` と理由を出します。確認の結果が FAIL のときはやり直しません。本物の失敗を、やり直しで隠さないためです。Edge は 1 回目が止まることが続いたため、起動オプションに `--disable-dev-shm-usage`（共有メモリの代わりに一時ファイルを使う）と `--disable-gpu` を足しています（CI のコンテナでレンダラーが応答しなくなる原因としてよく知られる 2 つへの対策。効いたかは `RETRY` の有無で見る）
- エッジランタイムは Cloudflare Workers だけにしました。workerd は Cloudflare が本番で動かしているのと同じコードで、Deno のチームも Cloudflare に加わって workerd との統合を進めています（2026 年 10 月）。Vercel の Edge Runtime を確かめるには npm の依存（`edge-runtime`）が要るので、確かめません。確かめていない環境は README に書きます
- 本物の Temporal を持つ環境では、Temporal のオブジェクトを入力にした確認も行い、持たない環境では飛ばしたことをログに出します（黙って飛ばすと、確かめたように見えるため）

## 27. README のコード例を pnpm check で実行する

`pnpm check` は README（英語・日本語）の ts のコード例をすべて実行し、コメントに書いた結果（`expr; // "2026-11-02"` や、次の行から続く `// { ... }`）と比べます（`scripts/check-readme-examples.ts`）。

- コード例は利用者が最もよく読む部分で、日英 2 つあるので、仕様の変更で片方だけ古くなりやすいところです
- ブロックは 1 つずつ別のモジュールにして、ビルド済みの `dist` で実行します。ブロックが import していない公開の名前は補い、ほかのブロックで定義した値を使う断片には決まった定義（`FIXTURES`）を補います。利用者のプロジェクトのファイルを import するブロックは実行できないので飛ばします
- 比べないもの: リテラルで始まらないコメント（説明だけのもの）、現在時刻（`new Date()`）を使う式。`{…}` は何にでも一致し、`…` を含む文字列は … 以外の部分を順に含めば一致とします
- README のサイズの値（minify + gzip）は、測るのに新しい依存（esbuild など）が要るので自動では確かめません。測った版を添え、マイナー版で測り直します（RELEASING.md）

## 28. 監視は外部から起動し、動いたことをハートビートで確かめる

GOV.UK の監視（govuk-watch）は、外部の cron サービス（cron-job.org）から `workflow_dispatch` を API で呼んで起動します。GitHub の schedule は予備として時刻をずらして残し、動いたことは最後に healthchecks.io へ知らせます（ハートビート）。

- GitHub の schedule は、高負荷時に遅れたり落ちたりするとドキュメントに書かれています。このリポジトリでも、追加してから一度も動きませんでした。3 時間ごとの設定で 4 日間一度も動かなかったという報告もあり、回数を増やしても解決しないと判断しました
- cron-job.org に預けるトークンは、このリポジトリだけ・Actions の Read and write だけに絞ります。漏れた場合にできるのは、`workflow_dispatch` のある govuk-watch の起動と、ワークフローの無効化・実行の取り消しなどの妨害までです。コードの変更はできず、npm への公開には staged publishing の 2FA での承認が要るので、利用者に悪いパッケージが届くことはありません
- GitHub の「失敗したときだけメール」の通知は、実行がなければ届きません。「来るはずの知らせが来ない」ことに気付くには、それを見張る仕組みが要るので、ハートビートを使います。cron-job.org・GitHub の schedule・ワークフロー・トークンの期限のどこで止まっても、知らせが途絶えて気付けます。healthchecks.io に預けるのは知らせ先の URL だけで、リポジトリを操作する権限は渡しません
- 通知の役割: 差分と監視の故障（取得の失敗など）は GitHub の失敗の通知と issue、監視が動かなかったことは healthchecks.io のメール。照合そのものが失敗したときは、ハートビートでも `/fail` を知らせます

## 29. 利用者からの改善提案への対応

複数頂いた改善提案に対して、0.9.0 で次のように対応しました。

- **`reason` の意味は変えない**: スケジュールの `dayInfo` の `reason` は「値を決めた規則」です。祝日の規則が `"weekday"` のときは、祝日でも `"weekday"` になります。「祝日の規則が関わったか」を表すフィールドは足さず、README に「祝日かどうかは `holiday` で判定する」と書きました。フィールドを足すと、「祝日か」「祝日の規則が値を決めたか」「関わったか」の区別が増えて、かえって分かりにくくなるためです
- **時刻を必ず持つ入力では `time` を `string` にする**: `civilOf`・`toDateTimeParts`・`toJapanDateTime` にオーバーロードを加えました。返す値は変えず、型を正確にするだけなので、既存のコードは壊れません。時刻を持つかどうかは入力の型で決まります（`Date`・Temporal の `Instant`・`ZonedDateTime`・`PlainDateTime`、`"YYYY-MM-DDTHH:mm…"` の文字列）。空白で区切った日時の文字列（`"2026-11-23 10:00"`）は実行時には受け付けますが、型では `string | null` のままです
- **期間の日ごとの情報（`daysBetween`）**: スケジュールと営業日カレンダーの両方に、同じ名前・同じ範囲の扱い（両端を含む）で足しました。`listBusinessDays` と同じく、`from` が `to` より後なら `invalid-range` です
- **型定義の確認は既存の tsc で**: `@arethetypeswrong/cli` は新しい依存になるので入れず（10 番）、既存の TypeScript で、利用者のプロジェクトとして `moduleResolution` を変えた型チェックを `pnpm check` に入れました。型定義の import が `.ts` の拡張子で書かれているため、利用者の設定で読めることを確かめる意味があります。古い TypeScript は新しい依存を避けるため CI では確かめず、確かめた範囲（0.9.0 の時点の手作業）を README に書きます
- **入れなかったもの**: 締め時刻の数値での指定（`cutoff: 14`）は、`14.5` が 14:30 なのかなどの曖昧さが増えるので入れません。`"14:00"` の文字列なら誤解の余地がありません。年月日と月日を 1 つの配列で渡す形も、今の明示的な分け方のほうが分かりやすいので変えず、README に振り分けの例を足しました
- **移行ガイド**: マイナー版の間を移るときの作業を `docs/migration.md` にまとめ、0.9.0 からは CHANGELOG の各マイナー版にも「移行」の小見出しを設けます。版を飛ばして移る利用者が、CHANGELOG を順に追わずに済むようにするためです

## 30. 規則の有効期間は `effectiveFrom`・`effectiveTo`、隔週は `interval`・`anchor`

繰り返しの規則と毎年の月日の規則に、省略可能な有効期間（両端を含む `"YYYY-MM-DD"`）を付けられます（0.10.0）。曜日の規則には、周期（週数）と起点の日付で「隔週」を書けます。

- 「2027 年 4 月から定休日を月曜から火曜に変える」は、カレンダーを 2 つ作って日付で呼び分けても、`addBusinessDays` のように切り替え日をまたいで探す計算が 1 つのカレンダーの中で完結するため正しく動きません。切り替え後の日付を個別の日付で列挙すると、件数が膨らむうえ、個別の日付は祝日より優先される（12 番）ので意味も変わります。規則そのものに期間を持たせるのが、意味を保てる唯一の形です
- 期間の外では、その規則は書かれていないのと同じに扱い、判定の順番（12 番）には影響しません。設定に省略可能な項目が増えるだけなので、互換性の約束の範囲です
- 項目の名前は、毎年の月日で使っている `from`・`to` と区別するため `effectiveFrom`・`effectiveTo` にしました。「有効期間」に対応する語として、業務システムで広く使われている言葉です
- 個別の日付（`closedDates` など）と定休日の曜日（`closedWeekdays`）には付けません。個別の日付はそれ自体が期間で、定休日の曜日の変更は「期間付きの毎週の規則」で表せるためです（判定の段階は違いますが、`holidayPolicy` のどの値でも結果は同じです。`reason` は `"closed-recurring"` になります）
- 「隔週」は `{ weekday, interval, anchor }` で書きます。`interval` は 2 以上の整数で、1 は毎週と同じなので受け付けません。`anchor` は `weekday` と同じ曜日の日付で、周期の位相を決めるだけです（起点より前の日にも当てはまります）。開始日を兼ねさせなかったのは、`anchor` の意味を 1 つに保つためで、開始日は `effectiveFrom` で書けます。起点を「偶数週・奇数週」や ISO 週番号にしなかったのは、年をまたぐと週の数え方が変わり、店舗の掲示（「○月○日から隔週」）と一致しなくなるためです
- 有効期間の診断（`never-matches`・`shadowed`・`redundant`・`out-of-range`）は 15 番に書きました。期間の中に当てはまる日がない規則は `never-matches` に含め、新しい code は足していません（message で区別します）

## 31. `businessDaysBetween` だけが半開区間

期間を取る API のうち、`daysBetween`・`listBusinessDays`・`holidaysBetween` は両端を含みますが、`businessDaysBetween(from, to)` は `from` 以上 `to` 未満の営業日の数です。

- 半開区間だと `businessDaysBetween(a, b) + businessDaysBetween(b, c) = businessDaysBetween(a, c)` が成り立ち、`addBusinessDays(a, n)` の結果 `b` について `businessDaysBetween(a, b) = n` になります（`addBusinessDays` の逆算）。日数の差を求める `diffDays` も同じ考え方です
- 「期間の営業日の一覧」を返す `listBusinessDays` は両端を含むほうが自然で、数が要るなら `.length` で求められます。「Between なのに範囲の扱いが違う」という違和感はありますが、名前を変える（`countBusinessDays` など）利用者の作業に見合う利益がないので、名前は変えず、README に範囲の扱いを明記します

## 32. 国ごとの日時の変換関数（`toJapanDate`・`toJapanDateTime`）は非推奨にし、国に依らない経路に集約する

`bizdays-toolkit/jp` の `toJapanDate`・`toJapanDateTime` を 0.10.0 で `@deprecated` にし、1.0.0 で削除します。移行先はルートの `toDateString(input, "Asia/Tokyo")`・`toDateTimeParts(input, "Asia/Tokyo")`、または営業日カレンダー・スケジュールの `dateOf`・`civilOf` です（同じ変換・同じ型）。

- 同じ変換が 3 経路にあり、国ごとの関数は日本だけの特別扱いでした（英国に `toLondonDate` はなく、足す予定もありません）。1.0.0 で API を固める前に、国に依らない 2 経路に減らします
- `bizdays-toolkit/jp` の祝日の関数（`isHoliday` など）は README の最初の例で使う入口なので残します。モジュール内の既定のカレンダーも、祝日の参照だけで設定を持たず共有しても結果が変わらないので残します
- 0.9.0 で型を強化した直後の非推奨ですが、0.9.x の利用がまだ広がっていない時点のほうが利用者の作業が少ないと判断しました。非推奨にしてから削除までは、互換性の約束（RELEASING.md）どおり少なくとも 1 つのマイナー版を置きます

## 33. 「祝日の翌日」は繰り返しの規則の形の 1 つ（`dayAfterHoliday: true`）

公立図書館・美術館の「祝日の翌日休館」のように、祝日そのものに従属する規則を、繰り返しの規則の新しい形として書けるようにしました（0.11.0）。

- 繰り返しの規則は曜日・第 n 曜日・日の形だけで、「祝日の翌日」は書けませんでした。回避策（`holidaysInYear` から翌日を生成して `closedDates` に入れる）は年を決めて生成する必要があり、個別の日付は毎年の月日より優先される（12 番）ので、「年末年始は祝日の翌日でも開館する」のような毎年の例外と順番が崩れます。規則であるべきものを結果として書くことになるため、規則として足しました
- 意味は「祝日の連続の翌日で、その日自身は祝日でない日」で、振替先（14 番）と同じ定義です。「祝日」は提供元の祝日だけで、休業日の設定は含めません（14 番と同じ理由）
- 当てはまる日は定義上祝日でないので、`onHolidayRule` は意味を持ちません。指定されたら `invalid-option` にします。黙って無視すると設定の意図を読み違えるためです。型では `never` にしていません。`{ ...rule, onHolidayRule }` のように既存の規則に `onHolidayRule` を重ねて書く使い方が、形の種類を知らなくてもできるようにするためで、実行時の検証で足ります
- 判定は繰り返しの規則の段階（12 番）で、配列の順番どおりです。月曜の祝日の翌日は「月曜の規則（`"after-holiday"`）の振替先」でも「祝日の翌日」でもあり、先に書いた規則が決めます
- 診断では、当てはまる日が年ごとの祝日で変わるため、曜日の規則との包含（`shadowed`）は判定せず、祝日の翌日の規則どうし（`months` と有効期間）に限ります。種類をまたぐ重なりは `redundant` で見つかります（15 番の考え方と同じ）
- 「祝日の前日」は需要が見えるまで入れません

## 34. カレンダーの合成は作成済みのカレンダーに対して行い、判定を決めたカレンダーの結果を引き継ぐ

`combineCalendars(calendars, { businessDay: "all" | "any" })` は、作成済みの営業日カレンダーを合成して、通常の営業日カレンダーを返します（0.11.0）。

- 設定を結合して 1 つのカレンダーを作る方法では、片方の臨時営業日（`openDates`、最優先）がもう片方の休業日を打ち消し、意味が保てません。片方を祝日の提供元として包む方法は、相手の休業日が `isHoliday()` で true になり、`holidayPolicy: "open"` の設定で相手の休業日に営業し、振替先も相手の休業日まで飛びます（14 番が避けた状態）。祝日と休業日の区別を壊さないため、作成済みのカレンダーの判定結果を組み合わせます。各カレンダーの中の判定の順番（12 番）は変わりません
- `dayInfo` には `"combined"` のような新しい `reason` を足さず、合成結果と同じ判定をした最初のカレンダーの `reason`・`name`・`shiftedFrom` を引き継ぎ、そのカレンダーの番号を `decidedBy` で返します。「年末年始休業（`closed-annual`）で休み、決めたのは 0 番」と読めるほうが、理由を 1 つの値に潰すより役に立つためです。「合成結果と同じ判定をした最初のカレンダー」は `"all"`・`"any"` のどちらでも、営業日・休業日のどちらでも必ず 1 つに決まります
- 祝日（`holiday`・`isHoliday`・`holidaysInYear`）は、各カレンダーの提供元の和集合で判定します。`outOfRange` は、どれかが `"throw"` なら `"throw"` です（そのカレンダーの判定が例外になるため）。このために `HolidayLookup` に `outOfRange` を公開しました
- タイムゾーンは同じでなければなりません（既存の `time-zone-conflict`）。日付の文字列を各カレンダーに渡して判定するため、暦日の意味がそろっている必要があります
- 公開インターフェース（`Calendar`）だけで合成するので、合成したカレンダーをさらに合成できます。設定の診断は設定に対するものなので、合成したカレンダーは対象にしません
- 内部では、営業日の探索・調整・月の営業日の実装を `createCalendar` から切り出して共用しています。合成でも `maxSearchDays` を指定できます
